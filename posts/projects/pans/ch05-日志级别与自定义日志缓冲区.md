## 1. 处理跨平台符号导入和导出

在 pans/include 目录下创建export.h

```cpp
#ifndef PANS_INCLUDE_PANS_EXPORT_H
#define PANS_INCLUDE_PANS_EXPORT_H
...
#endif // PANS_INCLUDE_PANS_EXPORT_H
```

首先防止头文件被重复包含

```cpp
#if defined(_WIN32) && defined(PANS_SHARED_LIBRARY)
// 在编译pans库本身的时候，通过__declspec(dllexport)，告诉编译器，把符号导出到DLL
#if defined(PANS_BUILDING_LIBRARY)
#define PANS_API __declspec(dllexport)
#else
// 其它项目使用pans动态库的时候，__declspec(dllimport)告诉编译器，符号来自于DLL
#define PANS_API __declspec(dllimport)
#endif
```

在 Windows 平台上，如果想让一个函数或类能够被其他程序（或其他 DLL）调用，需要使用 \_\_declspec(dllexport) 显式地告诉编译器“该符号是要导出的”。

而在使用这个动态库的应用程序中，则需要用 \_\_declspec(dllimport) 来标记。

```cpp
// 通过__attribute__((visibility("default")))，确保符号对外可见
#elif defined(__GNUC__) && defined(PANS_SHARED_LIBRARY)
#define PANS_API __attribute__((visibility("default")))
#else
#define PANS_API
#endif

#endif // PANS_INCLUDE_PANS_EXPORT_H
```

Linux 下的 ELF 共享库默认会导出所有全局符号，我们使用编译选项 -fvisibility=hidden 将所有符号默认隐藏，然后只用这个属性显式标记需要导出的符号

如果前面的条件都不满足，这时 PANS_API 被定义为空

## 2. 定义日志级别

### 2.1 日志级别

接下来我们创建一个 log_level.h 文件，定义一个日志级别（Log Level）的类。

```cpp
#ifndef PANS_INCLUDE_PANS_LOGGER_LOG_LEVEL_H
#define PANS_INCLUDE_PANS_LOGGER_LOG_LEVEL_H

#include <cstdint>
#include <string_view>

#include <pans/export.h>

namespace pans {

class PANS_API LogLevel final {
  public:
    enum class Level : std::uint8_t {
        LOG_LV_DEBUG = 1, // 记录调试细节，如变量值，程序执行流程等
        LOG_LV_INFO = 2,  // 记录正常运行的信息
        LOG_LV_WARN = 3,  // 可能存在问题，但是程序还能继续运行
        LOG_LV_ERROR = 4, // 操作失败，或者功能异常，需要检查处理
        LOG_LV_FATAL = 5, // 严重故障，程序继续执行可能存在较大问题
        LOG_LV_OFF = 6,   // 用来关闭日志
    };

    [[nodiscard]] static std::string_view ToString(Level level) noexcept;
    [[nodiscard]] static LogLevel::Level
    FromString(std::string_view value) noexcept;
};
} // namespace pans

#endif // PANS_INCLUDE_PANS_LOGGER_LOG_LEVEL_H
```

- `<cstdint>`：提供定宽整数类型，比如 `std::uint8_t`。后面要用作为枚举的底层类型。
- `<string_view>`：提供 `std::string_view`，一种不拥有字符串内存的“视图”类型，用于高效传递字符串参数。

- `PANS_API` 是前面 `export.h` 中定义的宏。在编译动态库时，它会被展开为 `__declspec(dllexport)`（Windows）或 `__attribute__((visibility("default")))`（GCC），表示这个类是对外可见的接口。如果编译静态库或直接使用源码，它通常为空。

- `final` 是 C++11 引入的关键字，用在类声明末尾，表示这个类**不能被继承**

- C++11 引入了**强类型枚举**（scoped enumeration），它解决了传统枚举的几个问题：

1. **作用域隔离**：  
   传统枚举的成员会“泄漏”到枚举所在的作用域，比如：

    ```cpp
    enum Color { Red, Green, Blue };
    // 之后可以直接使用 Red，而不需要 Color::Red
    ```

    这容易与其他同名符号冲突。而 `enum class` 的成员必须通过 `Level::LOG_LV_DEBUG` 这种方式访问，不会污染外部作用域。

2. **禁止隐式转换为整数**：传统枚举可以隐式转换为 `int`，这可能导致一些不易察觉的错误。强类型枚举默认不能隐式转换为整数，必须显式使用 `static_cast`，提升了类型安全性。

3. **可以指定底层类型**：`enum class Level : std::uint8_t` 明确指定了枚举的底层存储类型为 `std::uint8_t`。适合表示有限的小数值集合。如果不指定，底层类型通常是 `int`（4 字节），浪费空间。尤其对于日志级别这种只有几个值的枚举，用 1 字节既节省内存，也方便在日志记录中传输。

- `[[nodiscard]]` 是 C++17 引入的属性，标记在函数返回值类型前。**如果调用者忽略了该函数的返回值，编译器应该发出警告**。这对于有返回值的函数非常有用，可以防止程序员无意中丢弃重要结果。 这里两个函数都返回有意义的值（字符串表示或枚举值），忽略它们通常是编程错误，所以加上了 `[[nodiscard]]`。

- `noexcept`，表示它们**不会抛出异常**。日志系统可能在异常处理路径中被调用（比如捕获异常后记录日志），如果日志函数本身可能抛异常，就会导致更严重的问题。因此日志相关函数通常设计为不抛异常。

然后我们实现一下 log_level.cc 文件

### 2.2 ToString函数

```cpp
#include <algorithm>
#include <array>
#include <cctype>
#include <pans/logger/log_level.h>
#include <string>

namespace pans {
std::string_view LogLevel::ToString(Level level) noexcept {
    switch (level) {
#define XX(name)                                                               \
    case Level::LOG_LV_##name:                                                 \
        return #name;
        XX(DEBUG)
        XX(INFO)
        XX(WARN)
        XX(ERROR)
        XX(FATAL)
        XX(OFF)
#undef XX
    }
    return "UNKNOWN";
}
...
}
```

这个函数使用了 **X Macro** 技巧来避免重复书写大量的 `case` 语句。`switch(level)` 根据传入的枚举值执行不同的分支。由于 `Level` 是 `enum class`，其值可以直接在 `switch` 中使用（虽然 `enum class` 不能隐式转换为整数，但在 `switch` 的条件中，编译器会进行整型提升，枚举类会被转换为底层整数类型）。

- `#define XX(name) ...` 定义了一个带参数的宏，参数名为 `name`。
- `Level::LOG_LV_##name`：`##` 是宏中的**连接运算符**，它将左右两个记号连接成一个新的记号。例如当 `name` 是 `DEBUG` 时，`LOG_LV_##name` 变成 `LOG_LV_DEBUG`，再加上前缀 `Level::` 就得到了 `Level::LOG_LV_DEBUG`。
- `return #name;`：`#` 是宏中的**字符串化运算符**，它将参数 `name` 转换为字符串字面量。例如 `XX(DEBUG)` 中 `#name` 变成 `"DEBUG"`。

如果传入的 `level` 不在枚举定义的有效值范围内（比如有人显式 `static_cast<Level>(100)`），`switch` 没有匹配的 `case`，就会执行这个默认返回。这里返回字符串 `"UNKNOWN"` 表示未知级别。

### 2.3 FromString 函数

这个函数将输入的字符串（不区分大小写）转换为对应的枚举值。

```cpp
LogLevel::Level LogLevel::FromString(std::string_view value) noexcept {
    std::array<char, 6> normalized{};
    std::transform(value.begin(), value.end(), normalized.begin(),
                   [](unsigned char character) {
                       return static_cast<char>(std::toupper(character));
                   });
    const std::string_view upper_value(normalized.data(), value.size());
#define XX(name)                                                               \
    if (upper_value == #name)                                                  \
        return Level::LOG_LV_##name;
    XX(DEBUG)
    XX(INFO)
    XX(WARN)
    XX(ERROR)
    XX(FATAL)
    XX(OFF)
#undef XX
    return Level::LOG_LV_OFF;
}
```

- `std::array<char, 6>` 定义了一个包含 6 个 `char` 的固定数组作为缓冲区，并且使用 `{}` 进行值初始化，所有元素被初始化为 `'\0'`。枚举中最长的名称都是 5 个字符，再加一个结尾的 `'\0'` 就是 6。

- `std::transform` 是标准算法，它遍历输入范围 `[value.begin(), value.end())`，对每个元素应用一元操作（这里是 lambda 表达式），并将结果写入从 `normalized.begin()` 开始的输出范围。

- Lambda 参数类型是 `unsigned char`，这是为了安全地传递给 `std::toupper`。C 标准库的 `toupper` 函数要求参数是 `int`，且值必须在 `unsigned char` 的范围内或为 `EOF`。如果直接传递 `char` 且 `char` 是有符号类型，且字符为负数（比如非 ASCII 字符），可能导致未定义行为。因此这里先将 `char` 隐式转换为 `unsigned char` 再传递给 `toupper`（`toupper` 接受 `int`，`unsigned char` 会安全地提升为 `int`）。

- `std::toupper` 返回的是 `int`，所以我们用 `static_cast<char>` 将其转回 `char` 存入 `normalized`。

- `normalized.data()` 返回指向数组首元素的指针。

- `upper_value` 是 `std::string_view` 类型，大小为 `value.size()`，与字符串字面量（`const char*`）比较时，`std::string_view` 提供了 `operator==` 的重载，可以比较字符串内容是否相等。因此这里的比较是值比较，而不是指针比较。

如果没有匹配任何已知级别，返回 `LOG_LV_OFF`。

## 3. 自定义日志缓冲区

日志记录需要高效、低延迟，并且不能因为日志的写入而影响服务器核心性能。我们需要设计一套自定义的日志缓冲区，它能在栈上分配内存来应对高频、小数据量的日志，当遇到超长日志时再回到堆上分配。

在服务器环境中，日志操作非常频繁，如果每次都使用 `std::string` 或 `std::ostringstream` 动态分配内存，会带来大量的堆分配和释放，影响性能。我们可以采取以下方案：

- **Inline Buffer**：在对象内部嵌入一个固定大小的数组（栈上），大多数日志消息都很短，可以直接放在这个数组里，避免堆分配。
- **Overflow Buffer**：当消息长度超过内联容量时，切换到 `std::vector<char>`（堆上）来存储，并自动扩容。

### 3.1 配置常量

```cpp
#ifndef PANS_SRC_LOGGER_BUFFER_CONFIG_H
#define PANS_SRC_LOGGER_BUFFER_CONFIG_H

#include <cstddef>

namespace pans::detail {

inline constexpr std::size_t LOG_MESSAGE_INLINE_CAPACITY = 128;
inline constexpr std::size_t PRINTF_FORMAT_INLINE_CAPACITY = 128;
inline constexpr std::size_t FORMATTED_RECORD_INLINE_CAPACITY = 256;

} // namespace pans::detail

#endif
```

- `constexpr` 表示该变量在编译期就可以求值，并且是常量。

- `inline` 是 C++17 引入的，用于修饰变量或函数，允许它们在多个编译单元中被定义而不违反 ODR 。对于 `constexpr` 变量，默认具有内部链接，但加上 `inline` 可以让它们具有外部链接，同时保证在所有包含此头文件的编译单元中是同一个实体，不会产生重复定义错误。

### 3.2 核心缓冲区实现

```cpp
#ifndef PANS_SRC_LOGGER_BUFFER_H
#define PANS_SRC_LOGGER_BUFFER_H

#include <algorithm>
#include <array>
#include <cstddef>
#include <cstring>
#include <streambuf>
#include <string_view>
#include <vector>

template <std::size_t INLINE_CAPACITY>
class InlineBuffer
{
public:
    void append(const char* data, std::size_t size) { ... }
    void append(std::string_view value) { ... }
    void append(char value) { ... }
    [[nodiscard]] const char* data() const noexcept { ... }
    [[nodiscard]] std::size_t size() const noexcept { ... }
    [[nodiscard]] std::string_view view() const noexcept { ... }

private:
    std::array<char, INLINE_CAPACITY> m_inline{};
    std::vector<char> m_overflow;
    std::size_t m_size = 0;
};
```

`template <std::size_t INLINE_CAPACITY>` 使得 `InlineBuffer` 可以适应不同的内联容量需求。

- `std::array<char, INLINE_CAPACITY> m_inline{}`：一个固定大小的字符数组，位于对象内部（如果是栈上对象，则在栈上）。`{}` 初始化将其所有元素值初始化为零。这是我们的“快速通道”存储。
- `std::vector<char> m_overflow` 动态数组，默认为空。只有当数据量超过内联容量时才会使用。`std::vector` 自动管理内存，并且可以动态扩容。
- `std::size_t m_size = 0` 当前缓冲区中已存储的字节数。当使用内联存储时，它等于已写入 `m_inline` 的字节数；当使用溢出存储时，它等于 `m_overflow.size()`。

### 3.3 append 函数

`append(const char* data, std::size_t size)` 用于向缓冲区追加一段数据。

```cpp
void append(const char *data, std::size_t size) {
    if (size == 0)
        return;

    if (m_overflow.empty() && m_size + size <= INLINE_CAPACITY) {
        std::memcpy(m_inline.data() + m_size, data, size);
        m_size += size;
        return;
    }

    if (m_overflow.empty()) {
        const std::size_t required_capacity = m_size + size;
        m_overflow.reserve(
            std::max(INLINE_CAPACITY * 2, required_capacity));
        m_overflow.insert(m_overflow.end(), m_inline.data(),
                          m_inline.data() + m_size);
    }
    m_overflow.insert(m_overflow.end(), data, data + size);
    m_size = m_overflow.size();
}
```

1. 如果 `size == 0`，直接 return。

2. `m_overflow.empty() && m_size + size <= INLINE_CAPACITY` 表示目前还没有使用溢出缓冲区，并且追加后总大小不会超过内联容量。我们直接将数据拷贝到 `m_inline` 的末尾：`std::memcpy(m_inline.data() + m_size, data, size);` 然后更新 `m_size`。 `m_inline.data()` 返回指向数组首元素的指针，`+ m_size` 得到当前写入位置的指针。

3. 如果内联容量不够，我们需要将数据放入 `m_overflow`。但第一次进入时，`m_overflow` 还是空的，所以需要先把之前内联缓冲区中已有的数据迁移到溢出缓冲区。
    - `if(m_overflow.empty())` 确保只执行一次初始化迁移。
    - 计算迁移后所需的总容量 `required_capacity` 。
    - `reserve` 预先分配足够的内存，避免后续插入时频繁重新分配。选择 `INLINE_CAPACITY * 2` 和 `required_capacity` 的较大者作为初始容量，这样即使后续再有少量追加也不需要再次扩容。
    - 将内联缓冲区中已有的 `m_size` 个字节拷贝到 `m_overflow` 中。

4. **追加新数据到溢出缓冲区**：调用 `m_overflow.insert()` 将新数据追加到 `m_overflow` 末尾。最后更新 `m_size = m_overflow.size()`。

- 内联路径非常快，只有一次 `memcpy` 和一次加法。
- 溢出路径第一次会拷贝内联数据，之后就直接在 `vector` 上操作，可能涉及扩容，但因为 `reserve` 通常不会频繁扩容。

### 3.4 其他 append 重载

```cpp
void append(std::string_view value) { append(value.data(), value.size()); }

void append(char value) { append(&value, 1); }
```

- `std::string_view` 重载：允许直接传入字符串视图（例如从 `"hello"` 隐式转换）。
- `char` 重载：允许追加单个字符，通过传递该字符的地址和长度 1 实现。

### 3.5 访问方法

```cpp
[[nodiscard]] const char *data() const noexcept {
    return m_overflow.empty() ? m_inline.data() : m_overflow.data();
}

[[nodiscard]] std::size_t size() const noexcept { return m_size; }

[[nodiscard]] std::string_view view() const noexcept {
    return {data(), size()};
}
```

- `data()` 返回指向当前实际存储数据的指针。如果溢出缓冲区是空的，返回 `m_inline.data()`；否则返回 `m_overflow.data()`。  
  注意：当 `m_overflow` 非空时，`m_inline` 可能还保留着旧数据，但我们已经不再使用它。`m_overflow` 中存储了完整的数据。
- `size()` 返回当前数据长度。
- `view()` 利用 `data()` 和 `size()` 构造一个 `std::string_view`，方便调用者使用只读字符串视图，避免拷贝。

### 3.6 `SmallStreamBuffer` 类实现

```cpp
template <std::size_t INLINE_CAPACITY>
class SmallStreamBuffer final : public std::streambuf {
  public:
    explicit SmallStreamBuffer(InlineBuffer<INLINE_CAPACITY> &buffer) noexcept
        : m_buffer(buffer) {}

  protected:
    std::streamsize xsputn(const char *data, std::streamsize size) override {
        if (size <= 0)
            return 0;

        m_buffer.append(data, static_cast<std::size_t>(size));
        return size;
    }

    int_type overflow(int_type character) override {
        if (traits_type::eq_int_type(character, traits_type::eof())) {
            return traits_type::not_eof(character);
        }

        m_buffer.append(traits_type::to_char_type(character));
        return character;
    }

  private:
    InlineBuffer<INLINE_CAPACITY> &m_buffer;
};
```

1. `std::streambuf` 是 C++ 标准库中流缓冲区的基础类，负责字符的输入输出缓冲。通过继承它并重写几个虚函数，我们可以自定义缓冲区行为，然后将这个 streambuf 对象与一个 `std::ostream` 关联，这样就能使用 `<<` 操作符将数据写入我们的 `InlineBuffer`。

2. `SmallStreamBuffer()` 接收一个 `InlineBuffer` 的引用并保存，后续所有写入都会转发到这个缓冲区。

3. `xsputn` 是 `std::streambuf` 的受保护虚函数，用于高效地写入一块连续字符序列。当使用 `ostream::write()` 或 `<<` 输出字符串时，流会调用这个方法，而不是一个字符一个字符地调用 `overflow`。

4. `overflow` 是 `std::streambuf` 的另一个虚函数，用于处理单个字符的写入。当输出缓冲区没有空间或者流需要刷新时，会调用这个函数。 `character` 是要写入的字符，类型是 `int_type`（通常是 `int`），可能包含特殊值 `traits_type::eof()` 表示“文件结束”或“无字符”。如果成功，返回一个非 EOF 值（通常是写入的字符或 `traits_type::not_eof(character)`），如果失败，返回 EOF。

### 4.1 实现 CMakeLists.txt 文件

```cmake
set(INNER_TEST_NAME test_log_buffer)
```

```cmake
add_executable("${INNER_TEST_NAME}" "${INNER_TEST_SOURCE}")
```

- `add_executable(<name> <source>)` 告诉 CMake 生成一个可执行文件，名称是 `test_log_buffer`，源文件是之前指定的 `.cpp` 文件。CMake 会根据这个命令创建一个编译目标。

```cmake
target_link_libraries("${INNER_TEST_NAME}" PRIVATE pans Threads::Threads)
```

- `target_link_libraries` 指定目标需要链接的库。
- `PRIVATE` 表示这些库仅用于构建该目标自身，不会传递给依赖此目标的其他目标。
- `pans`：这是要测试的库目标。

```cmake
target_include_directories("${INNER_TEST_NAME}" PRIVATE "${PROJECT_SOURCE_DIR}/pans/src")
```

- `target_include_directories` 为目标添加头文件搜索路径。
- `${PROJECT_SOURCE_DIR}/pans/src`：指向项目根目录下的 `pans/src` 目录。测试代码可能会包含一些内部头文件（比如之前看到的 `buffer.h` 位于 `pans/src/logger/` 下），这些头文件可能不属于 `include` 目录，需要手动添加。

```cmake
set_target_properties("${INNER_TEST_NAME}" PROPERTIES
    RUNTIME_OUTPUT_DIRECTORY "${PANS_TEST_OUTPUT_DIRECTORY}"

```

- `set_target_properties` 设置目标的属性。
- `RUNTIME_OUTPUT_DIRECTORY` 指定可执行文件的输出目录。`${PANS_TEST_OUTPUT_DIRECTORY}` 表示所有测试可执行文件统一的输出位置。

CMake 生成器分为单配置和多配置：

- 单配置生成器（如 Unix Makefiles、Ninja）在构建时只生成一种配置（如 Debug 或 Release），由 `CMAKE_BUILD_TYPE` 决定。
- 多配置生成器（如 Visual Studio、Xcode）可以在同一个构建目录中生成多个配置，每个配置的输出目录可能不同。

对于单配置生成器，设置 `RUNTIME_OUTPUT_DIRECTORY` 即可。

```cmake
foreach(CONFIG IN LISTS CMAKE_CONFIGURATION_TYPES)
    string(TOUPPER "${CONFIG}" CONFIG_UPPER)
    set_target_properties("${INNER_TEST_NAME}" PROPERTIES
        "RUNTIME_OUTPUT_DIRECTORY_${CONFIG_UPPER}" "${PANS_TEST_OUTPUT_DIRECTORY}"
    )
endforeach()
```

- `foreach(CONFIG IN LISTS CMAKE_CONFIGURATION_TYPES)`：遍历每一个配置类型。对于多配置生成器，`CMAKE_CONFIGURATION_TYPES`变量包含所有可用的构建类型。对于单配置生成器，该变量为空。
- `string(TOUPPER "${CONFIG}" CONFIG_UPPER)`：将配置名转换为大写。然后为每个配置单独设置输出目录，确保无论构建哪个配置，测试可执行文件都输出到同一个 `PANS_TEST_OUTPUT_DIRECTORY`。

```cmake
add_test(NAME "${INNER_TEST_NAME}" COMMAND "${INNER_TEST_NAME}")
```

- `add_test` 向 CTest 注册一个测试。
- `NAME` 参数指定测试名称。
- `COMMAND` 指定要运行的命令。

### 4.2 实现日志缓冲区测试文件

然后我们创建 `test_log_buffer.cpp` 用来比较我们自定义的日志缓冲区 `SmallStreamBuffer` 和标准库的 `std::stringstream` 在写入字符串时的效率。模拟高频日志写入的场景，通过测量执行时间、平均每次操作耗时，来展示自定义缓冲区的优势。

```cpp
#include <array>
#include <atomic>
#include <chrono>
#include <cstddef>
#include <cstdint>
#include <iomanip>
#include <iostream>
#include <sstream>
#include <string>
#include <string_view>

#include "logger/buffer.h"
#include "logger/buffer_config.h"

constexpr int RUNS = 7;
std::uint64_t g_target = 0;
std::atomic<std::uint64_t> BENCHMARK_SINK{0};
```

- `RUNS` 这里设置每次测试重复运行的次数为 7，最终取平均值。
- `g_target` 是每次测试中操作执行的次数。
- `BENCHMARK_SINK` 是一个类型为 `std::atomic<std::uint64_t>` 的原子变量，初始化为 0。作用是**防止编译器优化掉我们的测试代码**。

在测试中，我们关心的是函数执行的时间。但如果编译器发现测试结果没有被使用，并且函数本身没有副作用，它可能会将整个循环优化掉，导致计时不准确。为了强制编译器保留计算过程，我们把每次迭代产生的校验和（checksum）最终异或（XOR）到这个原子变量中。这样，即使校验和的值没有被输出，编译器也不能假设这个操作是多余的，因为 `BENCHMARK_SINK` 是一个全局变量，它的值可能会影响程序的其他部分。使用原子类型是因为我们可能在多线程环境下考虑，而且 `fetch_xor` 本身也有内存序语义，确保操作不会被重排或省略。

#### `Observe` 函数

```cpp
std::uint64_t Observe(std::string_view value) noexcept
{
    return static_cast<std::uint64_t>(value.size()) +
           static_cast<unsigned char>(value.front()) +
           static_cast<unsigned char>(value[value.size() / 2]) +
           static_cast<unsigned char>(value.back());
}
```

这个函数接收一个 `std::string_view`，返回一个 `std::uint64_t` 的“校验和”。它把字符串长度、首字符、中间字符、尾字符的整数值相加。这里假设 `value` 非空（我们测试的消息长度都大于 0），所以调用 `front()` 和 `back()` 是安全的。

**为什么需要这个函数？**  
测试函数（比如 `WriteWithSmallStreamBuffer`）写完缓冲区后，需要返回一个值，这样外部才能把返回值累加并最终喂给 `BENCHMARK_SINK`。`Observe` 的作用就是从缓冲区内容中提取一个与内容相关的数值，使得编译器无法预先计算出结果（因为内容每次可能不同），从而确保写入操作确实被执行。如果没有这个函数，测试函数可能返回 `void`，然后编译器可能把整个写入过程优化掉。

#### 两种写入方式的实现

1. 使用自定义 `SmallStreamBuffer`

```cpp
std::uint64_t WriteWithSmallStreamBuffer(std::string_view message)
{
    pans::detail::InlineBuffer<pans::detail::LOG_MESSAGE_INLINE_CAPACITY> buffer;
    pans::detail::SmallStreamBuffer<pans::detail::LOG_MESSAGE_INLINE_CAPACITY> stream_buffer(buffer);
    std::ostream stream(&stream_buffer);
    stream << message;
    return Observe(buffer.view());
}
```

- `InlineBuffer<LOG_MESSAGE_INLINE_CAPACITY>` 是我们之前设计的栈缓冲区，这里实例化时容量来自配置常量。
- `SmallStreamBuffer` 继承自 `std::streambuf`，它把流写入的数据转发到 `InlineBuffer`。
- 然后创建一个 `std::ostream` 对象，并将它的缓冲区指向我们的 `stream_buffer`。这样，使用 `<<` 操作符向 `stream` 写入时，数据会进入我们的 `InlineBuffer`。
- 最后通过 `buffer.view()` 获得 `std::string_view`，传给 `Observe` 生成校验和。

**整个过程没有任何堆分配**（如果消息长度小于内联容量）。栈上创建了三个对象，它们都在栈上。

2. 使用标准 `std::stringstream`

```cpp
std::uint64_t WriteWithStringStream(std::string_view message)
{
    std::stringstream stream;
    stream << message;
    return Observe(stream.view());
}
```

- `std::stringstream` 在内部使用 `std::string` 作为缓冲区。
- 当向 `stream` 写入数据时，`std::stringstream` 会动态管理内存（堆分配），通常需要至少一次 `malloc`。
- `stream.view()` 是 C++20 为 `std::stringstream` 添加的成员函数，返回一个 `std::string_view`，指向其内部字符串。这个操作不拷贝数据，只是提供一个视图。

#### 基准测试模板函数

1. `BenchmarkWrites`

```cpp
template <typename Operation>
std::chrono::nanoseconds BenchmarkWrites(Operation&& operation)
{
    std::uint64_t checksum = 0;
    const auto begin = std::chrono::steady_clock::now();
    for(std::uint64_t iteration = 0; iteration < g_target; ++iteration)
    {
        checksum += operation();
    }
    const auto end = std::chrono::steady_clock::now();
    BENCHMARK_SINK.fetch_xor(checksum, std::memory_order_relaxed);
    return std::chrono::duration_cast<std::chrono::nanoseconds>(end - begin);
}
```

- 这是一个函数模板，接受任意可调用对象 `operation`，返回执行 `g_target` 次操作所花费的纳秒数。
- `Operation&&` 是**万能引用**，可以绑定左值或右值，这里我们传入的是 lambda 临时对象，所以是右值。
- 在循环开始前记录开始时间 `begin`，循环内重复调用 `operation()` 并将返回值累加到 `checksum`。
- 循环结束后记录结束时间 `end`，然后将 `checksum` 异或到全局原子变量 `BENCHMARK_SINK` 中，使用 `std::memory_order_relaxed` 内存序，因为这个操作只是为了产生副作用，不需要同步。
- 最后返回 `std::chrono::duration_cast<std::chrono::nanoseconds>(end - begin)`，将时间差转换为纳秒。

**为什么使用 `steady_clock`？**：`std::chrono::steady_clock` 是单调时钟，不会被系统时间调整影响，适合测量时间间隔。

2. `Run` 模板函数

```cpp
template <typename Benchmark>
double Run(Benchmark&& benchmark)
{
    long double total_nanoseconds = 0.0L;
    for(int run = 0; run < RUNS; ++run)
    {
        total_nanoseconds += static_cast<long double>(benchmark().count());
    }
    return static_cast<double>(total_nanoseconds / RUNS);
}
```

- 这个函数接受一个可调用对象 `benchmark`，它会执行 `RUNS` 次，每次都调用 `benchmark()` 并累加耗时。`benchmark()` 返回的是一个 `std::chrono::nanoseconds` 对象，调用 `.count()` 获取其内部数值。
- 使用 `long double` 累加以保证精度，最后返回平均值（转换为 `double`）。

#### 输出辅助函数 `PrintResult`

```cpp
void PrintResult(std::string_view name, double total_nanoseconds)
{
    std::cout << std::left << std::setw(30) << name << std::right
              << total_nanoseconds << " ns \ttotal, "
              << total_nanoseconds / static_cast<double>(g_target) << " ns/op\n";
}
```

#### 主函数 `main`

```cpp
int main(int argc, char** argv)
{
    if(argc != 2)
    {
        std::cerr << "Usage: ./test_log_buffer count\n";
        return 1;
    }
    g_target = std::stoull(argv[1]);

    std::cout << std::fixed << std::setprecision(2);
    std::cout << "operations: " << g_target << ", average of " << RUNS << " runs\n\n";
    constexpr std::array<std::size_t, 6> MESSAGE_SIZES = {50, 100, 200, 500, 1000, 2048};
    for(const std::size_t message_size : MESSAGE_SIZES)
    {
        const std::string message(message_size, 'x');
        const double small_stream_buffer_nanoseconds = Run([&]() {
            return BenchmarkWrites([&]() { return WriteWithSmallStreamBuffer(message); });
        });
        const double stringstream_nanoseconds = Run([&]() {
            return BenchmarkWrites([&]() { return WriteWithStringStream(message); });
        });

        std::cout << "message: " << message_size << " characters"  << '\n';
        PrintResult("SmallStreamBuffer", small_stream_buffer_nanoseconds);
        PrintResult("std::stringstream", stringstream_nanoseconds);
        std::cout << "speedup: " << stringstream_nanoseconds / small_stream_buffer_nanoseconds << "x\n\n";
    }

    return 0;
}
```

- `std::stoull(argv[1])` 将字符串转换为 `unsigned long long`，存入 `g_target`。
- 定义一个编译期数组 `MESSAGE_SIZES`，包含 6 种消息长度。这些长度覆盖了小于内联容量、略大于内联容量、以及远大于内联容量的情况。
- 对于每种长度：
    - 创建一条由 `message_size` 个 `'x'` 组成的 `std::string`。
    - 使用 `Run` 分别测试 `WriteWithSmallStreamBuffer` 和 `WriteWithStringStream`，传入 lambda 捕获 `message`，lambda 内部调用 `BenchmarkWrites`，再内部调用具体的写入函数。
- 输出每种消息长度下两种方法的平均总耗时和每次操作耗时，并计算加速比。如果加速比大于 1，说明自定义缓冲区更快。
