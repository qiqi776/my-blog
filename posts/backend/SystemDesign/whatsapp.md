## WhatsApp 即时通讯系统设计

本文设计的是一个类似 WhatsApp 的即时通讯系统。用户需要能创建单聊和群聊、实时收发消息、在离线后补收消息，还要支持媒体消息与多设备同步。它和普通 CRUD 系统最大的不同，在于核心路径是长连接和事件投递，而不是短请求。系统一边要维持海量在线连接，一边还要保证消息不丢、尽快送达、掉线后能补发。因此，设计重点不只是“消息存哪”，而是如何让在线用户低延迟收消息，如何保证离线用户最终能收到消息，如何在多台 Chat Server 之间正确路由消息，以及如何处理连接断开、漏消息和多设备同步。

### 问题定义与边界

#### 功能需求

用户能够创建最多 `100` 人的群聊；用户能够发送和接收消息；用户离线时，系统能在最多 `30` 天内为其保留未送达消息；用户能够发送和接收媒体消息。

#### 非功能需求

1. 低延迟：在线用户应在约 `500ms` 内收到消息
2. 可送达：消息最终必须能送到用户
3. 大规模：系统需要支撑十亿级用户和极高吞吐
4. 最小化中心存储：消息不应在中心服务器上无限保留
5. 高可用：单点组件故障不能导致整体不可用

#### 本文暂不展开

音视频通话、注册登录与用户资料管理、端到端加密协议细节、商业号、朋友圈、状态等扩展能力。

### 核心实体、接口与数据模型

#### 核心实体

`Chat`：聊天会话；`ChatParticipant`：会话参与者关系；`Message`：消息正文；`Inbox`：尚未被目标客户端确认的待投递消息；`Client`：用户的具体设备；`LastSeen`：用户最近一次断线时间。这里最重要的建模思想，是把“消息正文”和“投递状态”拆开：`Message` 保存消息本体，`Inbox` 保存“谁还没收到这条消息”，这样系统才能同时满足实时投递和离线补偿。

#### 连接与 API

这类系统更合适的接口不是 REST，而是基于 `WebSocket` 的双向长连接。客户端和服务端建立 TLS 加密的 socket 后，双方通过命令消息交互。最小 API 可以整理为：`createChat`、`sendMessage`、`ack`、`getAttachmentTarget`、`sync`、`getLastSeen`。

例如：

```json
// -> createChat
{
  "participants": [],
  "name": ""
}
```

```json
// -> sendMessage
{
  "chatId": "",
  "message": "",
  "attachments": []
}
```

```json
// -> ack
{
  "messageId": "",
  "clientId": ""
}
```

#### 数据模型

一个比较自然的表设计如下：`Chat` 主键 `chatId`；`ChatParticipant` 主键 `chatId + participantId`，GSI `participantId + chatId`；`Message` 主键 `messageId`，可带 `chatId + createdAt` 索引用于拉历史消息；`Inbox` 主键 `recipientUserId` 或 `clientId`，值为待确认的 `messageId`；`Client` 主键 `userId + clientId`；`LastSeen` 主键 `userId`。这类系统通常适合 DynamoDB 这类高吞吐 KV/宽表存储；数据库名字不是重点，重点是这些表都偏向按 key 查询和高写入，不依赖复杂 join。

### 核心架构设计

#### 一、用户能够创建聊天

第一步，用户通过 `createChat` 请求创建会话。服务端完成三件事：写入一条 `Chat`、为每个参与者写入一条 `ChatParticipant`、返回 `chatId`。`ChatParticipant` 的访问模式很明确：需要按 `chatId` 查出所有参与者，需要按 `participantId` 查出一个用户加入了哪些聊天，因此很适合“主键 + 反向 GSI”的结构。

#### 二、用户能够在线收发消息

最早期的单机版设计其实很简单：用户连到一个 `Chat Server`，服务器在内存里维护 `userId -> websocket connection`，某个用户发消息时，服务端先查 `ChatParticipant`，然后把消息直接推给所有在线参与者。这个设计显然不能扩展，但它是一个很好的起点：先把真实的消息收发机制讲清楚，再逐步扩到分布式。

#### 三、用户离线时也能收到消息

只靠内存连接映射，消息一旦目标用户不在线就丢了。所以系统必须加入持久化投递层。最直接的办法是引入 `Inbox`：用户发送 `sendMessage`；`Chat Server` 查出聊天参与者；先把消息写入 `Message`；再为每个接收者写入一条 `Inbox`；然后立即尝试通过当前 WebSocket 推送 `newMessage`；客户端收到后回 `ack`；服务端收到 `ack` 后删除对应 `Inbox` 记录。

这样就实现了两层保障：在线用户尽量走实时推送，离线用户依靠 `Inbox` 做最终投递。当用户重新连上来时，服务端只需要查 `Inbox`、找到所有未确认的 `messageId`、回查 `Message`、顺序推回客户端、等客户端 `ack` 后删除 `Inbox`。这条链路构成了系统的可靠性骨架。为了满足“中心服务器不长期保留消息”的需求，`Message` 和 `Inbox` 都可以挂 TTL，例如 `30` 天。

#### 四、用户能够发送媒体消息

媒体消息不能直接塞进聊天数据库，也不适合通过 WebSocket 长连接承载完整大文件。一个能工作但不理想的方案，是让 `Chat Server` 先接收媒体，再转存到 blob storage，这样至少把大对象从数据库里拿走了。但更好的方案，是把媒体上传链路和聊天控制链路彻底拆开：客户端先通过 `getAttachmentTarget` 向服务端申请上传目标；服务端返回预签名上传 URL；客户端直接把文件传到 blob storage；上传完成后，客户端把附件 URL 当作普通消息元数据发给 `Chat Server`；接收方再通过受控 URL 下载。这样 Chat Server 就退回控制面，不再亲自搬运二进制大文件。

### 深入讨论

#### 一、如何扩展到海量在线用户

如果系统有 `1B` 用户，可能同时有约 `200M` 在线，显然不可能靠一台机器维持所有 WebSocket 连接。但把多台 `Chat Server` 简单挂到负载均衡后面还不够，因为发送者可能连在 A 机器，接收者可能连在 B 机器，A 机器本地并不知道 B 机器上有哪些连接。也就是说，关键问题不是“如何横向扩容”，而是“如何跨节点路由消息”。一种常见做法是引入 `Pub/Sub`：每个在线用户对应一个用户级 topic/channel；当某个用户连到某台 `Chat Server` 时，这台服务器会订阅该用户的 channel；某条消息需要投递给该用户时，发送方所在服务器只需要向这个 channel 发布事件；正在订阅这个 channel 的 Chat Server 会收到事件并转发给本地 WebSocket。这个设计的好处是 Chat Server 之间不需要维持复杂的两两直连，路由逻辑从“找哪台机器”变成“发到哪个 channel”，节点扩缩容更自然。这里和 Kafka 的差别很关键：Kafka 适合持久化日志流，Redis Pub/Sub 这类系统更适合做轻量、瞬时的在线事件转发。因为这条链路本身不负责最终存储，消息真正的可靠性仍然来自前面的 `Message + Inbox` 写入。所以完整写路径应该是：先写 `Message`，再写 `Inbox`，最后向 Pub/Sub 发布实时投递事件。如果第三步失败，消息仍然不会丢，只是实时性下降，用户稍后会通过重连、轮询或补同步拿到消息。

#### 二、按用户分 channel 还是按聊天分 channel

这里有一个重要取舍：按用户分 channel，还是按聊天分 channel。如果按用户分 channel，每个在线用户只需订阅自己的 channel，非常适合 1:1 聊天占主导的场景。如果按聊天分 channel，一个大群发消息时只需发布一次，更适合大群场景。在以 1:1 聊天为主、群聊人数上限约 `100` 的前提下，按用户分 channel 更合理。不过对于特别大的群，系统也可以做自适应策略：普通聊天仍按用户 channel 投递，大群额外建立 chat-level channel，大群消息优先发到 chat-level channel。本质上，这是一种针对少数边缘大群的局部优化。

#### 三、如何支持多设备

一旦用户不只一个设备，之前“每个用户一个 Inbox”的模型就不够了。例如手机已经收到了消息，但笔记本还没开机；等笔记本上线后，它仍然应该补到这条消息。因此模型需要升级成：新增 `Client` 表，记录某个用户有哪些设备；`Inbox` 从“按用户”改成“按客户端”；一条消息发出后，要为目标用户的每个设备分别建立待确认记录。这样每个设备都可以独立 ACK、独立补同步。Pub/Sub 层反而不需要大改，因为它依旧只需按 `userId` 转发到当前在线的 Chat Server；真正的设备粒度确认发生在 `Inbox` 和 `Client` 这层。工程上通常还会限制设备数，例如每个账号最多 `3` 台设备，否则存储和写放大会明显恶化。

#### 四、WebSocket 断了但双方还没察觉怎么办

真实网络环境里，最麻烦的不是“明确断线”，而是连接其实已经死了，但 TCP 还没来得及超时。如果完全依赖 TCP keepalive，检测可能要花几分钟，这对聊天应用太慢了。因此需要应用层心跳：服务端每 `10~30s` 发一次 ping；客户端需要在短超时内返回 pong；如果没收到 pong，服务端主动关闭连接；客户端随后重连并从 `Inbox` 做补同步。这样系统能把断线检测时间收敛到十几秒量级，而不是几分钟。

#### 五、如果 Pub/Sub 漏投了一条消息怎么办

Pub/Sub 一般是 best-effort 的，例如 Redis Pub/Sub 属于 `at most once`，如果没有订阅者或中间出了短暂故障，实时事件可能直接丢掉。这不会破坏最终可靠性，因为消息已经持久化进 `Inbox`，但它会影响在线用户的实时体验。

常见补救有三层。其一，周期性轮询：客户端每隔 `30~60s` 主动发一次 `sync` 请求，看是否有漏掉的消息。这是最简单的兜底，但轮询频率越高，系统读压越大。其二，序列号检测：可以给每个聊天或每个用户维护单调递增序列号，客户端如果收到了 `#5`，但本地只见过 `#3`，就知道自己漏了 `#4`，于是立刻触发补同步。其三，把序列号塞进心跳：更进一步，可以在 heartbeat 里带上用户当前最新序列号，服务端发 ping 时顺便带上最新 seq，客户端发现本地 seq 落后，就立即发起 sync。这样基本不需要额外放大太多流量，因为心跳本来就要发。真实系统里，通常是三者组合：心跳负责发现“连接死了”，序列号负责发现“消息漏了”，周期轮询负责最终兜底。

#### 六、消息顺序乱了怎么办

分布式系统里，绝对顺序很贵。如果强行保证所有消息严格按发送顺序交付，就需要等待迟到消息、做重排序缓冲区，复杂度和延迟都会明显上升。而聊天应用通常更关心“尽快显示”，而不是“绝对不乱序”。因此一个更务实的办法是：所有 Chat Server 用 NTP 同步时间；消息进入服务端时，由服务器打上接收时间戳；客户端按服务端时间戳展示。这样用户偶尔会看到某条消息“插队”到上面，但整体顺序在所有客户端上是一致的，而且实时性更好。

#### 七、如何实现 last seen

一个不合适的方案是每次心跳都把用户的 `lastSeen` 写数据库，这会制造海量无意义写入。对于数亿在线用户来说，光心跳更新就会把存储写爆。更合理的办法是利用现有连接状态：用户在线时，系统本来就知道他在线；用户断开连接时，再把“最近断线时间”写入 `LastSeen` 表。查询某个用户 last seen 时，一路去查 `LastSeen` 表，同时通过在线链路问目标用户当前是否在线；如果在线，直接返回 `ONLINE`；否则返回最近断线时间。这样 durable storage 里只需要每个用户一条记录，写入频率也只发生在断线事件，而不是每次心跳。

### 整体链路

#### 发送消息路径

1. 客户端通过 WebSocket 发 `sendMessage`
2. `Chat Server` 查询 `ChatParticipant`
3. 写入 `Message`
4. 为每个目标客户端写入 `Inbox`
5. 向对应用户 channel 发布实时事件
6. 在线客户端收到 `newMessage`
7. 客户端回 `ack`
8. 服务端删除已确认的 `Inbox` 记录

#### 用户重连路径

1. 客户端重新连到某台 `Chat Server`
2. 服务器为该用户订阅对应 user-level channel
3. 查该客户端的 `Inbox`
4. 回查 `Message` 并补发未确认消息
5. 等待客户端 `ack`

#### 媒体消息路径

1. 客户端请求 `getAttachmentTarget`
2. 服务端返回预签名上传 URL
3. 客户端直传 blob storage
4. 客户端把附件引用作为普通消息发送
5. 接收方收到消息后按受控 URL 下载附件

### 总结

WhatsApp 即时通讯系统的核心思路，是把系统拆成两层：实时层 WebSocket + Pub/Sub，负责把在线消息尽快送达；可靠层 Message + Inbox，负责掉线恢复和最终投递。然后再围绕这两层逐步补齐关键问题：用 `Inbox` 解决离线可达、用 blob storage + 预签名 URL 解决媒体消息、用 Pub/Sub 解决多台 Chat Server 之间的消息路由、用多客户端 Inbox 解决多设备同步、用心跳、序列号和轮询解决断线与漏消息、用断线时间表而不是心跳写库解决 last seen。整体来看，这是一套**面向长连接的实时投递系统，外加一个面向可靠性的离线补偿系统**。
