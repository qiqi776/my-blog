## 网络爬虫系统设计

网络爬虫系统的核心任务，是从一组种子 URL 出发，持续抓取网页内容，抽取其中的文本与链接，并将新发现的链接继续加入待抓取集合，从而不断扩展抓取范围。它可以服务于多种业务场景，例如搜索引擎建立索引、研究型数据采集，或为大语言模型准备训练数据。

在本文中，我们假设目标是从互联网上抓取网页文本，并将文本存储下来，供后续训练 LLM 使用。因此，讨论重点将放在“抓取网页”和“提取文本”两个环节。

### 问题定义与需求

- 问题定义：设计一个网页爬虫系统，从互联网中抓取网页并提取文本数据，最终将这些文本保存下来，用于训练大语言模型
- 功能需求：从一组种子 URL 出发，持续向外抓取网页，从网页中提取文本数据并完成存储
- 规模假设：抓取目标规模约为 100 亿个网页，平均每个页面按 2MB 的传输体积估算，系统需要在 5 天内完成抓取
- 非功能需求：具备容错能力，发生失败后能够恢复处理进度；具备礼貌性，遵守 `robots.txt`，避免对目标站点造成过大压力；具备足够的扩展性，能够支撑 100 亿页面规模；具备足够高的效率，确保在 5 天内完成抓取
- 核心实体：文本数据（Text Data）、URL 元数据（URL Metadata）、域名元数据（Domain Metadata）

### 系统接口与数据流

#### 系统接口

- 输入：一组种子 URL
- 输出：从网页中提取出的文本数据

#### 数据流

1. 从待抓取队列中取出一个 URL
2. 对该 URL 所属域名执行 DNS 解析
3. 向目标网站请求页面并获取 HTML
4. 从 HTML 中提取正文文本
5. 从 HTML 中抽取页面链接
6. 将文本存入存储系统
7. 将新链接加入待抓取队列
8. 重复上述过程，直到抓取任务结束

从接口与数据流可以看出，这个系统虽然功能目标明确，但实际处理链路是多阶段的。也正因为如此，后续的高层设计和深入讨论，核心都围绕如何把这条链路拆分得更稳定、更礼貌、更高效。

### 基础版设计

基础版架构可以先保持简单。`Frontier Queue` 是待抓取 URL 队列，系统以种子 URL 为起点，后续不断将新发现的链接加入其中。`Crawler` 是执行抓取任务的核心处理单元，负责取 URL、做 DNS 解析、请求网页、提取文本和链接。`DNS` 负责把域名解析为可访问的 IP 地址。`External Websites` 是爬虫访问的外部网页来源。`Blob Storage` 用于存储抓取结果，尤其是大体积文本或 HTML 数据，适合使用 S3 一类的对象存储。虽然目前只是一个简单版本，但系统已经能够从种子链接出发抓取网页、提取文本并持续发现新的链接。

### 核心拓展

接下来需要考虑系统能否在真实世界中稳定且高效地工作。后续讨论将围绕先前提出的非功能需求逐项展开，依次考察容错性、礼貌性，以及在大规模场景下的效率与可扩展性。

#### 一、如何保证系统具备容错能力

原始方案中的 crawler 承担了过多职责。它既要访问 DNS，又要请求网页、提取文本、抽取链接，并将结果重新送回系统。随着后续对礼貌性和效率的要求不断加入，这个组件还会承担更多逻辑。虽然从功能上说，一个服务可以把这些任务全部做完，但从容错角度看，这种设计并不理想。只要某个环节中途失败，当前处理过程中的进度就可能全部丢失。

在这些步骤中，最容易失败的是网页抓取本身。互联网环境并不稳定，网站可能下线，连接可能超时，请求可能过慢，页面体积也可能超出预期。因此，更合理的做法是将单体化的 crawler 拆分成更小的流水线阶段。这样一来，系统只需重试失败的那一段，而不必回退整个流程。

按照这一思路，原始 crawler 可以被拆成两个阶段。第一阶段是 URL Fetcher，它负责根据 URL 请求目标页面，并将抓取到的原始 HTML 写入对象存储。第二阶段是 Text & URL Extraction，它负责从已经保存下来的 HTML 中提取正文文本，并抽取页面中的链接，再将新发现的链接放回 frontier queue。文本提取和链接提取也可以继续拆开，但在这一层设计里，这两项工作都比较轻量，而且可以并行完成，因此保留在同一个阶段即可。

一旦系统转为多阶段流水线，就必须补充一层状态管理。这里需要引入 Metadata DB，用来记录 URL 的处理状态，以及相关数据在 blob storage 中的位置。数据库中至少要能够记录某个 URL 的原始 HTML 存放位置，以及对应文本数据的存放位置。这样做有两个直接好处。其一，消息队列中不必存放大块 HTML 内容，因为队列并不适合承载大负载数据；消息只需要保存 URL 对应的记录 ID 即可。其二，系统会因此具备更强的演进能力。例如，若后续文本提取逻辑发生变化，团队希望在正文中加入图片的 alt 文本，那么系统只需要重跑提取阶段，而不必重新访问那些已经抓取过的网页。

如果 URL 抓取失败，系统需要把重试状态从 worker 内存里拿出来。最简单的办法是在 worker 内部启动一个内存计时器，等待几秒后再次尝试，但这种做法的问题很明显：一旦 crawler 在等待期间崩溃，计时信息就会丢失；失败的原因往往也不会在几秒钟后自然消失，因此固定短等待并不可靠。如果采用 Kafka，可以自行构建重试逻辑，例如将抓取失败的 URL 写入单独的失败主题，再由专门的服务读取这些消息，并依据消息中记录的“下次重试时间”实施指数退避。这种方案理论上可行，但实现和维护成本较高，因为消息系统本身并未直接提供现成的失败重试能力。

相比之下，SQS 更适合这里的场景。虽然它并没有一个现成的“指数退避开关”，但它提供了足够直接的基础能力。系统可以利用 visibility timeout 机制，在消费者收到消息后暂时隐藏该消息；若处理失败，则不删除消息，而是依据当前的重试次数动态调整下一次可见时间。实现上，可以通过 ApproximateReceiveCount 获取消息已被消费的次数，再结合 ChangeMessageVisibility 设置新的可见性超时，从而实现指数退避。若某个 URL 连续失败达到预设阈值，例如五次，则可通过 redrive policy 将该消息送入死信队列，视为该站点暂时不可抓取。

如果某个 crawler 自己崩溃，系统只需要重新启动新的 crawler。关键在于失败时任务是否会丢失。只要系统保证某个 URL 在 HTML 成功写入 blob storage 之前不会被确认完成，那么即使当前 crawler 在中途退出，消息也仍然保留在队列中，稍后会被其他 crawler 再次领取。对于 SQS 来说，消息只有在抓取结果已经安全持久化之后才会被删除；如果消费者在此之前异常退出，visibility timeout 到期后，该消息就会重新变得可见。解析阶段同理，只有当文本提取完成且结果已写入存储后，对应任务才能确认结束。

经过这一步，系统会从“单 crawler 负责所有事情”，演进为一个以 SQS 为核心调度机制、以多阶段流水线为基本组织形式、并以 Metadata DB 和 blob storage 共同支撑状态持久化的容错架构。

#### 二、如何保证系统的礼貌性

在解决容错问题之后，下一步重点是礼貌性。所谓礼貌性，并不仅仅意味着“抓得慢一点”，而是指系统在抓取网页时，应当尊重目标网站的资源约束，不对其正常服务造成干扰。这既包括遵守网站公开声明的抓取规则，也包括主动控制请求节奏，避免对单个站点形成压力。

robots.txt 是网站用来向爬虫表达访问规则的约定文件，它通常说明两类信息：哪些路径允许抓取，哪些路径被禁止抓取；以及抓取请求之间应当间隔多久。举例而言，Disallow 用于声明禁止访问的路径，Crawl-delay 用于告知抓取方在两次请求之间应预留的等待时间。尽管 Crawl-delay 并不是所有大型爬虫都严格遵守的正式标准，但在这里，系统目标是尽可能礼貌地工作，因此仍应将其纳入设计考虑。系统首先要做的是为每个域名单独抓取并保存 robots.txt。保存之后，系统在每次消费 URL 时，都要先到 Metadata DB 中查询该域名对应的规则，再决定是否继续抓取。

这里需要逐步处理两个问题。第一个问题是当前 URL 是否允许抓取。这一部分相对直接，只需根据 Disallow 规则判断当前路径是否被禁止访问。如果该 URL 属于禁止范围，那么系统应直接确认并丢弃该消息，然后转向下一条任务。

第二个问题是两次请求之间是否满足该域名要求的最小时间间隔。这个问题不只依赖静态规则，还依赖运行时状态。为了解决抓取间隔问题，系统需要在 Metadata DB 中增加一张 Domain 表，用于记录每个域名最近一次被访问的时间。这样，当 crawler 从队列中取出一个 URL 时，就可以先读出该域名的 crawl-delay 要求，再与上次抓取时间进行比较。如果等待时间尚未满足，则不应当立刻发起请求，而应当利用 ChangeMessageVisibility 将消息重新延后，使它在适当时间后再被消费。这里需要特别注意的是，DelaySeconds 只适用于新消息投递，而对已经处于 in-flight 状态的消息，正确的做法是调整其 visibility timeout。

不过，在多 crawler 并行运行的环境中，仅靠 Domain 表中的时间戳仍然不够。两个不同的 crawler 可能同时取到同一域名下的两个 URL，并且在同一时刻看到相同的旧时间戳，于是双双认为“现在可以抓取”，最终并发打到同一个站点上。为了避免这种并发竞争，系统还需要引入按域名加锁的机制。例如，可以通过 Redis 的 SET NX 配合合适的 TTL，为每个域名加一把短时锁。成功获得该锁的 crawler 才允许继续处理该域名；未能获得锁的 crawler，则应将消息再次延后。这样，抓取间隔约束才能在分布式环境中真正成立。

在落实 robots.txt 之后，还需要考虑速率限制问题。即使目标站点没有明确配置 crawl-delay，系统仍应主动限制对单一域名的访问频率。常见的设计是对单个域名控制在每秒一次请求。为此，可以借助 Redis 之类的中心化存储，按域名维护请求计数，并采用滑动窗口算法判断当前时间窗口内的访问量是否超过阈值。每个 crawler 在发起请求前，都需要先查询这一计数器；若发现该域名的单位时间请求数已经达到上限，就必须等待。

但这一设计还会带来一个新的副作用。如果多个 crawler 都在等待某个域名的限流窗口重置，那么在下一秒开始时，它们很可能同时重试，结果再次形成竞争，只有其中一个请求通过，其余请求继续回退。这种“同步重试”现象会使系统产生大量无谓竞争。为了打破这种同步行为，需要在限流等待逻辑中加入 jitter，也就是在等待时间中引入小幅随机偏移。这样，不同 crawler 的重试时间就会被有意错开，系统整体将变得更加平滑。

经过这一轮扩展之后，礼貌性将基于三层机制之上：其一，基于 robots.txt 的访问许可判断；其二，基于 Domain 表和消息可见性控制的抓取间隔管理；其三，基于中心化存储和随机扰动的域名级速率限制。

#### 三、如何将系统扩展到百亿页面规模，并在五天内完成抓取

扩展性与效率适合放在容错和礼貌性之后讨论。只有在系统的主要处理环节、失败恢复方式以及礼貌性约束都已明确之后，才能判断真正的瓶颈究竟在哪里。若过早讨论扩容，就很容易遗漏后续引入的新瓶颈，例如解析 worker、DNS 或队列延迟等因素。

那么在一百亿页面、五天完成的要求下，系统究竟需要多少机器？网页抓取本质上是一个 I/O 密集型问题，其瓶颈主要受网络带宽、站点响应速度、DNS 查询、礼貌性限制和失败重试影响，而不是 CPU 计算。

数量级粗略估算：若平均每个页面的传输大小按 2MB 计算，而一台高带宽网络优化实例的理论网络能力约为 200Gbps，则单机的理论上限大致为 200 Gbps / 8 / 2MB ≈ 12,500 pages/s。当然，这只是理想值，真实环境中不可能完全利用。由于系统还要受 DNS、目标网站延迟、抓取间隔、速率限制和重试成本影响，假定只能利用约 30% 的带宽。按这个折算，单机大约能够达到 3,750 pages/s 的有效吞吐。既然对单个域名的访问频率被限制在每秒一次，为什么总体吞吐仍然能够达到每秒数千页？关键在于系统不是围绕一个域名并发，而是围绕海量不同域名并发。每个 crawler 都可以同时维护大量面向不同站点的连接，因此单个域名上仍保持克制，而全局维度上的总吞吐却依然很高。

若一台机器能以约 3,750 页每秒的速度工作，那么处理一百亿页面大约需要 10,000,000,000 / 3,750 ≈ 2,666,667 秒，也就是约 30.9 天。若假设这种能力可以近似线性扩展，则八台机器并行时，总时间约为 3.9 天，能够满足五天内完成抓取的要求。当然在真实环境中，最终仍需要通过压测和观测数据来校准这些假设。

紧接着需要考虑 parser worker 的扩缩容。相比于网页抓取，解析阶段的工作模式更加标准化。它只需要从 blob storage 中取回 HTML，提取文本，并将文本重新写回存储。因此，解析阶段不一定需要像抓取阶段那样精确推导单机能力。更实际的做法，是让 parser worker 依据待处理队列的积压情况自动扩缩容。无论是 Lambda、Fargate 还是其他自动伸缩计算资源，只要能让解析阶段始终跟上抓取阶段的速度即可。

DNS 也需要被单独纳入设计。表面上看，DNS 似乎只是抓取请求中的一个透明步骤，因为像 curl 这样的工具都会自动完成域名解析。但在高并发、大规模、多域名的抓取任务中，DNS 往往会成为被低估的瓶颈。对于大量首次访问的域名，系统需要不断向 DNS 体系发起解析请求，每次解析都可能涉及多次网络往返。早期的一些网页爬虫研究甚至发现，在未专门优化之前，DNS 查询曾占据爬虫线程大量运行时间。因此，当系统扩展到数千请求每秒、面对数百万不同域名时，DNS 必须被纳入架构考虑。针对这一问题，通常有两种优化方向。其一，是在 crawler 侧进行 DNS 缓存，使同一域名下的后续 URL 尽量复用已有解析结果，从而减少重复查询。其二，是同时接入多个 DNS provider，并在它们之间进行轮询或分流。这样既可以缓解单一 DNS 服务的速率限制，也能够降低某个解析服务异常时对整个抓取系统的影响。

重复内容需要从 URL 和内容两层处理。最基础的措施是 URL 级去重，也就是在新链接进入队列之前，先到 Metadata DB 中检查该 URL 是否已经存在。如果某个 URL 已经出现在 URL 表中，就无需再次调度。这是防止重复工作最直接的第一道屏障。然而不同 URL 可能返回完全相同的内容，例如带 www 和不带 www 的地址，甚至不同域名也可能托管相同页面。因此，系统还需要进行内容级去重。其思路是在抓取完成后，对页面内容计算哈希值，并将该哈希与历史内容进行比对。如果数据库中已经存在完全相同的内容哈希，则可以跳过后续昂贵的解析步骤。

针对内容去重，第一种方案是将页面内容哈希写入 Metadata DB，并在哈希字段上建立索引。这样，系统在抓取新页面后，只需计算哈希并查询该索引，就能迅速判断该页面内容是否已经出现过。虽然索引规模会不断增大，并在一定程度上影响写入性能，但在现代数据库环境下，这种额外开销通常是可以接受的。第二种常见方案是布隆过滤器。布隆过滤器能够以较低空间开销判断某个元素是否可能已经存在，因此很适合用于大规模去重场景。系统可以将内容哈希加入布隆过滤器，在新页面到来时先检查其哈希是否可能已经出现过。如果布隆过滤器明确给出“不存在”，则说明这是全新内容；若给出“可能存在”，则说明该页面大概率已经抓过。当然这种方案存在误判风险，也就是有可能把实际未抓取的页面误判为已抓取。因此，尽管布隆过滤器是一个很常见的选择，但在当前问题里，直接依赖数据库索引往往反而更适合。

Crawler trap 需要靠深度限制和预算控制规避。某些页面或站点会通过无限链接、自循环链接或极度膨胀的站内路径结构，让爬虫持续停留在局部空间中，消耗大量预算却无法扩展真正的覆盖范围。解决这个问题，可以为抓取过程设置最大深度限制。这里的“深度”是从种子 URL 出发，经过了多少次链接跳转。系统可以在 URL 表中维护一个深度字段，每沿着链接向外扩展一层，就将深度加一。一旦该值超过预设阈值，例如 15 到 20，系统便停止继续沿该分支向外爬取。这样可以有效防止系统陷入某些站点设计出的无限扩展结构。
