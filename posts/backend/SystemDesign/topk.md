## YouTube Top-K 热门视频系统设计

本文讨论的是一个 Top-K 系统，具体场景是 YouTube 视频观看量排行榜。系统需要在任意时刻返回 all-time 最热视频，以及最近 `1` 小时、`1` 天、`1` 月的 Top-K 视频

和普通排行榜设计的不同点在于：输入不是少量写入，而是一个巨大的 view event firehose。真正的难点也不在“如何排序”，而在于：如何定义时间窗口；如何在超高写入下维护计数；如何把查询延迟压到几十毫秒；以及是否需要近似算法来换取效率

### 问题定义与边界

#### 功能需求

客户端能够查询所有时间的 Top-K 视频；客户端能够查询最近 `1` 小时、`1` 天、`1` 月的 Top-K 视频；`K` 有上限，最多约 `1000`

#### 非功能需求

1. 允许至多约 `1` 分钟统计延迟
2. 查询结果默认要求精确，不先引入近似误差
3. 查询延迟目标是 `10s of milliseconds`
4. 系统要能承受极大规模的视频观看事件流

在设计这类系统时，最先要明确的是时间窗口的定义，是滑动窗口还是滚动窗口。为了让系统更容易做预计算，我们选择使用滚动窗口：最近 1 小时指上一个完整的小时，最近 1 天指上一个完整的天，最近 1 月指上一个完整的月

- 本文暂不展开任意起止时间范围查询、任意大 `K`、个性化热门榜、复杂去重与反作弊

### 规模估算

YouTube Shorts 约 `70B views/day`，折算后大约 `700k views/s`。视频规模约 `1` 小时内容 / 秒上传，如果平均每个视频约 `6` 分钟，那么约 `1M videos/day`，十年量级约 `3.6B videos`

### 核心实体、接口与数据模型

#### 核心实体

- `Video`
- `View`
- `TimeWindow`

业务接口很简单，复杂度几乎都在内部数据流上

#### 初始接口

```http
GET /views/top-k?window={WINDOW}&k={K}
```

返回结果可以是：

```json
[
  { "videoId": "v1", "views": 123456 },
  { "videoId": "v2", "views": 120001 }
]
```

#### 输入数据流

假设系统上游已经有一个 `Kafka` 之类的 `ViewEvent` 流，Top-K 系统只需要消费这条流，并把它转成可查询的排行结果

### 核心架构设计

#### 一、先支持所有时间 Top-K

`View Consumer` 从 Kafka 消费 `ViewEvent`；每来一个 view，就把对应 `videoId` 的计数加一；把计数落到一个数据库表；`TopK Service` 查询数据库中 `views` 最大的前 `K` 个视频

如果用关系型数据库表达，可以写成一张 `VideoViews(videoId, views)` 表，对 `views` 建索引。查询时大致就是：

```sql
SELECT videoId, views
FROM VideoViews
ORDER BY views DESC
LIMIT k;
```

做完这步我们有输入事件流，有计数存储，有 Top-K 查询接口

#### 二、再支持时间窗口

如果要支持时间窗口，我们可以不再只保存 `videoId -> total views`，而是按时间粒度记录计数。例如按小时保存 `videoId`、`timestamp(hour bucket)`、`views`。这样查询最近 `1` 小时 / `1` 天 / `1` 月时，就可以扫描对应时间范围内的记录，按 `videoId` 做 `SUM`，再按和排序取 Top-K。这个设计的功能上没问题，但它会立刻暴露两个大瓶颈：每次查询都要扫很多数据；每次事件仍然要写库。这也是后续讨论的出发点

### 深入讨论

#### 一、如何扩展读取：缓存和预计算

既然我们允许约 `1` 分钟延迟，那么最先应该想到的就是不要每次查询都现算

##### 1. 缓存查询结果

最直接的优化是给 `TopK Service` 前面加缓存，key 为 `top-k:{window}:{truncated_timestamp}`，value 为该窗口的 Top-K 结果。这样大部分请求都能在亚毫秒级缓存里命中。但仅靠缓存仍有问题：缓存过期瞬间会有一波请求直接打回数据库，这些 miss 请求很可能同时突破 SLA

##### 2. 定时预计算并回填缓存

既然结果天然按窗口更新，那么系统完全可以用 cron / scheduler 定时触发，预先把各窗口的 Top-K 结果算出来，直接回填到 Redis / Memcached。这样在线查询几乎只读缓存，不碰底层存储。这一步其实奠定了整个系统的读路径原则：查询层要尽量只服务预计算结果

#### 二、如何扩展写入：分片和批处理

真正麻烦的是写入。按前面的估算流量约 `700k views/s`，如果每一条都触发一次数据库写入，单机关系型数据库很快就会被压垮

##### 1. 按 `videoId` 分片

因为上游 Kafka 天然支持按 `videoId` 分区，所以很自然的做法是 `ViewEvent` topic 按 `videoId` 分区，`View Consumer` 水平扩展，数据库也按相同规则分片。这样同一个视频的计数稳定落到同一 shard，中间不会产生复杂的跨分片写冲突。但仅靠分片还不够，如果想把每个分片的写入压到约 `10k tps`，可能仍然需要几十个数据库实例

##### 2. 批处理聚合

更好的方案是不要为每一次 view 单独写库，先在流处理层做批量聚合，再把聚合结果批量刷库。可以利用 Flink 实现这一模式：从 Kafka 消费事件，按 videoId 聚合，利用其 watermark 机制处理晚到事件，以小时为粒度输出每个视频的增量观看计数，最后将批量结果写入存储。这样做能显著降低写入频率，充分发挥数据库对批量写入的吞吐优势，同时还能顺便解决晚到事件的问题

#### 三、如何优化窗口查询

即使读层已经有缓存，系统仍然需要去把缓存算出来。而 naive 窗口查询本身仍然很重：例如查“最近一个月 Top-K”，需要扫描整个窗口内大量分桶数据，还要对每个视频聚合求和，这在大数据量下会非常慢

##### 1. 更粗粒度聚合

一种改进是维护多个粒度：小时级、天级、月级。查询最近一个月时，就尽量用天级聚合，而不是把 `24 * 30` 个小时桶都重新加一遍。这能减少查询处理量，但系统仍然在“读时做很多聚合”

##### 2. 直接维护每个窗口的总表

直接维护 `VideoViewsLastHour`、`VideoViewsLastDay`、`VideoViewsLastMonth`、`VideoViewsAllTime` 这几张表。每张表都表示当前这个窗口内每个视频的总 views，然后对每张表的 `views` 列建立索引。这样查询时就变成了直接对对应窗口表做 `ORDER BY views DESC LIMIT k`，读路径几乎不再做聚合，而是直接读已经维护好的窗口状态。代价也很明确：写路径更复杂，每批聚合结果可能要写多张表

#### 四、如果是滑动窗口怎么办

我们前面主动选择了滚动窗口，因为它更容易预计算。但如果改变成滑动窗口，例如当前 `10:06` 查最近 1 小时，实际想看的是 `9:06 ~ 10:06`，那系统就要进一步演进

一种思路是 minute-grain 增量维护：每分钟聚合一次每个视频的 views 增量；对 `VideoViewsLastHour` 来说，加上当前这一分钟的增量，减去正好 `60` 分钟前那一分钟的增量。也就是说，窗口值不再通过扫描重算，而是 `current = current + increment - decrement`

但这种做法复杂度和存储都会明显上升：必须保留细粒度历史桶用于 decrement，写路径变成读+写+更新。因此我们通常采用最近 1 小时支持滑动窗口，最近 1 天 / 1 月继续使用滚动窗口

#### 五、如果允许近似

如果产品不要求绝对精确，而只关心趋势榜，那就可以继续演进到近似算法。官网题解重点提到 `Count-Min Sketch`，它适合在超大规模流里近似估计每个 item 的出现次数，同时显著降低内存占用。但 CMS 有一个限制：它天然支持 `add` 和 `estimate`，不直接保留完整 item 列表。因此 Top-K 场景通常需要 `Count-Min Sketch` 再配一个 heap / sorted set 保存候选 Top-K

事件到来时，先 `CMS.add(videoId)`；再 `CMS.estimate(videoId)`；用这个估计值去更新 heap / sorted set后持续裁剪，只保留前 `1000` 候选。这样可以显著减少状态体积，但代价是结果不再绝对精确

#### 六、为什么时序数据库不是最合适的

很多人一看到“按小时 / 按天 / 按月统计”，就会想到时序数据库。但这里的问题不是“查询某个视频的一条时序曲线”，而是要跨所有 videoId 做全局 Top-K。这意味着系统可能面对几十亿的超高基数 videoId。而多数时序数据库更擅长处理某个指标的时间序列和较窄的 point/range 查询，并不天然适合跨数十亿键做全局 top 排名

### 整体链路

#### 写路径

1. 上游把 view 事件写入 Kafka
2. Flink 消费 Kafka
3. 按 `videoId` 聚合，处理晚到事件
4. 以小时或分钟粒度产出批量增量
5. 批量更新各窗口总表

#### 预计算路径

1. 定时任务按窗口读取各 shard 的 Top-K
2. 在聚合层合并 shard 结果
3. 把最终 Top-K 结果写入缓存

#### 查询路径

1. 客户端请求 `GET /views/top-k?window={WINDOW}&k={K}`
2. `TopK Service` 直接命中缓存
3. 返回结果
