## Facebook 帖子搜索系统设计

本文讨论 Facebook 的帖子搜索功能。用户发布帖子后，系统需在短时间内让帖子变为可搜索状态；当用户搜索关键词时，系统需支持按发布时间或点赞数排序返回结果。问题并不在单次查询，而在于索引的维护成本。因为系统不仅要响应搜索请求，还要持续处理海量的发帖事件和点赞事件，而点赞事件的体量通常远大于发帖。这便引出了三个核心问题：如何构建支持快速查询的倒排索引；如何在高写入压力下维护这些索引；如何对热数据与冷数据进行分层，以防存储成本失控

### 问题定义与边界

#### 功能需求

用户能够发帖；用户能够给帖子点赞；用户能够按关键词搜索帖子；搜索结果能够按时间或点赞数排序

#### 非功能需求

低延迟：搜索的中位延迟希望控制在 `500ms` 以内；高写入：新帖子需要在 `1` 分钟内可搜索；高可用：搜索服务需要稳定可用；全量可发现：即使是旧帖子或冷门帖子，也最终应该能被搜到

#### 前提假设

不考虑个性化排序；不考虑隐私过滤和复杂可见性规则；不考虑模糊匹配、同义词扩展和完整搜索 DSL；不依赖 Elasticsearch、Postgres Full-Text 这类现成全文检索系统，重点放在底层原理。这一组边界非常重要，只要把个性化和复杂权限先拿掉，缓存就会容易很多，因为相同查询对不同用户可以直接复用结果

### 规模估算

假设用户规模约 1B（10 亿），每个用户平均每天发 1 条帖子、点 10 个赞、执行 1 次搜索。按一天 100k 秒粗估：发帖写入约 10k posts/s，点赞写入约 100k likes/s，搜索读取约 10k searches/s。这里最重要的不是这些数字，而是系统本质上偏向**写密集**。提起搜索，很容易联想到读很多，但在本文背景下，持续维护索引的成本更值得优先重视。进一步估算存储：假设 Facebook 运行 10 年，日均 1B 条帖子，每条帖子元数据按 1KB 计算，那么原始帖子规模将达到约 3.6PB。这意味着搜索系统不能无节制地把所有数据长期留在热索引里

### 核心实体、接口与数据流

#### 核心实体

`User`、`Post`、`Like`

#### 初始 API

- 发帖：`POST /posts`
- 点赞：`PUT /posts/{postId}/like`
- 搜索：`GET /search?q={query}&sort={recency|likes}&cursor={cursor}`

这里的写路径可以被理解为“业务事件入口”，后面完全可以演化成写入 Kafka 之类的事件流

#### 高层数据流

1. 发帖请求进入 `Post Service`
2. 帖子写入 `Post Store`
3. 发帖事件进入 `Ingestion Service`
4. Ingestion 对帖子做分词，把 `postId` 写入搜索索引
5. 点赞请求进入 `Like Service`
6. 点赞事件推动点赞排序索引更新
7. 搜索请求进入 `Search Service`
8. Search 读取倒排索引并按排序方式返回结果

### 核心架构设计

#### 一、用户能够发帖和点赞

先从最简单的功能开始。用户发帖后，`Post Service` 把帖子写入主存储；用户点赞后，`Like Service` 记录点赞事实，并维护帖子当前的点赞数。在这一层里，系统还没有真正“可搜索”，因为帖子正文只是存在了主存储中，还没有变成适合按关键词查询的结构

`Ingestion Service`的职责是接收发帖事件、对帖子文本做 tokenization、抽取关键词、更新搜索索引。也就是说，写帖子和让帖子可搜索，不一定是同步完成的，只要我们接受“帖子在 `1` 分钟内进入索引”这个 SLA，就可以把索引维护链路做成异步

#### 二、用户能够按关键词搜索帖子

最差的方案，是把所有帖子存在数据库里，然后在查询时执行类似 `SELECT * FROM Posts WHERE content LIKE '%keyword%'` 的全表扫描。这个方案在功能上没错，但在规模上完全不可行，即使做分库分片，本质也只是把全表扫描拆给更多机器，问题并没有被解决

我们使用**倒排索引**，正常存储是 `postId -> content`，搜索索引改成 `keyword -> matching postIds`。这样一来，搜索 `Taylor` 时，系统不必扫描所有帖子，只需要直接命中 `Taylor` 这条索引项，就能拿到相关的帖子 ID 列表。为了降低查询延迟，我们可以把这个索引放在内存型系统里，例如 Redis / MemoryDB。索引按关键词访问；查询延迟足够低；可以水平扩展

#### 三、搜索结果需要按时间或点赞数排序

如果只是按关键词返回一批 `postId` 还不够，系统还需要支持按发布时间和按点赞数两种排序。很容易想到的做法是：先从关键词索引里拿回所有 `postId`，再逐个查这些帖子各自的时间戳或点赞数，最后在请求时排序。但常见词可能命中上千万帖子，索引返回的数据量会非常大，每个结果还要再查详情，请求时排序会把延迟直接打爆

更好的方式，是为同一个关键词维护两套索引：`creation index` 按发布时间排好序，`likes index` 按点赞数排序。这样，搜索服务就不需要在请求时做大规模排序，而是直接读取“已经排好序”的结果。一种很自然的实现是时间排序索引用追加友好的 list，点赞排序索引用支持 score 的 sorted set。当新帖子创建时，它会被写进对应关键词的两套索引；当帖子收到点赞时，只需要更新对应关键词在点赞索引中的分值

### 深入讨论

#### 一、如何处理大量重复搜索请求

本文背景虽然偏写密集，但读流量也不低，尤其是热门事件出现时，同一个词会被反复搜索。本文还有两个前提：不考虑个性化；允许最多约 `1` 分钟的索引滞后。这几乎是在明示我们应该引入缓存。第一层是搜索服务旁边的分布式缓存：key 可以是 `query + sort + cursor`，value 是对应的结果页，TTL 控制在 `1` 分钟以内，这样可以直接复用最近的热门查询结果。第二层可以更进一步，直接上 CDN 边缘缓存，因为没有个性化推荐，相同查询对所有用户都相同，所以 `/search?q=taylor&sort=likes` 这类请求天然适合走 HTTP cache，对命中缓存的用户，请求甚至不必穿过应用层

#### 二、如何支持多关键词和短语搜索

单关键词搜索相对简单，但真实用户经常搜的是短语，比如 `Taylor Swift` 或 `All your base`。第一种改法是在查询时做交集和过滤：取 `Taylor` 与 `Swift` 的结果集，做交集，再回表验证正文里是否真的出现了连续短语 `Taylor Swift`。但当两个词都很常见时，集合会非常大，网络传输、交集计算和正文过滤都会吃掉很多时间

更优的做法是直接把短语片段也索引出来，也就是引入 `bigrams / shingles`。例如句子 `I saw Taylor Swift at the concert`，除了单词索引，还额外生成 `I saw`、`saw Taylor`、`Taylor Swift`、`Swift at` 等二元短语。这样搜索 `Taylor Swift` 时，就可以直接查短语级索引，而不是先查两个单词再做交集。代价也很明显：索引规模会显著膨胀，因为二元短语远比单词稀疏，词项总数会多很多。所以更现实的策略通常是：对高频、常见搜索短语建立 bigram 索引；没命中的时候，再回退到“单词交集 + 过滤”，这样可以在查询效率和索引规模之间取得平衡

#### 三、如何处理海量写入

1. 发帖写入

一条帖子发出来后，系统要先做分词，再把 `postId` 写进它命中的所有关键词索引。如果一条帖子里有 `100` 个词，那可能就意味着 `100+` 次索引写入，发帖高峰期一来，`Ingestion Service` 很容易成为瓶颈。典型做法是把写路径拆成：入口服务只负责接收事件；事件进入 Kafka 这类日志/队列；多个 ingestion worker 并行消费；索引按关键词做分片，分散写压力。这样做有三个好处：峰值流量可以先缓存在队列里；分词和索引写入可以横向扩容；某一批 worker 异常时，事件仍然可以重放

2. 点赞写入

点赞比发帖多得多，如果帖子每多一个赞，我们都去更新所有相关关键词上的点赞排序索引，那么系统会非常痛苦，因为一次 like 事件背后，很可能对应很多关键词项的分值更新。我们可以用批处理进行优化：先收集一段时间窗口内的点赞，对同一个 `postId` 聚合，再一次性把增量写回索引。这对爆款帖子很有效，因为几十秒里可能聚合掉几百上千次点赞更新，但它对长尾帖子帮助有限，很多帖子并不会在短窗口里积攒很多赞，最后还是得频繁写回

3. 两阶段排序架构

更进一步，把“索引里的点赞数”从精确值改成**近似排序值**。例如只在帖子点赞数跨过某些里程碑时才更新索引，比如 `1`、`2`、`4`、`8`、`16` 这样指数增长，或者按 `10`、`100`、`1000` 这样的级别更新。这样一来，帖子从 `0` 到 `1000` 个赞，不再需要 `1000` 次索引写入，而只需要少数几次“跨档位”更新。代价是索引变得不完全精确，但它仍然能提供一个“足够接近”的粗排结果，比如有 `10k` 赞的帖子，一定不会排在只有 `1` 个赞的帖子后面。最后再做一次精排：先从 `likes index` 里取 Top `N * 2`，再向 `Like Service` 查询这些帖子的最新真实点赞数，用真实点赞数重新排序，返回最终 Top `N`

#### 四、如何控制索引存储成本

如果不做约束，倒排索引会无限膨胀。因为帖子总量本身已经是 PB 级；每个帖子又会写入很多关键词；常见词会挂上极长的 posting list；多关键词、短语索引还会进一步放大存储。因此，存储优化至少要做两件事

1. 对热索引做截断。很多高频词其实没必要在热内存里保存“全部历史结果”，比如关键词 `Mark` 或 `happy`，用户更可能关心最近或最热门的那几千条，而不是一千万条历史帖子，因此可以给热索引设置上限，例如每个关键词只保留最近或最热门的 `1k ~ 10k` 条结果，这样能把热存储规模直接压下几个数量级
2. 冷热分层。本文有一个很重要的非功能需求：旧帖子和冷门帖子也应该能被搜到，但允许慢一些。这就给了我们很自然的分层策略：热词、热结果留在内存索引里；低频关键词和长尾历史索引迁到冷存储，例如 Redis / MemoryDB 保存热关键词索引，S3 / R2 这类 blob storage 保存冷关键词索引。查询时，搜索服务先查热层，如果热层没有，再降级去冷层拿数据，多付出一点延迟

### 整体链路

#### 写路径

1. 用户发帖，请求进入 `Post Service`
2. 帖子写入 `Post Store`
3. 发帖事件进入 Kafka
4. `Ingestion Service` 消费事件，做分词和短语抽取
5. 将 `postId` 写入对应关键词的 `creation index` 和 `likes index`
6. 用户点赞，请求进入 `Like Service`
7. 点赞事件进入聚合/批处理链路
8. 系统按批量或按档位更新点赞排序索引

#### 读路径

1. 用户请求 `GET /search`
2. 请求优先命中 CDN 或搜索结果缓存
3. 未命中时，`Search Service` 查询关键词索引
4. 如果是短语查询，优先命中 bigram / shingle 索引，否则退化为交集 + 过滤
5. 如果按点赞排序，先用近似 likes index 粗排
6. 再向 `Like Service` 取真实点赞数，对 Top 候选集精排
7. 返回结果给用户
