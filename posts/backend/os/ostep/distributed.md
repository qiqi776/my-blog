### 分布式系统

分布式系统已经是现代软件世界的默认背景。浏览器访问远程 Web 服务、手机调用云端接口、搜索和社交网站背后数千台机器协同工作，这些都属于分布式系统的范畴

但一旦系统跨越多台机器，一个最基本的问题立刻出现：**组件会故障，而系统最好不要因此一起挂掉**

> **关键问题：如何用会故障的组件，构建一个整体上看起来依然可靠的系统？**

这个问题和前面 RAID 里“用不可靠磁盘构建可靠存储”的思路有点像，只不过现在对象从磁盘扩展到了机器、网络、软件和整套服务

#### 分布式系统为什么难

分布式系统最显著的变化，是程序不再只依赖本地 CPU 和内存，而必须通过网络与远端机器合作完成任务。这会引入几类新的问题：

- **故障**：机器会宕机，磁盘会坏，网络会断，软件会崩
- **性能**：跨网络通信远比本地函数调用和内存访问昂贵
- **安全**：远程方是否可信，通信过程是否被窃听或篡改

这一章最关注的，是其中最核心的一类：**通信和故障处理**

### 通信基础

#### 网络默认是不可靠的

现代网络的一个核心事实是：数据包会丢。导致丢包或损坏的原因很多：

- 传输途中位翻转或包损坏
- 链路、交换机、路由器或主机本身故障
- 接收路径上缓冲区不够，数据包被直接丢弃
- 终端主机被大量请求压垮，来不及处理所有消息

这里应当注意一点：网络不可靠是默认状态，不是例外

#### 最简单的通信层：不可靠消息传递

一种很自然的做法是：底层通信层不主动帮你处理丢包，只负责“尽力发送”。应用如果需要更强语义，就自己在更高层补上。UDP 就是这种思路的典型例子。程序通过 socket API 建立通信端点，然后：

- 客户端用 `sendto()` 发送数据报 `datagram`
- 服务端用 `recvfrom()` 接收数据报
- 服务端再回一个响应消息

这已经足够让你写出最简单的客户端/服务器程序

UDP 的特点很明确：

- 它很轻量
- 它不保证消息一定到达
- 发送方通常也不会被显式告知某个包丢了
- 它可以用校验和发现部分损坏，但不负责“把丢掉的包找回来”

因此，UDP 很适合作为一个**基本但不可靠的通信层**

### 在不可靠网络上实现可靠通信

如果应用不想自己面对丢包，一个自然的问题就是：能不能在不可靠的网络上，再包一层“看起来可靠”的通信协议？

答案是可以，但需要一些机制

#### 第一步：确认 `ack`

最基础的办法是发送方发出消息，接收方收到后回一个确认 `acknowledgment`，这样发送方只要收到了确认，就知道对方大概率已经收到原始消息

#### 第二步：超时与重试

但如果确认没回来呢？这时发送方需要发送消息后启动一个计时器，在超时前如果没收到确认，就认为消息可能丢了，重新发送同一条消息。这就是典型的 **timeout/retry** 机制，发送方必须在本地保留原始消息副本，因为随时可能要重发

#### 还不够：确认本身也会丢

如果接收方已经成功收到了消息并处理完，但返回确认的那一包丢了，发送方就会误以为“原消息没送到”，于是再次重发。这样接收方就可能看到重复消息

如果你传的是文件数据，重复传一个数据块可能只是多收到一份；但如果你传的是“扣款 100 元”这样的操作，重复执行就会变成严重错误

所以，可靠通信不只要解决“能送达”，还要解决“不要被处理两次”

#### 顺序号 `sequence number`

解决重复消息的经典办法是给每条消息加一个唯一标识。最直接的想法是给每条消息生成唯一 ID，但那需要接收方一直记住所有见过的 ID，代价很高

一个更轻量的做法是使用**顺序计数器**：

- 发送方和接收方先约定起始编号，例如从 `1` 开始
- 每发一条消息，发送方把当前序号带上
- 接收方维护自己“下一条期望看到的序号”

如果接收方收到的序号正好是当前期望值：

- 它确认消息
- 把消息交给应用
- 然后把自己的计数器加一

如果接收方收到的是一个已经见过的旧序号：

- 它仍然可以回确认
- 但不会再次把消息交给应用

这样，即使确认包丢了、发送方重发了旧消息，接收方也能识别出它只是重复传输

#### TCP 是更完整的可靠层

实际系统里，最常见的可靠通信层就是 TCP。它当然比上面这个简化模型复杂得多，还包括：

- 流量控制
- 拥塞控制
- 多个未完成请求
- 更复杂的重传与排序机制

但从核心思想看，仍然离不开确认、超时、重试、序号

### 通信抽象

有了基本的消息机制之后，下一个问题是：**程序员到底应该用什么抽象来写分布式程序？**

#### 一个曾经很诱人的想法：分布式共享内存 `DSM`

有一类系统试图把分布式系统伪装成共享内存系统，也就是 **Distributed Shared Memory**

它的直觉很诱人：如果不同机器上的进程能共享一个大地址空间，那么写分布式程序时，感觉就像在写多线程程序。这类系统通常借助虚拟内存实现：

- 如果访问的页面就在本机，直接读写
- 如果页面在远程机器上，就触发 page fault
- 再由系统把远程页面取回来，映射到本地继续执行

这个想法的问题也很明显

**故障处理很差**。如果某台机器挂了，那台机器上的部分地址空间就一起消失。分布在整个虚拟地址空间里的复杂数据结构，会突然变成一半存在、一半失踪

**性能语义反直觉**。程序员平时默认“内存访问很便宜”，但 DSM 里某次访问可能只是本地加载，下一次却可能变成远程网络抓取整页，代价差几个数量级。为了让程序性能可控，最终还是得非常清楚哪些数据是远端的，这又打破了 DSM 想提供的透明性

所以 DSM 在研究上很有意思，但在工程上影响有限

### 远程过程调用 `RPC`

比 DSM 更成功的抽象，是 **远程过程调用 `Remote Procedure Call`**，RPC 的目标非常明确：

> **让调用远程机器上的代码，看起来尽量像调用本地函数**

从客户端视角看，它只是调用一个函数；过一会儿，函数返回结果。至于参数怎么打包、消息怎么发送、回复怎么重试、超时怎么办，尽量都交给 RPC 框架处理。一个 RPC 系统通常有两部分：

- **存根生成器 `stub generator`**
- **运行时库 `runtime library`**

#### 存根生成器在做什么

服务端先定义一个接口，例如：

```c
interface {
    int func1(int arg1);
    int func2(int arg1, int arg2);
};
```

存根生成器读取这类接口定义后，会自动生成客户端和服务端的样板代码

客户端存根做的事情大致是：

1. 创建消息缓冲区
2. 把函数 ID 和参数打包进去
3. 通过运行时库把消息发给服务器
4. 等待回复
5. 解包返回值
6. 把结果像普通函数返回值一样交回调用者

这里“把函数参数和返回值装进字节流”的过程，通常叫**封送 `marshaling`** 或**序列化 `serialization`**

与之相反的拆包过程则是**解封送 `unmarshaling`** 或**反序列化 `deserialization`**

服务端存根则负责反向过程：

1. 解包请求消息
2. 找到真正要调用的函数
3. 执行该函数
4. 把返回值重新打包
5. 发回客户端

#### RPC 为什么能减少出错

如果没有存根生成器，程序员就得手工去写：

- 参数布局
- 字节序转换
- 请求和回复格式
- 不同类型的编码和解码逻辑

这类代码机械、重复，而且特别容易出错。存根生成器的价值就在于把这类模板化工作自动化

#### RPC 的复杂参数问题

RPC 最麻烦的一类参数，是指针和复杂数据结构

比如本地函数调用里，一个指针很好理解：它就是当前进程地址空间中的一个地址。但在远程调用里，直接把这个地址值发给另一台机器毫无意义，因为对方机器上根本不存在同样的虚拟地址空间

因此，RPC 系统必须知道：

- 指针指向的是一段多大的数据
- 这段数据应该如何被序列化
- 对方收到后应如何还原

这通常要求接口定义中使用框架已知的类型，或者为复杂结构补充更多元信息

#### 服务端的并发

一个最简单的 RPC 服务端，可以写成死循环：

1. 收一个请求
2. 执行
3. 回应
4. 再收下一个

但这样效率通常很差。如果某个调用阻塞在 I/O 上，整个服务端就跟着卡住

因此更常见的做法是使用**线程池 `thread pool`**：

- 主线程不断接收请求
- 收到请求后分发给工作线程
- 多个 RPC 调用并行执行

这样吞吐更好，但也把传统并发问题带了进来，比如共享状态、锁和同步

### RPC 运行时库

RPC 的大部分麻烦，其实不在存根生成器，而在运行时库

#### 首先要解决命名问题

客户端要调用远程服务，先得知道：

- 目标机器是谁
- 目标服务监听哪个端口

最简单的办法，就是使用已经存在的网络命名体系：

- 主机名
- IP 地址
- 端口号

这本质上属于分布式系统里更广泛的命名问题：如何把一个逻辑服务名，解析到具体的通信端点

#### RPC 应该建立在 UDP 还是 TCP 上

从直觉上讲既然 RPC 想要可靠性，那当然应该建在 TCP 之上

但从性能角度看，事情没那么简单。RPC 本身已经是一个请求/响应协议，如果底下又套了一层“通用可靠传输”，就可能做了更多比这个场景实际需要的工作

因此，很多 RPC 系统选择：

- 底层使用 UDP 这样的不可靠传输
- 在 RPC 层自己实现超时、重试、确认和去重

这样做更麻烦，但可能更高效，也更贴合 RPC 的交互模式

#### 超时值怎么设

超时值设置得太小，会导致本来只是慢一点的请求被误判为丢失，系统不断重复发送，浪费网络和 CPU。超时值设置得太大，则真正丢包时，客户端又会傻等太久，响应时间变差。超时并不是一个固定常数就能完事的问题。在高负载场景里，系统常常还会用**指数退避 `exponential back-off`**：

- 第一次超时后，下一次等待更久
- 如果继续超时，就继续把等待窗口拉大

这样可以避免大家在服务器已经过载时一起疯狂重发

#### 长时间运行的 RPC

还有一类棘手情况：远程调用并没有失败，它只是执行时间很长

如果客户端只靠“长时间没回包”来判断失败，就会把这种正常但耗时的请求误认为丢失，然后重发

解决办法通常是：

- 服务器先回一个显式确认，表示“请求收到了”
- 之后客户端定期查询任务是否还在执行
- 只要服务器持续说“还在处理”，客户端就继续等待

这样就能把“慢”和“死”区分开

#### 大参数与分片

如果一个 RPC 的参数大到塞不进单个网络包，系统还得处理：

- **分片 `fragmentation`**：把大消息切成多个小包发送
- **重组 `reassembly`**：接收端把多个小包重新拼回完整消息

有些网络层会帮你做一部分；如果不会，RPC 运行时就得自己承担

#### 字节序问题

不同机器可能使用不同的字节序：

- **大端序 `big endian`**
- **小端序 `little endian`**

如果双方机器字节序不同，多字节整数在网络上传过去之后，不能直接拿来解释。RPC 系统一般会规定一种统一的外部表示格式，例如 XDR，让双方都按同一种格式打包和解包

这类转换不复杂，但会带来一些额外开销

#### 异步 RPC

默认 RPC 往往是同步的，但有时客户端其实还有别的工作能做。于是一些 RPC 系统也支持**异步 RPC** 提高客户端侧的并发度和资源利用率：

- 请求发出去后立刻返回
- 客户端继续干别的事
- 等真正需要结果时，再显式等待对应 RPC 完成

### Sun 的网络文件系统 `NFS`

分布式系统最早成功落地的一个重要方向，就是**分布式文件系统**。它的基本结构很直接：

- 服务器把文件和目录存放在自己的磁盘上
- 客户端通过网络发协议请求来访问这些数据

这样做的好处有三个：

- **共享**：多个客户端可以看到同一份文件系统视图
- **集中管理**：备份、配额、权限等更容易统一管理
- **安全与运维**：存储集中放在少数服务器上，更容易控制

这也引出了这一章的问题：

> **如何构建一个分布式文件系统，并且在客户端、服务器和网络都会出问题的前提下，仍然让它可用？**

#### 基本结构

分布式文件系统通常有两个最关键的软件部件：

- **客户端文件系统 `client-side file system`**
- **文件服务器 `file server`**

客户端应用程序并不直接和网络消息打交道，它只是像往常一样调用标准文件系统 API，由客户端文件系统负责把这些系统调用翻译成协议请求。例如，应用调用 `read()` 后，客户端文件系统可以：

1. 向服务器发送读取请求
2. 服务器从磁盘或自己的缓存里取出数据
3. 服务器把数据回给客户端
4. 客户端再把数据交给用户缓冲区

如果客户端已经把数据缓存到本地内存里，那么后续读取甚至可以完全不经过网络

#### NFS 的设计目标

Sun 的 NFS 之所以重要，是因为它采取了一种非常明确的设计取向：

> **让服务器崩溃后的恢复尽量简单、尽量快。**

这个目标在“多客户端 + 单服务器”的环境里非常合理。因为一台服务器不工作，往往会拖垮所有挂载它的客户端

NFSv2 为此做出的核心选择是：**无状态 `stateless`**

#### 为什么无状态这么关键

假设服务器是有状态的，那么客户端执行：

```c
int fd = open("foo", O_RDONLY);
read(fd, buffer, MAX);
read(fd, buffer, MAX);
close(fd);
```

服务器可能需要记住：

- 这个 `fd` 对应哪个文件
- 当前文件偏移在哪里
- 这个客户端打开了哪些文件

这样做的问题在于：这些状态通常只存在服务器内存里。一旦服务器崩溃，这些状态就全丢了。等服务器重启后，客户端再拿旧的 `fd` 来继续 `read()`，服务器已经不知道它代表什么

如果还考虑客户端自己崩溃，事情更麻烦：服务器可能一直保留着“某客户端打开了文件”的状态，却永远等不到那个客户端再来 `close()`

NFSv2 干脆避开这类问题：服务器不记客户端状态。每个请求都必须自带完成该请求所需的全部信息

#### 文件句柄 `file handle`

无状态协议的核心工具，就是**文件句柄**

可以把文件句柄理解为：一个能唯一标识某个文件或目录的令牌。它通常包含 3 部分信息：

- **卷标识符**：这个对象属于哪个文件系统
- **inode 号**：这个对象在该文件系统中的编号
- **世代号 `generation number`**：避免 inode 复用后老句柄误指向新文件

有了文件句柄，客户端后续每次读写时，都不用说“我是上次那个 fd=3 的客户端”，而是直接说：

- 我想访问这个文件句柄对应的对象
- 我想从哪个偏移开始读/写
- 我想读/写多少数据

#### NFSv2 里的典型操作

NFSv2 里比较关键的几个请求包括：

- `GETATTR`：取文件属性
- `LOOKUP`：在目录里按名字查找文件，返回文件句柄
- `READ`：根据文件句柄、偏移和长度读数据
- `WRITE`：根据文件句柄、偏移和长度写数据
- `CREATE` / `REMOVE`
- `MKDIR` / `RMDIR`
- `READDIR`

这里要特别注意：像 `READ` 和 `WRITE` 这样的请求本身就带着偏移量，因此服务器不需要替客户端维护当前文件指针

#### 一个读取文件的过程

假设应用程序调用：

```c
fd = open("/foo", ...);
read(fd, buffer, MAX);
read(fd, buffer, MAX);
close(fd);
```

在 NFS 里大致会发生这些事：

1. 客户端 `open("/foo")`
2. 客户端文件系统向服务器发 `LOOKUP(rootfh, "foo")`
3. 服务器返回 `foo` 的文件句柄和属性
4. 客户端在本地维护一个打开文件表，把 `fd` 映射到这个文件句柄，并记录当前偏移为 `0`
5. 第一次 `read()` 时，客户端发 `READ(fh, offset=0, count=MAX)`
6. 服务器返回数据
7. 客户端把本地偏移改成 `MAX`
8. 第二次 `read()` 时，再发 `READ(fh, offset=MAX, count=MAX)`
9. `close()` 时，只需要清理客户端本地状态，通常不需要告诉服务器

这里最重要的点是：

- 打开文件表和文件偏移都放在客户端
- 服务器只处理独立请求，不记住会话状态

这正是 NFS 能快速从服务器崩溃中恢复的前提

#### 服务器故障时怎么办

客户端给服务器发请求后，如果长时间收不到回复，可能有很多原因：

- 请求包在网络里丢了
- 回复包丢了
- 服务器短暂崩溃后重启了
- 网络分区导致客户端暂时联系不上服务器

NFSv2 的处理方式非常统一：**重试请求**

客户端发送请求后会启动计时器：

- 如果超时前收到回复，就正常结束
- 如果没收到，就重发同一个请求

之所以能这样做，是因为 NFS 大多数操作都设计成了**幂等的 `idempotent`**

#### 幂等性为什么重要

如果一个操作执行多次，效果和执行一次相同，那么它就是幂等的

NFS 中很多关键操作都具备这个性质：

- `LOOKUP` 是只读操作，天然幂等
- `READ` 也是只读操作，天然幂等
- `WRITE` 虽然会修改文件，但请求里带着**明确的文件句柄、偏移和数据内容**，因此把同一份数据写到同一偏移多次，结果和写一次相同

这意味着：

- 如果请求丢了，客户端重试，最终只是再执行一次相同操作
- 如果服务器实际上已经执行成功，但回复丢了，客户端重试，服务器再执行一次，结果通常也不会变坏

这一点非常漂亮，因为它让客户端不必精确区分“到底是网络丢了、服务器崩了，还是回复丢了”，统一重试就行

当然，像 `mkdir()` 这种操作就没那么天然幂等：

- 第一次 `MKDIR` 可能已经成功创建目录
- 但成功回复丢了
- 客户端重试时，服务器会发现目录已经存在，于是返回错误

所以 NFS 的哲学不是“所有情况都绝对完美”，而是“让大多数常见情况都能用统一而简单的方式恢复”

### 客户端缓存

如果每次 `read()` 和 `write()` 都走网络，分布式文件系统的性能会非常差。因此，NFS 客户端会缓存：

- 文件数据
- 元数据

这样第一次访问可能慢，但后续访问就可以直接从客户端内存里命中

客户端缓存还有一个很重要的用途：**写缓冲 `write buffering`**。应用调用 `write()` 时，客户端可以先把数据放进本地缓存，让系统调用先快速返回，再稍后异步地把数据发给服务器

这能显著改善应用感知到的写延迟，但也立刻引出了一个经典问题：

> **如果多个客户端都在缓存同一个文件，谁看到的是最新版本？**

#### 缓存一致性问题

缓存一致性在 NFS 里主要体现为两个子问题

第一是**更新可见性 `update visibility`**

假设客户端 `C2` 修改了文件 `F`，但暂时只把新内容缓存在自己内存里，还没写回服务器。这时另一个客户端 `C3` 去读 `F`，它看到的还是旧版本。也就是说，一个客户端的更新什么时候能被其他客户端看见，并不再是立即显然的事

第二是**陈旧缓存 `stale cache`**

假设 `C2` 最终已经把新版本写回服务器了，但 `C1` 本地还留着旧版本缓存。如果 `C1` 继续直接使用自己的缓存，它读到的仍然是过期数据

#### NFS 如何处理缓存一致性

NFSv2 用两套机制来缓和这个问题

第一套是**close-to-open 语义**，也常被描述为 **flush-on-close**

做法是：

- 客户端写文件时可以先缓存在本地
- 但当应用 `close()` 这个文件时，客户端要把脏数据刷新到服务器

这样，另一个客户端如果随后再 `open()` 这个文件，就更有机会看到最新内容

第二套是**打开时验证缓存**

客户端每次打开文件时，会先发一个 `GETATTR` 去取服务器上的属性，尤其是最后修改时间。如果服务器上的修改时间比本地缓存对应的时间更新，那么客户端就把自己的缓存作废，后续读取重新走服务器

因此，NFS 的缓存策略可以概括成：

- **写入时：close 时尽量刷回服务器**
- **读取时：open 时尽量验证本地缓存是否还新鲜**

#### 属性缓存

如果每次访问都要发 `GETATTR`，服务器会被大量属性查询轰炸。于是 NFS 又加了一层**属性缓存 `attribute cache`**：

- 文件属性先缓存在客户端
- 一段短时间内直接相信这份缓存
- 超时后再去服务器验证

这提高了性能，但也让语义变得稍微模糊：在属性缓存超时之前，客户端有可能继续使用旧内容

这也是 NFS 常被吐槽的一点：它的一致性语义不是精确而强的，而是偏向工程折中。有时候你会看到最新版本，有时候你可能暂时看到旧版本

### 服务器端写缓冲为什么危险

客户端缓存已经很棘手了，服务器端缓存同样有坑，尤其是**写缓冲**

NFS 服务器通常也有大量内存，因此：

- 读请求的结果可以缓存在服务器内存中
- 写请求理论上也可以先放在服务器内存里，稍后再落盘

但这里有个关键约束：

> **NFS 服务器在对客户端报告 WRITE 成功之前，必须保证数据已经进入稳定存储。**

原因是客户端的故障恢复逻辑建立在“成功回复意味着这次写已经真正完成”这个前提上

看一个例子。客户端顺序写 3 个块：

```c
write(fd, a_buffer, size);
write(fd, b_buffer, size);
write(fd, c_buffer, size);
```

理想结果当然是文件 3 个块分别变成 `a`、`b`、`c`

但如果服务器这么做：

1. 第一块写盘并回复成功
2. 第二块只缓存在服务器内存里，也回复成功
3. 服务器在第二块真正落盘前崩溃
4. 服务器重启后又成功处理第三块

那客户端会以为三次写都成功了，但磁盘上的文件却可能变成：

- 第一块是新的 `a`
- 第二块还是旧内容
- 第三块是新的 `c`

这就产生了“文件中间夹着旧块”的错误状态

为了避免这种问题，NFS 服务器必须在回复 WRITE 成功之前，把对应写入真正提交到稳定存储。代价也很明显：**写性能会被同步落盘拖慢**

这也是后来一些专门做 NFS 服务器的系统会重点优化的地方，比如：

- 先写入有电池保护的 NVRAM，再快速回复成功
- 使用更适合高速写入的底层文件系统

### Andrew 文件系统 `AFS`

如果说 NFS 的核心目标是让服务器崩溃恢复简单，那么 AFS 的核心目标就更直接：**扩展性 `scalability`**

AFS 的设计者关心的是：一个服务器到底能支撑多少客户端。如果协议让客户端频繁地去问服务器“我这份缓存还有效吗？”，服务器 CPU 和网络很快就会成为瓶颈。因此，AFS 从一开始就把“减少服务器交互”放在非常核心的位置

与此同时，AFS 还特别强调一件事：**缓存一致性的用户语义要尽量清楚。** 相比 NFS 那种依赖属性缓存超时的工程折中，AFS 希望做到“用户更容易理解系统到底什么时候能看到新版本”

#### AFSv1：全文件缓存

AFS 的第一个重要设计原则，是**全文件缓存 `whole-file caching`**

它和 NFS 很不一样：

- NFS 主要缓存块，通常放在客户端内存中
- AFS 在客户端本地磁盘上缓存整个文件

因此，AFSv1 的基本流程是：

1. 应用 `open()` 一个文件
2. 客户端向服务器发送 `Fetch`
3. 服务器把整个文件发给客户端
4. 客户端把它写入自己的本地磁盘缓存
5. 后续 `read()` / `write()` 都只针对本地副本进行
6. `close()` 时，如果文件被修改过，再用 `Store` 把整个文件写回服务器

这意味着一旦文件已经被取到本地，后续读写就和本地文件系统几乎一样快。因为：

- 数据已经在客户端本地磁盘上
- 一旦某些块被访问，它们还会进一步进入客户端内存缓存

所以 AFS 实际上用了两级缓存：

- **本地磁盘上的整文件副本**
- **本地内存中的热点块**

#### AFSv1 的协议大意

AFSv1 中几个关键请求包括：

- `Fetch`：获取整个文件内容
- `Store`：把整个文件写回服务器
- `TestAuth`：测试本地缓存副本是否仍然有效
- `GetFileStat` / `SetFileStat`
- `ListDir`

其中 `TestAuth` 很重要。因为客户端第二次访问一个已经缓存过的文件时，并不会直接盲信本地副本，而是先问服务器：“这个文件自从我上次缓存以后，有没有改过？” 如果答案是否定的，它就继续使用本地副本

#### AFSv1 的两个主要问题

AFS 设计者后来认真测量了系统行为，发现 AFSv1 没有达到他们想要的扩展性。最关键的两个瓶颈都出在协议上

第一，**路径查找太贵**

AFSv1 的 `Fetch` 和 `Store` 把完整路径名直接发给服务器，例如：

```text
/home/remzi/notes.txt
```

服务器每次都得自己从根目录一路走到目标文件：

- 在 `/` 里找 `home`
- 在 `home` 里找 `remzi`
- 在 `remzi` 里找 `notes.txt`

客户端一多，服务器就把大量 CPU 时间浪费在反复走目录树上

第二，**`TestAuth` 太多**

这和 NFS 里服务器被 `GETATTR` 轰炸很像。客户端为了确认缓存有效性，不断向服务器发送 `TestAuth`。而在大多数情况下，文件根本没改过，这些请求只是白白消耗了服务器资源

也就是说，AFSv1 的问题可以概括成两句：

- **请求太频繁**
- **每次请求又太贵**

#### AFSv2 的两大改进

AFSv2 为了解决上面两个问题，引入了两个核心概念：

- **回调 `callback`**
- **文件标识符 `FID`**

这两点几乎定义了 AFS 和 NFS 的最大差异

#### 回调：从轮询改成“有变更我通知你”

回调的含义可以理解成服务器对客户端做出一个承诺：

> **只要你缓存的文件没有被别人改，我就默认你这份副本有效；如果它真的变了，我会主动通知你。**

这样一来，客户端就不需要再不断发 `TestAuth` 去轮询服务器。它只要：

- 缓存文件
- 记住自己对这个文件持有一个有效回调
- 继续安心用本地副本

直到服务器明确把这个回调撤销

这和“轮询 vs 中断”的思路几乎一样：

- AFSv1 更像不断轮询
- AFSv2 更像服务器在变化发生时主动中断通知

#### `FID`：别再每次传完整路径名

AFSv2 的另一个关键变化，是用 `FID` 替代路径名来标识文件

`FID` 和 NFS 里的 file handle 很像，通常由以下部分组成：

- **卷标识符**
- **文件标识符**
- **全局唯一标识或世代信息**

这样客户端第一次沿路径查找文件时，仍然需要逐级解析目录；但一旦拿到目录和文件的 `FID`，后续访问就不必每次都让服务器从根开始重新走整条路径

更重要的是，客户端会把沿路径解析得到的目录内容也缓存起来。因此：

- 第一次访问 `/home/remzi/notes.txt` 可能需要多次交互
- 之后再访问同一路径时，很多步骤都可以完全本地完成

#### AFSv2 下读取文件是什么样

假设客户端第一次访问：

```text
/home/remzi/notes.txt
```

大致过程是：

1. 先拿到 `home` 目录内容并缓存在本地
2. 为 `home` 建立回调
3. 再拿到 `remzi` 目录内容并缓存在本地
4. 为 `remzi` 建立回调
5. 最后获取 `notes.txt` 的完整内容和 `FID`
6. 为 `notes.txt` 建立回调
7. 把 `notes.txt` 缓存在本地磁盘
8. 之后 `open()` / `read()` / `close()` 大多都只作用于本地副本

所以 AFSv2 的典型目标是：

- **第一次访问可能贵**
- **后续访问尽量完全本地化**

#### AFS 的缓存一致性更容易描述

AFS 的一致性模型之所以比 NFS 更好理解，关键就在于它的缓存单位和失效机制都更明确

在不同机器之间，AFS 的规则可以概括成：

- 客户端打开文件后，在本地修改自己的整文件副本
- 当客户端 `close()` 这个文件时，新版本才真正写回服务器
- 服务器一旦接受这个新版本，就会撤销其他客户端持有的回调
- 其他客户端下次再 `open()` 该文件时，就必须重新获取最新版

这意味着跨机器时，AFS 提供的是一种很经典的 **session semantics** 风格：

- 一个客户端对文件的修改，在它关闭文件之前，对其他机器通常不可见
- 一旦关闭并成功写回，其他机器后续再打开时，就能看到新版本

#### 同机和跨机语义不完全一样

AFS 在同一台机器上的行为，会稍微更像普通 UNIX：

- 同机上的其他进程通常可以更快看到本地更新

而跨机器时，更新可见性则主要以 `close()` 为界限。这种区分其实很符合用户直觉：本机行为尽量像传统本地文件系统；只有跨机器时，才显现出真正的分布式语义

#### 最后关闭者胜出

AFS 还有一个值得单独记住的语义：**last closer wins**

如果两个不同客户端同时打开并修改同一个文件，那么谁最后 `close()` 并成功把自己的整文件版本写回服务器，谁就覆盖前者，成为最终保留下来的版本

这和 NFS 的“按块逐步刷回”有很大不同。NFS 可能把两个客户端的块级修改混在一起，生成一个“拼接怪物”文件；AFS 至少保证最终服务器上保留的是某一个客户端提交的完整文件版本，而不是两份版本的块级混合

当然，这不等于并发编辑问题被解决了。它只是说明：

- AFS 不会产生那种块级拼接的破碎文件
- 但如果应用真的关心并发修改冲突，仍然需要显式锁或更高层的并发控制机制

### 崩溃恢复

AFS 因为引入了服务器状态，也就是回调，所以崩溃恢复自然比 NFS 更复杂

#### 客户端重启的问题

如果客户端短暂宕机或重启，在它离线这段时间里，服务器可能已经尝试向它发送若干回调撤销消息。客户端因为不在线，当然收不到这些消息

因此，客户端重启后，不能再盲信自己本地磁盘里的缓存副本。更安全的做法是：

- 把本地缓存标记为“可疑”
- 下次真正访问某个文件时，先和服务器确认这份缓存是否还有效

只有确认没过期，才能继续使用

#### 服务器重启的问题

服务器重启更麻烦，因为回调状态本来就放在服务器内存中。服务器一旦崩溃，这些“哪个客户端缓存了哪个文件”的信息就全没了

这意味着服务器恢复后：

- 它已经不知道哪些客户端手上还握着哪些回调
- 客户端也不能再默认自己的缓存仍然可信

因此服务器重启后，系统必须想办法让客户端意识到：

- 服务器已经失忆了
- 你们之前拿到的那些回调现在都不算数

之后客户端必须重新验证自己的缓存

这类恢复可以通过多种机制实现，例如：

- 服务器恢复后主动通知客户端
- 客户端通过心跳或周期检查发现服务器重启

无论具体机制怎样，核心结论都一样：**AFS 用更强的一致性与更低的服务器负载，换来了更复杂的恢复逻辑**

### AFS 的性能与扩展性取舍

AFSv2 的重新设计确实改善了扩展性。核心原因是：

- 客户端和服务器之间的交互次数更少了
- 客户端命中缓存时，很多访问完全本地化
- 服务器不再被海量的 `TestAuth` 轮询请求拖垮

因此单个服务器能支撑的客户端数量明显提升

但 AFS 的性能并不是在所有工作负载下都更好，它建立在一组比较明确的假设上：

- 文件通常不会被多个客户端高频共享写
- 文件经常被完整顺序访问
- 重复访问同一文件很常见

在这些场景下，AFS 很强：

- 首次获取文件后，后续读通常接近本地性能
- 重新读取大文件时，本地磁盘缓存比每次都走网络更有优势

但它也有明显弱点

#### AFS 适合什么，不适合什么

AFS 不太擅长的典型情况包括：

- 只读取大文件中的一小段
- 只修改一个很小的局部，却必须把整个文件拉下来再整文件写回
- 对大文件做频繁追加或随机小更新

因为 AFS 的单位是“整文件”，所以只要打开和修改，就可能牵扯整文件的提取与回写。相比之下，NFS 这种基于块的协议在“只动一小块数据”的工作负载下往往更自然

这也是一个很典型的系统设计教训：**协议优化永远依赖工作负载假设**

### AFS 的其他优点

除了缓存和回调协议，AFS 还有一些很重要的工程改进

#### 统一命名空间

AFS 更强调**全局命名空间**。也就是说，用户在不同客户端上看到的路径名组织方式更统一。相比之下，NFS 往往允许每台机器自己决定怎么挂载远端目录，结果同一个文件在不同机器上可能出现在不同路径下

#### 安全与访问控制

AFS 比早期 NFS 更认真对待安全：

- 更强调用户认证
- 更支持细粒度访问控制
- 更方便管理谁能访问哪些目录和文件

这让它在多用户、共享环境里更容易真正落地

#### 管理能力

AFS 还提供了更灵活的管理工具，例如卷 `volume` 的概念，可以帮助管理员在服务器之间迁移数据、平衡负载。这些能力虽然不像缓存协议那样“学术上显眼”，但对真实系统的可用性非常关键
