### 条件变量

前面几章已经解决了并发里的第一类问题：多个线程同时访问共享数据如何通过锁实现互斥。但并发程序里还有另一类同样常见的问题：一个线程需要等某个条件变成真，才能继续执行

例如：

- 父线程要等子线程结束
- 消费者要等缓冲区里出现数据
- 生产者要等缓冲区腾出空间

#### 基本概念和示例

条件变量 `condition variable` 可以理解成一个等待队列，线程在某个条件不满足时，把自己挂到这个队列上睡眠，等条件可能发生变化时，再由其他线程把它唤醒

POSIX 里，最核心的两个接口是：

```c
pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
pthread_cond_signal(pthread_cond_t *c);
```

以及另一个版本：

```c
pthread_cond_broadcast(pthread_cond_t *c);
```

- `wait()`：当前线程休眠，等待条件可能成立
- `signal()`：条件可能发生变化，唤醒一个等待者
- `broadcast()`：条件可能发生变化，唤醒所有等待者

举一个最简单的例子：父线程等子线程

假设我们想得到下面这样的输出顺序：

```text
parent: begin
child
parent: end
```

低效的写法是让父线程一直 spin：

```c
volatile int done = 0;

void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}

int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL);
    while (done == 0)
        ; // spin
    printf("parent: end\n");
    return 0;
}
```

这个方案中父线程在空转，白白浪费 CPU。我们真正想要的是条件没满足时睡眠，条件满足时再被唤醒

可以用条件变量实现 join 风格等待，这时就可以引入：

- 一个共享状态变量 `done`
- 一把互斥锁 `m`
- 一个条件变量 `c`

```c
int done = 0; // 真正的条件状态
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER; // 保护这个条件状态
pthread_cond_t c = PTHREAD_COND_INITIALIZER; // 线程睡眠和唤醒时所依附的等待队列

void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}

void *child(void *arg) {
    printf("child\n");
    thr_exit();
    return NULL;
}

void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}
```

##### `wait()` 为什么一定要带锁

`pthread_cond_wait(&c, &m)` 的语义不是“单纯睡一觉”，而是：

1. 调用时线程必须已经持有 `m`
2. `wait()` 会原子地释放锁并让线程睡眠
3. 被唤醒后，它会重新拿回锁
4. 然后再从 `wait()` 返回

这个设计的目的，是避免线程还没真的睡下去，条件已经被别人改了，然后唤醒信号又刚好丢掉

##### 为什么 `done` 不能省

很多人第一次看条件变量时，都会想把代码简化成这样：

```c
void thr_exit() {
    Pthread_mutex_lock(&m);
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}

void thr_join() {
    Pthread_mutex_lock(&m);
    Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}
```

这段代码有致命问题：如果子线程先跑完并 `signal()`，而此时父线程还没开始 `wait()`，这个信号就会直接丢失，之后父线程再去 `wait()`，就可能永远睡下去

##### 为什么 `signal()` 和 `wait()` 都要在持锁时使用

另一个容易犯的错误，是把锁去掉：

```c
void thr_exit() {
    done = 1;
    Pthread_cond_signal(&c);
}

void thr_join() {
    if (done == 0)
        Pthread_cond_wait(&c);
}
```

问题在于这里会发生非常典型的竞态：父线程检查 `done == 0`，还没来得及真正睡下去，子线程把 `done` 改成 `1`，并发出 `signal()`。因为这时没有真正睡着的线程，信号会被丢失。父线程随后再去睡，就可能一直睡下去

所以调用 `wait()` 和 `signal()` 时，都应当持有关联的锁

##### 为什么一定要用 `while`，不要用 `if`

在 join 的例子里，很多人会写成：

```c
if (done == 0)
    Pthread_cond_wait(&c, &m);
```

但标准写法始终是：

```c
while (done == 0)
    Pthread_cond_wait(&c, &m);
```

被唤醒不代表条件一定还满足，只代表条件可能发生了变化。发信号只是把线程唤醒，但并不保证它一醒来时条件仍然成立。因此线程被唤醒后，必须重新检查条件

#### 生产者/消费者（有界缓冲区）问题

条件变量最经典的场景，就是生产者 / 消费者，也叫有界缓冲区 `bounded buffer`。生产者负责往缓冲区里放数据，消费者负责从缓冲区里取数据。于是自然会有两个等待条件：缓冲区空时，消费者必须等，缓冲区满时，生产者必须等

##### 第一层错误：用 `if` + 一个条件变量

最开始很多人会写出这种结构：

- 生产者在 `count == 1` 时等待
- 消费者在 `count == 0` 时等待
- 大家共用一个条件变量

一旦线程数超过 1，很快就会暴露问题。因为某个消费者被唤醒后，在它真正运行之前，缓冲区状态可能已经被别的线程改掉了

这就是教材里那个经典时序：

- 生产者唤醒了消费者 `Tc1`
- 但还没轮到 `Tc1` 运行
- 另一个消费者 `Tc2` 先把数据拿走了
- `Tc1` 再继续往下跑时，就会在空缓冲区上执行 `get()`

所以 `if` 要改成 `while`

##### 第二层错误：只有一个条件变量

即使把 `if` 都改成 `while`，如果仍然只有一个条件变量，问题还没结束。生产者和消费者都睡在同一个等待队列上。于是消费者消费完一个值、调用 `signal()` 时，它理论上应该唤醒一个生产者，因为现在缓冲区空出来了

但如果它不巧唤醒了另一个消费者，就会出现：消费者醒来，发现缓冲区还是空的，又继续睡。与此同时，生产者和其他消费者也可能都在睡，最后所有线程一起睡死

所以这里的核心问题不是“有没有信号”，而是信号发给了错误的那一类线程

##### 正确做法：两个条件变量

标准修正方案是准备两个条件变量：`fill` 表示“缓冲区非空”，`empty` 表示“缓冲区非满”

生产者等待 `empty`，完成 `put()` 后 `signal(fill)`；消费者等待 `fill`，完成 `get()` 后 `signal(empty)`

这样就避免了消费者唤醒消费者、生产者唤醒生产者

##### 从单槽缓冲区到真正的有界缓冲区

教材一开始用的是一个只能放一个值的缓冲区，主要是为了把问题讲清楚。真正更实用的版本是用数组实现循环队列，并用 `fill` 指向写入位置、`use` 指向读取位置、`count` 表示当前元素个数。这样条件就变成了生产者在 `count == MAX` 时等待，消费者在 `count == 0` 时等待

这时系统的并发性和效率都会比“单槽缓冲区”更好，因为生产者不必每放一个值就卡住，消费者也不必每取一个值就立刻切换。即使只有一个生产者和一个消费者，上下文切换也会更少；如果有多个生产者和消费者，就更能发挥缓冲区的并发价值

#### 覆盖条件

最后还有一个更微妙但很实用的场景

假设这是一个多线程内存分配器，线程 A 等待 100 字节，线程 B 等待 10 字节。现在另一个线程释放了 50 字节内存，那么应该唤醒谁？

- 唤醒 A 没用，因为 50 还不够
- 唤醒 B 有用，因为它现在能分配成功

问题在于，普通 `signal()` 很难精确知道该叫醒谁，这时一种保守但有效的方法就是全叫醒

也就是使用：

```c
pthread_cond_broadcast(&c);
```

这样所有等待线程都会起来重新检查自己的条件：能继续的就继续，不能继续的再睡回去，这就是所谓的覆盖条件。代价也很明显，会造成一些不必要的唤醒，增加额外调度和锁竞争成本

所以 `broadcast()` 通常是最稳妥的兜底方法，但不一定是性能最优的方法

### 信号量

到这里为止，我们已经分别见过两类同步原语：

- 锁：解决互斥
- 条件变量：解决等待某个条件成立

而 Dijkstra 提出过一种更统一的抽象：

- 信号量 `semaphore`

信号量既可以拿来做锁，也可以拿来做条件同步

#### 信号量的定义

从使用者角度看，信号量是一个带整数值的对象，最核心的两个操作是 `sem_wait()` 和 `sem_post()`

POSIX 里，初始化通常长这样：

```c
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, 1); // 进程内线程共享，初值为 1
```

这里第三个参数是初值，决定了这个信号量一开始的行为

从直觉上看，这两个操作的语义可以理解成：

```c
sem_wait(s):
    value--          // 先消耗一个资源
    如果 value < 0   // 不够用了
        就睡眠等待

sem_post(s):
    value++            // 归还一个资源
    如果有等待线程
        就唤醒一个
```

`sem_wait()` 不只是“减一”，它还可能让线程阻塞：如果资源足够，就立刻返回；如果资源不够，就睡眠。`sem_post()` 则是增加可用资源，并顺便唤醒一个等待者

所以信号量和条件变量一个很大的区别是，条件变量本身不保存条件状态，而信号量自己的整数值就是状态的一部分

#### 二值信号量（锁）

信号量最直接的一种用法，就是拿来做锁

```c
sem_t m;
sem_init(&m, 0, 1); // 初值必须是 1，表示锁一开始可用

sem_wait(&m);       // 拿锁
// critical section
sem_post(&m);       // 释放锁
```

这里关键只有一件事：初值必须是 `1`

如果初值是 1，那么第一个进入的线程会调用 `sem_wait()` 把值从 1 减到 0，因为结果没有小于 0，所以继续执行。此时它就等价于获得了锁

第二个线程如果这时也来执行 `sem_wait()`，它会把值从 0 减到 -1，因为结果小于 0，所以睡眠，等第一个线程执行 `sem_post()`后，它才会被唤醒继续

所以这种初值为 1 的信号量，本质上就对应一次最多允许一个线程进入。这就是二值信号量

#### 信号量用作条件变量

信号量的第二种经典用途，是实现“一个线程等另一个线程完成”的同步

还是用最简单的父线程等子线程例子：

```c
sem_t s;

void *child(void *arg) {
    printf("child\n");
    sem_post(&s); // 告诉父线程：我结束了
    return NULL;
}

int main(int argc, char *argv[]) {
    sem_init(&s, 0, 0); // 初值是 0：父线程先等，子线程来通知
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL);
    sem_wait(&s); // 等待子线程发通知
    printf("parent: end\n");
    return 0;
}
```

这里关键还是初值：必须是 `0`

如果父线程先运行到 `sem_wait()` 值从 0 变成 -1，父线程睡眠，子线程执行完后 `sem_post()` 把值加回来并唤醒父线程

如果子线程先跑完，先 `sem_post()` 把值从 0 变成 1，之后父线程执行 `sem_wait()` 值从 1 变成 0，不需要睡眠，直接返回

两种时序都正确，这就是信号量相对条件变量一个很不一样的点，信号量可以天然记住一次已经发生过的通知，而条件变量做不到这一点，所以条件变量必须额外配一个状态变量来判断条件是否已经成立

#### 生产者/消费者（有界缓冲区）问题

信号量最经典的第二个大应用，就是生产者 / 消费者问题

我们这里还是沿用上一章的模型：有一个有界缓冲区，生产者往里放，消费者从里取

如果缓冲区大小是 `MAX`，那么最自然的两个信号量是：

- `empty`：还有多少空槽
- `full`：当前有多少已填充槽

于是初始化通常是：

```c
sem_init(&empty, 0, MAX);
sem_init(&full, 0, 0);
```

一开始所有槽都是空的，一开始没有任何满槽

##### 第一次尝试：只有 `empty` 和 `full`

最开始很多人会写出：

```c
producer:
    sem_wait(&empty);
    put(i);
    sem_post(&full);

consumer:
    sem_wait(&full);
    tmp = get();
    sem_post(&empty);
```

如果缓冲区只有一个槽位，这个方案其实能工作，生产者最多只能放一个，消费者最多只能拿一个

但只要 `MAX > 1`，再加上多个生产者或多个消费者，问题就出现了

##### 问题：缺少互斥

信号量 `empty/full` 解决的是：

- 缓冲区有没有空间
- 缓冲区有没有数据

但它们没有解决：

- 多个线程同时修改 `fill`
- 多个线程同时修改 `use`
- 多个线程同时操作缓冲区数组

这些地方本身仍然是临界区

例如两个生产者几乎同时执行 `put()`：

- 它们可能都看到同一个 `fill`
- 然后把数据写到同一个槽里
- 导致数据覆盖

所以这里还必须再补上一层：

- 互斥

##### 给缓冲区操作加一把互斥锁

最自然的补救办法是再加一个二值信号量：

```c
sem_t mutex;
sem_init(&mutex, 0, 1);
```

然后把 `put()` / `get()` 外面包起来

但这里非常容易写出一个死锁的版本：

```c
producer:
    sem_wait(&mutex);
    sem_wait(&empty);
    put(i);
    sem_post(&full);
    sem_post(&mutex);
```

```c
consumer:
    sem_wait(&mutex);
    sem_wait(&full);
    tmp = get();
    sem_post(&empty);
    sem_post(&mutex);
```

##### 为什么会死锁

考虑这样的场景：

1. 消费者先拿到 `mutex`
2. 然后去 `sem_wait(&full)`，发现没有数据，于是睡眠
3. 但它睡着时还持有 `mutex`

这时生产者想运行：

1. 它先要拿 `mutex`
2. 但 `mutex` 被消费者拿着
3. 所以生产者也阻塞

于是：

- 消费者在等 `full`
- 生产者本来能制造 `full`
- 但它又在等 `mutex`

这就形成了循环等待，也就是死锁

##### 正确做法：先等资源，再进临界区

正确顺序应该是：

```c
producer:
    sem_wait(&empty);
    sem_wait(&mutex);
    put(i);
    sem_post(&mutex);
    sem_post(&full);
```

```c
consumer:
    sem_wait(&full);
    sem_wait(&mutex);
    tmp = get();
    sem_post(&mutex);
    sem_post(&empty);
```

这个顺序的关键点在于先等待资源条件，真正进入修改缓冲区的那一小段时再拿互斥锁

这样不会拿着 `mutex` 去睡觉，也就不会卡住另一个本来能推进条件成立的线程

#### 读者—写者锁

除了生产者消费者，信号量还可以用来构造更灵活的同步原语，比如读者 / 写者锁。它要解决的场景是多个读者同时访问通常没问题，但写者必须独占

一个经典实现会维护一个保护读者计数的锁、一个控制写者进入的信号量和一个 `readers` 计数器。第一个读者进来时把写锁拿住，后续读者只增加计数，不再重复拿写锁，最后一个读者离开时再把写锁释放。这样就保证了只要还有读者在场，写者就进不来，多个读者之间仍然可以并发

##### 这种实现的缺点

这种简单实现虽然正确，但有明显公平性问题，读者很容易让写者饿死。只要读者源源不断地到来，可能总是有“至少一个读者还在”，于是写者永远拿不到锁。读写锁再次说明了一个现实问题：正确不等于公平，公平也不等于高性能

#### 哲学家就餐问题

哲学家就餐问题是并发教材里的著名例子。场景是 5 个哲学家围桌而坐，每两人之间有一把叉子，每个哲学家要同时拿到左右两把叉子才能吃饭。最直觉的写法是：

```c
sem_wait(left);
sem_wait(right);
```

吃完再：

```c
sem_post(left);
sem_post(right);
```

##### 问题：死锁

如果 5 个哲学家都先拿左边那把，每个人都会成功拿到一把叉子，然后都在等右边那把。于是形成一个环，每个人都等别人先放，这就是经典死锁

##### 一个简单修法：打破环

让其中一个哲学家反着拿。例如前 4 个都先左后右，最后一个则先右后左，这样就打破了等待环，死锁条件不再成立。这个例子真正想教的不是“叉子怎么拿”，而是只要资源获取顺序形成环，就可能死锁

#### 如何实现信号量

最后，教材中把方向反过来，前面一直在用信号量实现各种同步；现在反过来问能不能只用锁和条件变量，自己实现一个信号量？

通过一个 `Zemaphore` 通常包含一个整数 `value`、一把锁 `lock` 和一个条件变量 `cond`

```c
wait():
    拿锁
    while (value <= 0)
        wait(cond, lock)
    value--
    解锁

post():
    拿锁
    value++
    signal(cond)
    解锁
```

这里要注意两点。第一，这个实现里 `value` 不会真的掉到负数以下并记录等待线程数，它只是 `<= 0` 时阻塞，`> 0` 时允许通过。第二，它再次证明锁和条件变量本身已经足够强，可以构造出更高层的同步原语

### 常见并发问题

很多人一提并发 bug，第一反应就是死锁。但实际工程里，并发缺陷并不只有死锁。研究者对 MySQL、Apache、Mozilla、OpenOffice 这类成熟开源项目做过统计，发现更多的是非死锁类并发错误

#### 有哪些类型的缺陷

从实践角度看，常见并发缺陷大致分成两类：非死锁缺陷和死锁缺陷。前者最常见的是违反原子性 `atomicity violation` 和违反顺序 `order violation`，后者则是线程各自拿着一部分资源，同时等待别人手里的资源，最后谁也动不了。这两类问题看起来都像程序卡住了或者结果不对，但根源完全不同，因此修法也不同

#### 非死锁缺陷

非死锁缺陷之所以值得单独拎出来，是因为它们往往更隐蔽。程序没有彻底卡死但某个时序下会崩、会错、会读到脏状态。相比死锁，这类 bug 更难复现、更难调

##### 违反原子性 `atomicity violation`

第一类典型问题，是程序员以为“一小段代码应该整体执行”，但实际运行时并没有被当成一个原子单元

```c
Thread 1:
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}

Thread 2:
thd->proc_info = NULL;
```

线程 1 先检查 `proc_info` 非空，还没来得及 `fputs()`，线程 2 就把它改成了 `NULL`，等线程 1 恢复执行时，就可能解引用一个空指针。这里真正出问题的不是某一条语句，而是“检查非空”和“使用指针”本来默认应该连在一起，但实际上中间可以被别的线程插进来

##### 这类 bug 的本质

所谓违反原子性，就是程序员期待一段代码具有不可分割的语义，但实际运行中没有同步保证。常见修法也很直接，就是把这段本来应该整体成立的访问包进同一把锁里，例如：

```c
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
pthread_mutex_unlock(&proc_info_lock);
```

与此同时，所有其他会修改 `proc_info` 的地方也必须使用同一把锁

##### 违反顺序 `order violation`

第二类常见问题是代码默认某个动作一定先发生，但调度器并不保证这个顺序，例如：

```c
Thread 1:
void init() {
    mThread = PR_CreateThread(mMain, ...);
}

Thread 2:
void mMain(...) {
    mState = mThread->State;
}
```

线程 2 默认认为 `mThread` 已经初始化好，但如果线程 2 先跑到那一行，而线程 1 还没完成初始化，就会出现空指针引用或读取未初始化状态

##### 这类 bug 的本质

所谓违反顺序，就是 A 本来应该在 B 之前发生，但程序里没有强制这种先后关系。和原子性 bug 相比，这类问题更强调操作先后，修法就是加一个明确的初始化完成同步点。例如准备一个状态变量 `mtInit`、一把锁 `mtLock` 和一个条件变量 `mtCond`，线程 1 初始化完成后设置 `mtInit = 1` 并发出 `signal`，线程 2 在继续之前执行 `while (mtInit == 0) wait(...)`

所以如果你看到一段并发代码里隐含地假设某个对象肯定已经创建、某个字段肯定已经初始化、某个线程肯定已经先做过某事，那就应该立刻警觉：这里很可能藏着违反顺序问题

#### 死锁缺陷

除了非死锁错误，另一大类经典问题就是死锁 `deadlock`。最典型的例子就是两把锁交叉获取

```c
Thread 1:           Thread 2:
lock(L1);           lock(L2);
lock(L2);           lock(L1);
```

如果时序刚好是：

1. 线程 1 先拿到 `L1`
2. 线程 2 再拿到 `L2`
3. 线程 1 等 `L2`
4. 线程 2 等 `L1`

那么双方都会永久等待对方释放资源

与原子性或顺序错误不同，死锁表现为逻辑未崩溃，但执行彻底停滞

在真实系统中，死锁问题频发，首要原因在于模块间的交叉调用与深度嵌套。大型系统中，虚拟内存、文件系统、网络栈与缓存等组件往往相互依赖。锁的依赖关系是复杂的多层网状结构。若缺乏严格的设计约束，不同执行路径极易交叉成环，很容易产生死锁

更麻烦的是封装。例如你只看到：

```c
v1.AddAll(v2);
```

但你不知道它内部其实会先锁 `v1`，再锁 `v2`

如果另一条路径正好反过来调用：

```c
v2.AddAll(v1);
```

那即使两个调用点各自看起来都“很正常”，底层依然可能构成死锁。封装虽然让代码更整洁，但也可能让锁顺序问题更难看见

经典理论里，死锁需要同时满足 4 个条件：

1. 互斥
2. 持有并等待
3. 不可抢占
4. 循环等待

只要其中任意一个被打破，死锁就不会成立

##### 互斥

资源必须一次只能被一个线程占有，例如一把普通互斥锁，这显然满足互斥条件

##### 持有并等待

线程已经拿着某个资源，同时还在等待别的资源，例如线程先拿 `L1`，再去等 `L2`

##### 不可抢占

线程已经拿到的资源，别人不能强行夺走。对于普通锁来说也是这样，只有持有者自己 `unlock()`，别人没法直接抢走

##### 循环等待

线程之间形成等待环，比如 T1 等 T2 的资源，T2 等 T3 的资源，最后又绕回 T1

这 4 条里，很多预防思路本质上就是想办法打破其中某一条

##### 打破循环等待：规定加锁顺序

这是最实用、也最常见的一种做法。如果系统里规定永远先拿 `L1`，再拿 `L2`，那么就不会出现有人先拿 `L2` 再等 `L1`

于是等待环被破坏，死锁也就没法形成

这就是所谓的全序 `total ordering`。在更复杂的系统里，也可以是偏序 `partial ordering`，只要能保证不会形成环即可

这是现实系统里最常见的死锁预防方案，因为它直观、成本低，也不需要特殊运行时机制。不过缺点同样明显：设计难、维护难，而且一旦某个调用点偷偷违反约定，整个体系就会失效

##### 一个很实用的小技巧：按地址顺序加锁

如果一个函数需要拿两个外部传进来的锁，一个常见技巧是按锁对象地址大小来决定获取顺序，例如总是先拿地址较小的锁，再拿地址较大的锁

这样即使两个调用者传参顺序不同，底层加锁顺序仍然一致，从而避免简单的交叉死锁

##### 打破持有并等待：一次性原子地获取所有锁

另一种思路是先通过一个全局“预防锁”把抢锁这件事本身串行化，例如先拿 `prevention`，再拿 `L1` 和 `L2`，最后释放 `prevention`。这样同一时刻只有一个线程处在“我要连续获取多把锁”的阶段，于是持有并等待导致的环很难形成。但缺点也很明显，并发度会下降，封装性会变差，而且你必须提前知道自己到底要拿哪些锁，所以它更像一种思路，而不是通用优雅方案

##### 打破不可抢占：用 `trylock()`

还有一种办法是，不阻塞等待第二把锁，拿不到就先退出来，释放手头资源，稍后重试

例如：

```c
top:
lock(L1);
if (trylock(L2) == -1) {
    unlock(L1);
    goto top;
}
```

这样线程不会一边拿着 `L1` 一边永久等 `L2`，于是死锁被避免了

不过它会引出另一个问题，活锁 `livelock`。也就是两个线程都很“礼貌”，发现拿不到第二把锁就退，然后同时重试，再同时失败，如此反复，程序没死锁，但也没进展。常见缓解方法是随机退避一段时间再重试

##### 从根子上减少互斥：无锁 / 无等待结构

最后一种更激进的方向，是尽量不使用互斥锁本身

例如使用硬件原子指令 `compare-and-swap` 来实现原子计数器、无锁链表插入

这类方案的好处是没有传统锁意义上的死锁。但代价是实现难度高很多，容易活锁，对内存模型和原子指令理解要求更高

##### 通过调度来避免死锁

除了从代码结构上预防，还有一条思路叫死锁避免 `avoidance`。它的核心假设是系统能够提前知道线程会需要哪些资源，那就可以通过调度策略避免把危险组合同时放上去运行。经典代表就是 Dijkstra 的银行家算法

这种思路在某些场景可行，例如嵌入式系统，或者任务集合和资源需求都高度已知的环境。但在一般通用系统里，它的问题也很明显：需要较强的全局信息，太保守时会损失并发，对真实复杂软件不太友好，所以它很重要，但不是最常见的通用工程方案

##### 检测与恢复

最后一类策略是不强求提前彻底避免，允许死锁发生，但系统要能检测出来并恢复。这在数据库和大系统里很常见

它的基本流程通常是定期构建等待图或资源图，检测是否有环；一旦发现死锁，就选择某个线程或事务作为牺牲者，回滚、重启或中止它，让系统恢复推进

这种方案背后的工程哲学很现实：如果死锁很少发生，而提前完全规避的代价又太高，那么检测和恢复可能更划算。当然，这种思路适不适合，取决于系统容不容得下“偶尔出事再补救”，例如普通业务系统可能能接受，但航空航天、医疗控制这类高风险系统通常不能接受

### 基于事件的并发（进阶）

到这里为止，我们讨论的并发几乎都默认了一件事：并发 = 多线程

但这并不总成立。很多 GUI 程序、早期高性能网络服务器，以及后来的 `node.js` 这类运行时，都大量采用了另一条路线：基于事件的并发 `event-based concurrency`

它试图解决两类多线程方案里的老问题：一是多线程程序容易写错，二是线程调度由操作系统决定，程序员控制力不够

#### 基本想法：事件循环

基于事件的并发思想非常朴素：先等事件发生，事件来了以后判断它是什么，再执行一小段对应处理逻辑

整个系统的核心结构，通常就是一个事件循环 `event loop`

伪代码基本如下：

```c
while (1) {
    events = getEvents();
    for (e in events)
        processEvent(e);
}
```

这里最关键的一点是，某一时刻系统通常只在处理一个事件处理函数，因此它天然带来一个重要好处：调度决策变得显式

在多线程模型里，你创建线程之后，什么时候切换、谁先运行，主要由操作系统决定。而在事件驱动模型里，“接下来处理哪个事件”这件事通常就在事件循环里被明确控制

#### 重要 API：`select()`（或 `poll()`）

事件循环虽然简单，但它马上会遇到一个现实问题：程序怎么知道“现在有哪些事件发生了”？

在网络服务器里，最典型的问题就是哪些 socket 上有新数据到了、哪些连接现在可以写了。传统 UNIX 系统为此提供了 `select()` 和 `poll()`

它们做的事本质上都是检查一组文件描述符，告诉你哪些已经就绪，例如可读、可写或者有异常。这样事件循环就不必瞎猜，而是靠系统调用告诉它现在值得处理哪些 I/O 事件

#### 使用 `select()`

`select()` 的接口看起来比较长，但使用思路并不复杂：先准备一组自己关心的描述符，调用 `select()`，等内核返回后再检查哪几个真的准备好了，然后对这些就绪描述符分别执行处理逻辑

所以一个很典型的事件循环长这样：

```c
while (1) {
    FD_ZERO(&readFDs);
    for (fd = minFD; fd < maxFD; fd++)
        FD_SET(fd, &readFDs);

    select(maxFD + 1, &readFDs, NULL, NULL, NULL);

    for (fd = minFD; fd < maxFD; fd++)
        if (FD_ISSET(fd, &readFDs))
            processFD(fd);
}
```

这里的核心不是背 API，而是理解它在事件模型中的角色：它就是“事件从哪里来”的入口

#### 为何更简单？无须锁

基于事件的方法有一个很诱人的优点：在最基础的单线程版本里，通常不需要锁。原因很直接，一次只处理一个事件，事件处理函数不会被另一个线程同时打断

因此很多多线程里烦人的问题，在这里一开始就消失了，比如忘记加锁、锁顺序错误、条件变量用错和竞态条件四处乱飞。事件驱动常被看作一种以结构换复杂度的办法，也就是不让多个线程同时碰状态，从而把同步问题压缩掉

#### 一个问题：阻塞系统调用

事情不会这么完美。事件驱动最怕的就是阻塞调用 `blocking call`。例如某个事件处理程序里，如果你直接 `read()` 一个磁盘文件，或者 `open()` 一个还没缓存进内存的对象，这些调用都可能阻塞很久

而问题在于，事件驱动模型里通常只有这一个主循环线程。如果某个 handler 阻塞了，那么结果不是“某个线程慢了”，而是整个服务器停住了

这就是事件驱动里那条非常重要的工程纪律：事件处理函数里不要做会长时间阻塞的事，否则你虽然没有锁问题，但会把整个系统拖死

#### 解决方案：异步 I/O

为了让事件循环在 I/O 发出去之后还能继续跑，操作系统后来逐步提供了异步 I/O `asynchronous I/O`

它的基本语义是：你发起一个 I/O 请求，调用立刻返回，真正的 I/O 在后台进行，稍后你再检查它是否完成

这和传统阻塞 I/O 的区别就在于，阻塞 I/O 是发请求的人原地等结果，异步 I/O 则是先把请求挂出去，自己继续做别的事

这对于事件驱动非常关键，因为它保证了主循环不会因为一次磁盘读取而整个卡住

#### 另一个问题：状态管理

异步 I/O 解决了“别阻塞”这个问题，但也引出了另一个麻烦：程序状态管理会变复杂

在多线程写法里，代码通常很自然：

```c
read(fd, buffer, size);
write(sd, buffer, size);
```

为什么这么自然？因为 `read()` 返回时，线程自己的栈还在，变量 `sd`、`buffer`、`fd` 也都还在当前上下文里。线程栈天然帮你保存了“接下来干什么”的状态

但在事件驱动模型里，你把读请求异步发出去了，主循环先返回，等读完成时，早就不在原来那段调用栈里了。于是你必须自己把“后续还要干什么”记录下来，这就是很多文献里提到的手工栈管理 `manual stack management`

为了处理这种先发请求、以后再续上的流程，事件驱动系统常会用一个概念：延续 `continuation`，也就是把之后还要继续做什么记录在某个结构里。这些信息必须提前存起来，等事件真正发生时再取出来继续执行，例如某个文件描述符完成读取之后，结果该写到哪个 socket、该回调哪个函数、状态机该推进到哪一步。所以如果说线程模型的优势是栈天然就是 continuation，那么事件驱动模型的代价就是要自己维护。事件驱动简化的不是所有复杂度，而是特别简化了多线程同步复杂度。它减少了锁、竞态、条件变量误用和调度不可控，但把复杂度转移到了非阻塞 I/O 设计、事件拆分、状态机管理和 continuation 管理上

#### 什么事情仍然很难

即使不考虑实现细节，基于事件的方法仍然有几个天然难点。首先，多核时代它不再那么纯粹。在单 CPU 的单线程事件循环里，“没有锁”成立；但如果你想用满多核，就要并行运行多个 handler，或者并行运行多个事件循环，这时共享状态依旧会回来，锁、同步和竞态也会重新出现，所以“事件驱动不需要同步”只在最朴素的单线程事件循环里才完全成立

其次，隐式阻塞依旧可能出现。即使代码里没有显式写阻塞 I/O，也可能遇到页错误，或者缓存未命中导致的底层阻塞，事件循环一旦在这些地方卡住，整个系统仍然会停摆。再往后，程序结构也会变碎。在线程模型里，一段逻辑可以线性地写成先做 A，再等 I/O，再做 B；到了事件驱动里，同样的逻辑往往会裂成 A handler、I/O 完成后的 B handler，甚至后续 C handler。再加上网络 I/O、磁盘 I/O、计时器、信号在不同系统上的异步接口常常风格不一致，工程上的难点就变成如何把这些来源不同的事件统一进一个循环
