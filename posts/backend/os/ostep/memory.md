### 抽象：地址空间

#### 早期系统

早期的操作系统只是一组库函数，并没有提供多少抽象。在内存中，地址0 ~ 64KB存放操作系统代码和数据，64KB ~ Max存放当前运行的一个用户程序（进程）。一次只能运行一个程序，用户程序直接访问物理内存，没有保护和隔离

#### 多道程序与分时共享

为了提高昂贵机器的利用率（多道程序）和交互性（分时共享），必须让多个进程同时驻留在内存中

如果简单地让多个进程共享物理内存（进程 A、B、C 分别占用不同物理段），会面临严重的**保护**问题，进程 A 不应该能读写进程 B 的内存，更不能破坏操作系统的内存

#### 地址空间

操作系统为每个进程提供了一个易用的、抽象的物理内存视图，称为**地址空间**，是运行的程序所看到的系统内存

- **代码**：静态指令，通常位于地址空间顶部（地址 0），大小固定

- **堆**：动态分配的内存（`malloc`/`new`），位于代码之下，**向下增长**

- **栈**：函数调用栈（局部变量、参数、返回地址），位于地址空间底部，**向上增长**

- **虚拟化**：程序看到的地址（虚拟地址）通常从 0 开始。实际上，程序被加载到物理内存的任意位置。硬件和操作系统协作，通过页表将程序发出的虚拟地址动态转换为实际的物理地址

#### 目标

- **透明**：进程不应感知到内存被虚拟化，它认为自己拥有巨大的、连续的私有内存

- **效率**：尽可能高效。地址转换不能太慢，拖慢程序运行，虚拟化机制本身占用的内存（如页表）不能太多。依赖硬件支持（如 TLB）

- **保护/隔离**：进程间互不干扰，进程不能访问操作系统内核，每个进程都在各自独立环境中运行

你在 C 程序中打印出的任何指针`%p`都是**虚拟地址**。只有操作系统和硬件知道这些虚拟地址真正对应的物理位置

### 插叙：内存操作API

#### 内存类型

运行 C 程序时，会涉及两种不同的内存区域：

**栈内存**：隐式管理，由编译器自动处理申请和释放。变量在进入函数时分配，离开函数时立即释放，数据无法在函数调用结束后保留

**堆内存**：显式管理。程序员全权负责申请 (`malloc`) 和释放 (`free`)。从申请那一刻起，直到被显式释放为止。需要手动释放内存，这也是大部分内存 Bug (泄漏、悬垂指针) 的源头

#### `malloc()` 详解

`malloc` 用于在堆上请求空间。`void *malloc(size_t size)`。`size_t`为需要申请的字节数，成功则返回指向内存首地址的指针 (`void*`)；失败返回 `NULL`

建议使用 `sizeof()` 操作符，不要硬编码，因为不同机器上 `int` 大小可能不同，因为`sizeof` 是编译时操作符。编译器在编译阶段就把它替换成了具体的数字，不是函数调用

注意如果对一个指针用 `sizeof`，得到的只是**指针本身的大小**，而不是它指向的内存块大小

```c
int *x = malloc(10 * sizeof(int));
printf("%d\n", sizeof(x)); // 打印出 8 (指针大小)，而不是 40

int x[10];
printf("%d\n", sizeof(x)); // 打印 40 字节
```

另外还有要注意 C 字符串以空字符 `\0` 结尾，要习惯写成`malloc(strlen(s) + 1)`。不要忘记`+1`，否则会导致缓冲区溢出

`malloc` 返回 `void*`。虽然 C 语言允许自动转换，但写成 `(int *)malloc(...)`是一种好习惯

#### `free()` 详解

`free()` 用于释放不再使用的堆内存。`void free(void *ptr)`，\*ptr 必须是之前 `malloc` 返回的那个指针。 `free(ptr)` 不需要传入释放空间的大小。内存分配库会在分配的内存块头部记录这块内存的大小。`free` 时读取这个头部信息来决定释放多少空间

#### 常见错误

**忘记分配内存**

你声明了一个指针 `char *dst;`，却没有让它指向任何有效的内存地址，然后就试图往里面写入数据。这样会导致段错误：你试图访问不属于你的内存区域

```c
char *src = "hello";
char *dst;         // 这是一个野指针，未指向已分配的内存
strcpy(dst, src);  // 段错误，试图向随机地址写入数据

// 正确做法
// 申请空间
char *dst = (char *) malloc(strlen(src) + 1);
strcpy(dst, src);

// 或者使用 strdup (由库函数 malloc 和 strcpy)
char *dst = strdup(src);
```

**没有分配足够的内存**

在为字符串分配空间时，忘记了字符串结束符 \0：`malloc(strlen(src))`，也叫缓冲区溢出。后果不好预测，malloc 库通常会多分配一点点填充字节，或者覆盖了不重要的数据。最坏情况会引发严重的安全漏洞，黑客可利用溢出进行攻击。即使它正确运行过一次，也不意味着它是正确的

**忘记初始化**

调用 `malloc` 后，直接读取其中的数据。调用malloc后需要初始化分配的内存避免读到未知值，要么手动赋值（如 `strcpy`），要么使用 `calloc()` 替代 `malloc()`，它会将内存清零

**忘记释放内存**

申请内存，用完却忘了 `free()`，导致内存被占用，直到程序结束。这就是**内存泄漏**

短时间运行的程序（如 `ls`, `grep`）问题不大。因为进程退出时，操作系统会回收所有资源。长时间运行的程序（如 Web 服务器、数据库、操作系统内核）内存会被逐渐耗尽，最终导致OOM。即使在有垃圾回收（GC）的语言中，如果你一直持有对象的引用，GC 也无法回收，依然会导致泄漏

**提前释放内存**

这被称为**悬垂指针**。调用`free(x)`，但这块内存之后又被使用了，这会导致程序崩溃

或者这块内存被`malloc`分配给了另一个变量。你通过旧指针 `x` 的写入操作，会覆盖新变量的数据

**重复释放内存**

对同一个指针调用了两次 `free()`，会导致未定义行为，通常会让malloc library内部的元数据乱套，导致程序崩溃

**错误地调用free**

如果传给`free()`的指针不是`malloc()`返回的指针，例如释放栈上的指针，或者释放指针加了偏移量后的地址，这会引发崩溃

**为什么在进程退出时没有内存泄露？**

因为系统存在两级内存管理。**第一级是由操作系统执行的内存管理**，操作系统将内存按页分配给进程。当进程终止时，操作系统会回收该进程占用的所有物理内存页。**第二级管理在每个进程中**，`malloc` 和 `free` 是在进程内部管理操作系统给的那块地。内存泄漏指的是在进程**活着**的时候，堆越来越大，无法复用

### 机制：地址转换

和 CPU 虚拟化中的受限直接执行类似，内存虚拟化也试图同时达到两个目标：

- 高效：尽量依靠硬件快速完成常规工作
- 控制：确保进程只能访问自己被允许访问的内存

为此，系统采用的核心技术就是**地址转换 `address translation`**。程序看到的是虚拟地址，而硬件会在每次内存访问时把它翻译成真正的物理地址

#### 假设

书里第一次讲内存虚拟化时，先做了一组假设：

- 每个进程的地址空间必须连续地放在物理内存中
- 每个地址空间都小于物理内存
- 每个进程的地址空间大小都相同

这些假设当然过于理想化，但它们能先把问题压缩到最核心的一层：**如何让进程以为自己地址空间从 0 开始，但实际上被放在物理内存中的任意位置**。后面的 TLB、分段、分页、多级页表，都是在这个基础上一步步放宽假设得到的更现实方案

#### 一个例子

假设程序执行这样一行：

```c
x = x + 3;
```

对应的汇编可能类似：

```asm
128: movl 0x0(%ebx), %eax
132: addl $0x03, %eax
135: movl %eax, 0x0(%ebx)
```

这里可以把 `ebx` 看作保存变量 `x` 地址的寄存器。程序从它自己的角度出发，认为自己运行在一个从 `0` 开始的地址空间里。例如：

- 代码在地址 `128`
- 变量 `x` 在地址 `15KB`

从程序视角看，这些地址都完全合理；但操作系统并不一定真的把这个程序放在物理内存从 `0` 开始的位置。它可能把程序整个搬到物理地址 `32KB` 开始的地方，这就产生了一个根本问题：

- 程序发出的地址是虚拟地址
- 真正访问的应该是另一处物理地址

并且这一切必须对程序透明

#### 动态（基于硬件）重定位

最早的一种硬件支持方案叫**基址加界限机制 `base and bound`**，也常叫**动态重定位 `dynamic relocation`**。

它只需要每个 CPU 提供两个寄存器：

- 基址寄存器 `base`
- 界限寄存器 `bound`

工作方式非常简单。程序发出的每个虚拟地址，硬件都会做一次加法：

```text
physical address = virtual address + base
```

如果一个进程的地址空间被放到了物理内存 `32KB` 开始的位置，那么：

- 程序引用虚拟地址 `128`
- 硬件实际访问物理地址 `32KB + 128`

这样，程序仍然以为自己从 `0` 开始运行，但实际上已经被重定位到了别处

界限寄存器则负责保护。假设地址空间大小是 `16KB`，那么：

- 小于 `0` 的地址非法
- 大于等于 `16KB` 的地址非法

如果进程访问越界地址，CPU 会触发异常

这套机制的好处非常明显：

- 地址转换逻辑简单
- 每次访问只要加一个基址即可
- 界限检查也容易做

书里也顺带提到了更早的纯软件办法，也就是静态重定位。那种方式是在加载程序时直接修改指令中的地址常量，但它既不灵活，也很难提供真正的保护，因此很快被基于硬件的动态重定位替代

#### 硬件支持：总结

为了让基址加界限方案真正可行，硬件必须提供几类支持。

- **特权模式**。因为基址寄存器和界限寄存器控制了内存访问的基本规则，绝不能让用户程序自己随便改

- **基址/界限寄存器**以及执行地址转换和越界检查的电路。这部分整体上可以看作早期内存管理单元 `MMU` 的最简形式

- **特权指令**来设置这些寄存器，以及注册异常处理程序。因为只有操作系统才有资格设置进程的地址空间映射并决定越界访问时该怎么办

- 硬件在错误发生时**触发异常**

从这个角度看，地址转换不是“纯硬件功能”，而是**硬件提供快速路径，操作系统负责配置和兜底**

#### 操作系统的问题

有了这些硬件支持之后，操作系统必须承担一组新的职责。

- 在进程创建时，操作系统要为它找到一块足够大的连续物理内存，并把这个地址空间装进去。因此，内核需要维护某种空闲内存数据结构，例如空闲列表

- 在进程结束时，操作系统必须回收这块内存，把它重新放回空闲空间管理结构中

- **上下文切换**时，操作系统必须保存并恢复基址/界限寄存器。因为每个进程被装在不同的物理位置，所以这两个寄存器的值显然是进程相关的，而不是 CPU 全局固定的

- 操作系统必须提供**异常处理程序**。一旦进程越界访问，或者试图做特权操作，内核必须接管，并通常会终止这个进程

书里给出的时间线很能说明这个机制：

1. 操作系统启动时初始化陷阱表、中断、空闲列表和进程表
2. 启动进程 A 时，操作系统设置好基址/界限寄存器
3. 之后 A 在用户态直接运行，地址转换都由硬件完成
4. 时钟中断发生，进入内核
5. 操作系统切换到进程 B，并恢复 B 的基址/界限值
6. 如果 B 越界访问，硬件触发异常，再次进入内核
7. 操作系统终止 B 并回收资源

这说明虚拟内存实现上仍然遵循和 CPU 虚拟化相同的模式：**大部分时间直接运行，关键时刻由内核介入**

### 分段

上一节用基址加界限寄存器实现了最简单的地址转换，但那个方案有一个明显问题：它要求整个地址空间作为一个连续整体放进物理内存。这样一来，即使栈和堆之间大部分区域根本没被使用，这些空洞仍然会占据真实物理内存

如何支持很大的地址空间，同时避免把其中大量根本没用到的区域也一并装入物理内存？如果一个进程逻辑上拥有很大的地址空间，但实际上只用到其中几小段，该怎么办？

#### 分段：泛化的基址/界限

分段的基本想法，是把“一个地址空间只有一对基址/界限寄存器”推广成“地址空间中的每个逻辑段都有自己的一对基址/界限寄存器”。每个段本身仍然是连续区域，但不同段可以被独立放到物理内存中的不同位置。这样，操作系统不再需要把整个地址空间完整搬进物理内存，而只需要给真正使用的段分配空间

这就直接解决了之前的浪费问题。原来基址加界限方案中，堆和栈之间的巨大空洞必须跟着整个地址空间一起分配；而分段之后，这块空洞根本不需要映射到物理内存

从这个角度看，分段其实就是延续地址转换，但把转换粒度从“整个地址空间”缩小到“地址空间中的每个逻辑部分”。这样就能更自然地支持稀疏地址空间 `sparse address space`。

#### 引用哪个段

一旦地址空间被拆成多个段，硬件就必须回答一个问题：某次内存访问到底引用的是哪个段？

一种常见方法是**显式方式**。也就是把虚拟地址的高位拿出来作为段号，剩余低位作为段内偏移。

例如，如果我们有 3 个段，那么通常需要 2 个高位来表示：

- `00` 表示代码段
- `01` 表示堆段
- `10` 或 `11` 表示其他段

之后，硬件做的事就类似于：

1. 取出虚拟地址的高位，判断是哪个段
2. 取出剩余位，作为段内偏移
3. 检查偏移是否超过该段界限
4. 若合法，就用 `base + offset` 得到物理地址

这和之前的地址转换公式很像，只不过现在先要找到“该用哪一组寄存器”

书里给出的伪代码本质上就是：

```text
segment = 取虚拟地址高位
offset = 取剩余低位
if offset >= bounds[segment]:
    异常
else:
    phys = base[segment] + offset
```

还有一种方式叫**隐式方式**。硬件不通过虚拟地址的高位来判断段，而是通过地址产生的上下文判断：

- 程序计数器产生的地址来自代码段
- 栈指针相关地址来自栈段
- 其他普通数据访问默认属于堆段

无论哪种方式，核心都没变：硬件必须先判断“这是哪个段”，然后才能完成地址转换

#### 栈怎么办

栈段比代码段和堆段更特别，因为它通常是**反向增长**的。代码段和堆段一般从低地址往高地址扩展，而栈往往从高地址往低地址增长。因此，仅有基址和界限寄存器还不够，硬件还必须知道该段的增长方向

为此，分段系统通常为每个段再增加一位额外信息，用来表示：

- 正向增长
- 反向增长

这样处理栈地址时，硬件就不会把它当作“普通从段起始处向上偏移”的地址，而是按反向偏移解释

书里的例子说明了这个差别：某个虚拟地址虽然表面上接近地址空间上界，但对栈来说它其实对应的是“离栈顶向下多少”的位置。硬件必须按这种方式算出真正物理地址

这里也引出了一个熟悉的术语：**段错误 `segmentation fault`**。其本意正是“某次内存访问不在对应段的合法范围内”，硬件因此抛出异常

即使现代系统未必真的用传统分段实现虚拟内存，这个名字仍然保留下来了

#### 支持共享

分段除了节省空间，还有一个额外优点：更容易支持共享

最典型的共享对象就是**代码段**。多个进程运行同一个程序时，它们的代码通常是一样的。如果代码段被标记为只读并可执行，那么操作系统就可以把同一份物理代码映射到多个进程的虚拟地址空间里

要做到这一点，硬件需要为每个段增加**保护位 `protection bits`**，用来指示该段的访问权限。于是典型权限组合就会变成：

- 代码段：读 + 执行
- 堆段：读 + 写
- 栈段：读 + 写

这样一来进程可以共享同一份代码，但又不能随意修改它，这既节省物理内存，又保持了隔离性。同时，硬件在做地址转换时也必须多做一步检查：不仅要看是否越界，还要看访问类型是否符合权限。例如，向代码段写数据，或者从栈段执行指令，都应该触发异常

#### 细粒度与粗粒度的分段

到目前为止，我们讨论的分段大多是粗粒度的：整个地址空间通常只有几个大段，例如代码、堆、栈。但历史上也存在更细粒度的分段系统，它们允许把地址空间拆成很多小段。这样做的目标是让系统更灵活：

- 编译器可以把不同代码部分、不同数据对象拆成不同段
- 操作系统可以更精细地管理它们
- 某些没被用到的小段甚至可以不放入内存

要支持大量段，光靠少量固定段寄存器就不够了，因此需要引入某种**段表 `segment table`**

不过，虽然细粒度分段更灵活，它也会带来更复杂的硬件和操作系统实现。后续内存管理的发展转向了分页等更统一的机制

#### 操作系统支持

分段带来了更好的空间利用率，但同时也给操作系统引入了新的负担

- 上下文切换时，内核必须保存和恢复每个进程对应的段寄存器状态。因为不同进程的代码段、堆段、栈段都可能放在完全不同的物理位置

- **物理内存管理**。因为现在分配的对象不再是“大小统一的一整块地址空间”，而是“大小不同的许多段”。于是物理内存中很容易出现很多分散的小洞

这就是**外部碎片 `external fragmentation`**

- 总空闲内存也许足够
- 但它被分割成了许多不连续的小块
- 因此无法满足某个需要较大连续空间的新段分配请求

书里给出的例子很典型：明明总共有 `24KB` 空闲空间，但它们散落在三个彼此不相邻的小区域里，于是一个 `20KB` 的新段仍然无法分配。

应对外部碎片，操作系统通常有两种思路：

- 紧凑 `compaction`。也就是暂停一些进程，把它们的段拷贝到新的、更连续的位置，再更新段寄存器，从而把空闲空间重新拼成大块。这种办法有效，但代价非常高，因为大量内存复制本身就很昂贵。

- 使用更聪明的空闲空间分配算法，例如：

1. 最佳匹配 `best-fit`
2. 最差匹配 `worst-fit`
3. 首次匹配 `first-fit`
4. 伙伴算法 `buddy algorithm`

这些算法能在一定程度上缓解外部碎片，但很难从根本上消除它

### 空闲空间管理

如何管理可变大小的空闲空间。这个问题出现在很多地方，例如：

- `malloc()` / `free()` 这样的用户态分配器
- 操作系统里的分段式虚拟内存管理
- 任何需要处理变长对象分配的内存系统

如果空间被切成固定大小单元，那么管理很简单；但一旦请求大小可变，外部碎片就会成为核心难题。面对变长分配请求，应该怎样管理空闲空间？哪些策略有助于减少碎片？不同方法各自的时间开销、空间开销和适用场景是什么？

#### 假设

最基础的接口形态是：

```c
void *malloc(size_t size);
void free(void *ptr);
```

这里有一个很关键的接口特征：`free()` 只收到一个指针，没有收到块大小。这意味着分配器必须自己知道被释放块的大小，否则就无法把这块空间正确归还给空闲空间管理结构

书里还做了几项简化假设：

- 主要关注外部碎片 `external fragmentation`
- 已分配给用户的块不能被移动
- 分配器管理的是一块连续的堆空间
- 这块空间在讨论中默认大小固定

这些假设让问题聚焦在“如何在已有连续区域里管理变长空闲块”上

这里也再次区分两种碎片：

- 外部碎片：总空闲空间足够，但被切碎后没有足够大的连续块满足请求
- 内部碎片：分配给用户的块比请求更大，块内部剩余空间被浪费

#### 底层机制

在讨论具体策略前，书里先介绍了大多数分配器都依赖的一些基础机制

##### 分割与合并

设想堆里有两个空闲块：

```text
[ 10字节空闲 ][ 已分配 ][ 10字节空闲 ]
```

如果此时来了一个 `1` 字节请求，分配器不会浪费整块，而是从一个足够大的空闲块里切下一部分给用户，剩余部分继续留在空闲列表里。这就是**分割 `splitting`**

反过来，如果用户释放了一块和已有空闲块相邻的内存，而分配器只是简单把它插回列表，不去合并，就会导致整个空间虽然都空着，却仍然被人为切成很多小块

因此，分配器通常还需要**合并 `coalescing`**：如果新归还的块和前后空闲块相邻，就把它们拼成一块更大的空闲块。否则，即使总空闲空间足够，也可能因为没有大块连续空间而分配失败

分割解决“怎么从大块里拿出小块”，合并解决“怎么避免空闲空间越变越碎”。这两者几乎是所有分配器最基础的动作

##### 追踪已分配空间的大小

因为 `free(ptr)` 并不知道 `ptr` 对应的块有多大，所以分配器必须在块附近偷偷存一些元数据。最常见的方法，是在返回给用户的内存块前放一个**头块 `header`**

```c
typedef struct header_t {
  int size;
  int magic;
} header_t;
```

其中至少要记录：

- 这块空间的大小
- 一些额外校验信息，例如 `magic`

这样，用户拿到的是“头块之后”的可用指针；当 `free(ptr)` 被调用时，分配器只要做一点指针运算，就能回到头块位置，读出块大小并完成释放

##### 嵌入空闲列表

分配器需要维护空闲列表，但又不可能在自己内部调用 `malloc()` 去申请链表节点，否则就循环依赖了。解决方法是：**把空闲列表节点直接嵌进空闲空间本身**

```c
typedef struct node_t {
  int size;
  struct node_t *next;
} node_t;
```

空闲块本身既是一段可分配空间，同时也暂时充当空闲列表中的节点。于是：

- 分配时，从这些节点代表的空闲区域里切下一块
- 释放时，再把新的空闲区域插回列表

这就是经典 malloc/free 分配器的基本组织方式

##### 让堆增长

如果空闲空间彻底用完了怎么办？一种做法是直接失败，返回 `NULL`。但大多数通用分配器会选择向操作系统继续申请更多堆空间，例如通过 `sbrk()` 或类似机制

也就是说，分配器虽然逻辑上在管理“堆”，但它自己其实也只是向操作系统再要更多内存而已

#### 基本策略

有了上述基础机制之后，核心问题就变成：当一个请求到来时，到底该从哪个空闲块里分配？理想目标当然是：

- 分配速度快
- 外部碎片少

但这两者往往彼此冲突。书里依次介绍了几种经典策略

##### 最优匹配

最优匹配 `best fit` 的思路是：遍历整个空闲列表，在所有“足够大”的空闲块里，选那个最小的返回。尽量让被消耗的空闲块和请求大小接近，以减少浪费

问题在于：

- 需要遍历整个列表
- 开销偏大
- 还常常会留下很多很小的边角块

因此，它在减少某些浪费的同时，也容易制造大量难再利用的小碎片

##### 最差匹配

最差匹配 `worst fit` 则反过来，总是选最大的空闲块来切。切最大的块之后，剩下的部分仍然可能比较大，因此可能更有利用价值

但实践里，这种策略往往表现并不好：

- 同样需要遍历整个列表
- 常产生不必要的浪费
- 碎片控制效果通常不理想

##### 首次匹配

首次匹配 `first fit` 是找到第一个足够大的空闲块就停下并使用

它最大的优点是速度快，因为无需扫完整个列表。缺点是：

- 空闲列表前部容易被不断切碎
- 列表前端很快堆满大量小块

因此，首次匹配通常和某种列表组织方式一起使用，尤其是按地址排序，这样更有利于之后做合并

##### 下次匹配

下次匹配 `next fit` 是首次匹配的一个变体。它不总是从头开始找，而是从上一次查找结束的位置继续

它的目标是：

- 避免总是把列表前面切得太碎
- 让搜索成本分摊到整个列表

性能特征通常与首次匹配相近，但在某些负载下会让碎片分布得更均匀一些

##### 这些策略真正意味着什么

书里通过一个简单空闲列表例子说明了几种策略的差别：给定若干大小不同的空闲块，面对同一个请求，不同策略会选择不同块，从而产生不同后果。选择哪个块，会直接影响未来还剩下什么空闲空间形状，也就是会影响未来请求的成功率和查找成本

因此，分配策略本质上是在“当前请求”和“未来空间形状”之间做博弈

#### 其他方式

基础策略之外，人们又提出了大量改进方法，其中最重要的几类如下

##### 分离空闲列表

分离空闲列表 `segregated free lists` 的核心想法是：如果某类对象大小很常见，那就给它单独准备一套空闲列表，而不是让所有请求都混在一个总列表里竞争，好处很明显：

- 查找更快
- 几乎不需要复杂搜索
- 某些常见大小的分配和释放都能非常高效

典型例子就是 slab 分配器。它会为某些高频对象大小建立专门缓存，例如 inode、锁、内核对象等。这样不仅分配快，而且还常常让对象保持“已初始化”的状态，从而连初始化/析构开销都省掉一部分

##### 伙伴系统

另一种经典方法是伙伴分配器 `buddy allocator`，它把空闲空间按 2 的幂划分。需要一块空间时，就不断把较大的块二分，直到得到刚好能容纳请求的块。释放时，再检查它的“伙伴块”是否也空闲，如果是，就合并为更大的块，并递归继续向上合并，优点是：

- 合并非常容易
- 伙伴位置计算也简单
- 分割和合并逻辑规则统一

代价则是只能分配 2 的幂大小的块，因此会产生内部碎片，它是在实现简单性和空间精细度之间做的折中

##### 更复杂的数据结构

简单链表策略在规模变大后查找效率不够好，因此很多更先进的分配器会使用：

- 平衡树
- 伸展树
- 其他更复杂的数据结构

目的很直接：减少查找时间，提高可扩展性

再往后，随着多核和多线程程序普及，现代分配器还必须考虑并发扩展性。也就是说，问题不再只是“怎么减少碎片”，还包括“怎么在多核上让分配和释放不互相卡死”

### 分页：介绍

前面分段的思路是把地址空间切成若干逻辑段，但这种可变大小的空间管理方式会带来外部碎片。分页提供了另一条路线：**把空间切成固定大小的单元**。这样分配与回收都会简单很多，也不再需要面对“总空闲空间足够但没有足够大连续块”的典型分段难题

怎样利用固定大小的页来实现虚拟内存，从而避免分段的问题？分页的核心机制是什么？它又会引入哪些新的时间和空间开销？

#### 一个简单例子

分页的做法是：

- 把虚拟地址空间切成固定大小的页 `page`
- 把物理内存切成同样大小的页帧 `page frame`

例如，书里的小例子中：

- 虚拟地址空间大小是 `64B`
- 每页是 `16B`
- 因此共有 `4` 个虚拟页

物理内存则有 `8` 个页帧。操作系统要做的事，就是把这 4 个虚拟页分别放到若干空闲页帧里，不要求它们在物理内存中连续

这正是分页最重要的优点之一：**灵活性**。地址空间中的不同部分不必连续装入物理内存，只要每页能找到一个空闲页帧即可

为了记录“每个虚拟页被放到了哪个物理页帧”，操作系统要为每个进程维护一个**页表 `page table`**。它是分页中最核心的数据结构

举例来说，如果一个进程的 4 个虚拟页分别被放到了物理页帧 3、7、5、2，那么页表本质上就记录了这 4 条映射关系

#### 页表存在哪里

页表是每个进程都需要维护的数据结构，因此它的规模很关键，假设：

- 虚拟地址空间是 `32` 位
- 页大小是 `4KB`
- 一个页表项大小是 `4B`

那么一个进程大约有：

- `2^32 / 2^12 = 2^20` 个虚拟页

也就是大约一百万个页表项。乘上每项 `4B`，单个页表大小就是 `4MB`，一个进程的页表就可能占几 MB，一百个进程就可能仅页表就吃掉数百 MB 内存

因此，页表不可能像基址寄存器那样直接塞进硬件里。它通常只能放在内存中，由操作系统管理，而硬件在地址转换时去访问它

这也引出了分页的第一个问题：**页表会非常大**

#### 列表中究竟有什么

如果把页表实现成最简单的形式，那么它通常就是一个数组，也叫**线性页表 `linear page table`**

数组下标是虚拟页号 `VPN`，对应元素就是该页的页表项 `PTE`

一个页表项里通常不只是物理页帧号，还会包含很多控制信息，例如：

- 有效位 `valid`：这个虚拟页是否合法
- 保护位 `protection bits`：是否允许读、写、执行
- 存在位 `present`：页面是否当前在物理内存中
- 脏位 `dirty`：是否被修改过
- 访问位 `reference/accessed`：最近是否被访问过

例如，地址空间里未使用的大块区域可以通过把 PTE 标记为无效来表示。这样系统就不用真的给这些页分配物理页帧，从而支持稀疏地址空间

因此，页表项并不只是“地址翻译记录”，同时也是访问控制和内存状态管理的一部分

#### 分页：也很慢

虽然分页很灵活，但它也带来第二个现实问题：**地址转换本身会拖慢访存**

设想有一条简单指令：

```asm
movl 21, %eax
```

它想从虚拟地址 `21` 读取数据。为了完成这个读取，硬件不能直接去访问物理内存中的某个地址，而必须先完成几步：

1. 从虚拟地址中取出虚拟页号 `VPN`
2. 用页表基址寄存器找到当前进程页表的位置
3. 到内存里读取对应的页表项 `PTE`
4. 从 PTE 中取出物理页帧号 `PFN`
5. 再和偏移量组合成最终的物理地址
6. 最后才真正访问这个物理地址

也就是说，一次普通访存至少会变成一次访问页表 + 一次访问真实数据。这在逻辑上等于每次访存都要付出双倍内存访问成本。对于现代系统来说，这种开销太高了。因此，分页虽然解决了分段的外部碎片问题，但马上又引入了第二个关键难题：**地址转换过慢**

#### 内存追踪

为了让这个问题更直观，书里用一个小数组初始化循环做例子：

```c
int array[1000];
for (i = 0; i < 1000; i++)
  array[i] = 0;
```

这个循环看起来很简单，但如果在分页系统里仔细展开，会发现每次迭代可能涉及很多内存访问：

- 获取指令本身需要访存
- 执行 `mov` 写数组时又需要一次显式数据访存
- 而这些访存之前，还都可能要先访问页表完成地址转换

于是，一个看似简单的循环，会不断地产生：

- 指令取值访问
- 数组访问
- 页表访问

书中的追踪图就是为了说明这个事实：只要没有额外缓存机制，分页会让每次普通内存访问变得相当昂贵。既然地址转换太慢，就需要一个办法把这些频繁重复的转换缓存起来

### 分页：快速地址转换（TLB）

TLB 的本质就是一个很小、很快、放在芯片上的地址转换缓存。它缓存最近常用的“虚拟页号 -> 物理页帧号”映射，让绝大多数内存访问不再需要去查页表

#### TLB 的基本算法

有了 TLB 之后，地址转换的基本流程变成：

1. 从虚拟地址中取出 `VPN`，在 TLB 中查这个 `VPN`
2. 如果找到，就是 `TLB hit`，直接拿到 `PFN`，和偏移量拼出物理地址
3. 如果没找到，就是 `TLB miss`，再去查页表，更新 TLB，然后重试该指令

书里的伪代码本质就是：

```text
VPN = 取出虚拟页号
if TLB中有VPN:
    检查权限
    组成物理地址
    访问内存
else:
    访问页表
    检查有效位和权限
    把结果插入TLB
    重试指令
```

#### 示例：访问数组

书里用一个数组访问例子说明 TLB 如何利用空间局部性

- 一个由 10 个整数构成的数组
- 每个整数 `4B`
- 虚拟地址空间只有 `8` 位
- 页大小是 `16B`

那么每页正好能放 4 个整数中的一部分。数组会横跨若干页，例如：

- 前几个元素在一个页里
- 中间几个元素在下一页
- 最后几个元素又在下一页

```c
for (i = 0; i < 10; i++)
  sum += a[i];
```

访问 `a[0]` 时，由于是第一次碰到对应页，往往会 `TLB miss`。但访问 `a[1]`、`a[2]` 时，它们仍在同一页里，因此就会命中

当访问跨到下一页的 `a[3]` 或 `a[4]` 时，会再次 miss；随后同页访问又继续命中

所以，哪怕是第一次遍历数组，TLB 也能因为**空间局部性**获得不错的命中率：只要一页里有多个连续元素，那么通常只有每页第一次访问要付出 miss 成本

如果程序不久后再次访问同一数组，而且 TLB 容量足够保留这些映射，那么还会进一步享受到**时间局部性**带来的高命中率

#### 谁来处理 TLB 未命中

当 TLB miss 发生时，到底谁来负责把正确映射补进 TLB？有两种典型设计

第一种是**硬件管理 TLB**。硬件自己知道页表长什么样，也知道页表基址寄存器在哪里。miss 发生后，硬件自动去遍历页表，取出目标 PTE，更新 TLB，然后重新执行原指令

第二种是**软件管理 TLB**。这类系统里，硬件在 miss 时只做一件事：抛出一个异常，进入操作系统。然后由内核里的 TLB miss 处理程序负责：

- 查页表
- 构造映射
- 用特权指令写回 TLB
- 再从异常返回，重试原指令

软件管理方式的优点主要有两个：

- 更灵活，操作系统可以使用自己想要的页表结构
- 硬件更简单

但它也要求操作系统写得足够小心。例如，TLB miss 处理代码本身不能再轻易触发新的 TLB miss，否则很容易递归出问题。因此系统通常要么把这段处理代码放在不经过地址转换的物理内存中，要么在 TLB 中预留一些固定项，保证处理路径总能命中

#### TLB 的内容

TLB 本身通常是一个小而快的全相联缓存。典型大小可能只有：

- 32 项
- 64 项
- 128 项

每个 TLB 项最少包含：

- `VPN`
- `PFN`
- 一些控制位

控制位通常包括：

- 有效位
- 保护位
- 地址空间标识符 `ASID`
- 脏位
- 其他缓存一致性相关位

页表项里的有效位表示：**该虚拟页在这个进程地址空间中是否合法存在**

而 TLB 项里的有效位表示：**这条缓存项现在是否装着一条可用的转换映射**

两者概念相关，但层次不同，不能混淆

#### 上下文切换时对 TLB 的处理

TLB 是按进程地址空间缓存转换映射的，这就带来一个问题：上下文切换时，前一个进程的地址映射对下一个进程通常没有意义

如果不小心处理，会出现严重错误。例如：

- 进程 P1 的虚拟页 `10 -> 物理帧 100`
- 进程 P2 的虚拟页 `10 -> 物理帧 170`

如果硬件不区分它们，那么同一个 VPN `10` 就可能被错误翻译

最简单的解决方法是**上下文切换时直接清空 TLB**。这样新进程开始运行时，TLB 中不会残留旧映射

但这个办法有明显代价：每次切换后，新进程都得重新把热点映射慢慢填回 TLB，会增加大量 miss

更高效的办法是给 TLB 项加入 **ASID `Address Space Identifier`**。它相当于一个较短的进程标识符。这样即便两个进程拥有同样的 VPN，只要 ASID 不同，硬件也能区分开它们

因此有了 ASID 之后：

- TLB 不必每次切换都清空
- 不同进程的地址映射可以暂时共存在 TLB 里

这能显著减少上下文切换后的冷启动代价

另外，书里也提到一种特殊情况：两个不同进程可能把不同的 VPN 映射到同一个 PFN，例如共享代码页。这种共享在 TLB 中同样可以自然表示，只要 VPN、PFN、ASID 三者组合正确即可

#### TLB 替换策略

TLB 很小，因此新映射插入时必须决定淘汰谁

LRU 试图利用局部性，优先保留最近常用的映射。随机替换则实现极其简单，而且在某些特别糟糕的访问模式下，反而可能比看似更聪明的策略更稳，这一点和一般缓存系统是相通的，最终仍取决于局部性模式

#### 实际系统的 TLB 表项

书里最后以 MIPS R4000 为例，展示了真实 TLB 项比教学模型复杂得多

一个真实 TLB 项通常除了 `VPN` 和 `PFN` 之外，还包含：

- 有效位 `valid`
- 脏位 `dirty`
- 全局位 `global`
- ASID
- 一些缓存一致性控制位

例如：

- `global` 用来表示该映射是否对所有地址空间都共享
- `dirty` 用来表示页面是否被写过
- `ASID` 用来区分不同进程

MIPS 这类软件管理 TLB 的系统，还会提供一些专门的特权指令来操作 TLB，例如：

- 查某条映射是否存在
- 读取某条 TLB 项
- 覆盖某一项
- 随机替换某一项

### 分页：较小的表

分页解决了分段带来的外部碎片问题，但又引入了另一个很现实的成本：页表本身可能太大。线性页表最直接，也最好理解，但它把整个虚拟地址空间都一视同仁地展开成数组，即使大量虚拟页根本没被使用，也照样要给它们留页表项。

当简单的线性页表占用太多内存时，应该如何缩小它？核心思路是什么？这些节省空间的方法又会带来哪些额外的时间开销和复杂性？

#### 简单的解决方案：更大的页

原因很简单：页越大，虚拟页数就越少，页表项数量自然就越少。书里举的例子是：

- 32 位地址空间
- 原来页大小是 `4KB`
- 如果改成 `16KB`

那么页数会变成原来的四分之一，页表大小也就缩成四分之一

但问题同样明显：**页越大，内部碎片越严重**。程序往往并不会把每个大页都用满，于是页内部会出现更多浪费

因此，这个方案只是把问题从“页表过大”转移成了“页面过大”。现代系统通常仍然默认使用相对较小的页，例如 `4KB` 或 `8KB`，只在某些特殊场景下额外支持大页

大页真正常见的用途，往往不是为了节省页表空间，而是为了提高 TLB 覆盖范围，减少 TLB miss

#### 混合方法：分页和分段

既然线性页表的问题来自“整个地址空间都必须有页表项”，一个自然的想法就是：能不能把分页和分段结合起来，只给真正使用到的段建立页表？这就是一种分页和分段的混合方案

- 地址空间仍然分成代码段、堆段、栈段等逻辑段
- 但每个段内部再用分页管理
- 不再为整个进程维护一张统一的大页表
- 而是每个段维护自己的一张页表

这样做的好处是，像代码段和堆段之间那些根本没用到的大块区域，就不需要为它们分配页表项了

在这种设计里，段寄存器的角色也发生了变化：

- 基址寄存器不再指向段本身
- 而是指向“该段页表”的起始物理地址

界限寄存器则表示这个段页表中有多少有效页

因此，地址转换过程会变成：

1. 先根据虚拟地址高位判断是哪个段
2. 选中该段对应的页表基址/界限
3. 再在该段页表里索引对应页表项

这个方法确实能显著减少页表空间浪费，但它仍然继承了分段的一些问题：

- 依赖分段
- 对大而稀疏的堆支持仍然不理想
- 页表本身大小不固定，可能重新引入外部碎片

所以，这只是一个过渡性思路，而不是最终答案

#### 多级页表

更主流、也更有代表性的方案是**多级页表 `multi-level page table`**

它的核心思想是：

- 先把线性页表切成一页一页的小块
- 如果某整页页表项全是无效的，就根本不为它分配物理内存
- 再用一个额外的数据结构记录“哪些页表页存在，以及它们在哪里”

这个额外结构就是**页目录 `page directory`**

可以把多级页表理解成把原来“大而平的线性页表”，变成一棵树。树的上一层只记录“下一层页表页是否存在、存在的话在哪”；真正的页表项则放在下面那些只在需要时才分配的页表页中

这样一来，如果地址空间很稀疏，大量完全没用到的区域就不会占用页表内存

这正是多级页表最大的优点：

- 页表空间只和“实际用到的虚拟地址范围”相关
- 不再和“整个理论地址空间大小”成正比

书里给出的 16KB 地址空间例子很好说明了这一点。原本线性页表要完整地覆盖全部虚拟页，而在多级结构下，只需保留那些真的包含有效映射的页表页，再用页目录指过去即可

##### 两级页表怎么查

在一个简单的两级页表中，虚拟地址会被拆成几部分：

- 一部分索引页目录
- 一部分索引具体页表页
- 最后一部分作为页内偏移

因此，发生 TLB miss 后，地址转换大致分两步：

1. 先根据高位找到页目录项 `PDE`
2. 再根据中间位找到页表项 `PTE`
3. 最后拼出物理地址

也就是说，多级页表通过减少内存占用，换来了额外的一层甚至多层查找

##### 超过两级

如果地址空间很大，而页又比较小，那么“页目录本身”也可能太大。这时，解决办法只能继续递归，再给页目录本身加一层目录，于是就会有两级页表，三级页表，甚至更多层

本质上，这只是把“页表页不够小”的问题继续套娃处理。每多一层，就进一步压缩空闲区域的页表开销，但也让 TLB miss 后的查找过程变得更长

##### 多级页表的代价

多级页表是一个很典型的时间—空间折中

它的优点是：

- 更节省内存
- 更适合稀疏地址空间
- 页表各部分天然按页组织，更容易分配和管理

它的缺点是：

- TLB miss 时要做更多次内存访问
- 硬件或操作系统的页表遍历逻辑更复杂

所以，多级页表并不是绝对更好，而是在现实系统里，对页表太大问题的一个非常成功的折中

#### 反向页表

还有一种更激进的思路，叫**反向页表 `inverted page table`**

普通页表的规模是跟虚拟页数走的：每个虚拟页都可能有一个页表项。而反向页表反过来，不再按虚拟页组织，而是按**物理页帧**组织：

- 系统里每个物理页帧对应一个表项
- 表项记录：当前是哪个进程的哪个虚拟页映射到了这里

因此，它的大小和物理内存规模成正比，而不是和所有进程的虚拟地址空间规模成正比

这当然能极大节省空间，但代价也很直接：查找不再像线性页表那样简单按索引完成，而需要搜索“有没有某个表项刚好对应这个进程的这个虚拟页”。因此，通常需要配合散列表等结构加速查找

从这个角度看，反向页表再次说明了书里一直强调的一点：**页表只是数据结构**。数据结构的不同选择，就是在空间开销、查找速度、实现复杂度之间做不同折中

#### 将页表交换到磁盘

到这里，书里最后再放松一个假设：页表不一定永远都全部驻留在物理内存里

如果进程很多、地址空间很大，即使使用多级页表，页表本身仍可能很占空间。因此，某些系统会把页表也视为可以被换入换出的对象，把它们放进内核虚拟内存中，在必要时再交换到磁盘

这让页表管理进一步变复杂，因为：

- 你不只是要管理普通数据页的换入换出
- 还要处理“页表页自己不在内存里”的情况

不过，书里这里不展开细讲，因为完整理解它需要先掌握后面关于页换入换出和缺页处理的机制
