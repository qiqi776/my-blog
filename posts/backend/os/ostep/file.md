### 插叙：文件和目录

到这一部分为止，操作系统已经通过进程和地址空间分别虚拟化了 CPU 和内存。系统还需要处理另一类完全不同的资源：持久存储。和易失的内存不同，磁盘、SSD 这类设备在断电后仍然保留数据，因此操作系统必须提供一套稳定而统一的接口，让程序能够创建、访问、组织并长期保存这些数据

#### 文件和目录

存储虚拟化最核心的两个抽象是：

- 文件 `file`
- 目录 `directory`

文件可以理解为一个线性的字节数组，每个字节都可以被读取或写入。用户平时通过可读文件名访问文件，但文件系统内部还会给每个文件分配一个更底层的标识，通常叫 **inode 号**

目录也有自己的 inode 号，但目录存放的内容不是普通字节数据，而是一组映射关系：用户可读名称, inode号

例如，如果某个文件的可读名字是 `foo`，其 inode 号是 `10`，那么所在目录里就会有一项：

```text
("foo", "10")
```

目录中的条目既可以指向文件，也可以指向其他目录。因此，把目录嵌套到目录里之后，就形成了熟悉的目录树。这棵树从根目录 `/` 开始，并通过路径名逐层访问。例如，如果根目录下有目录 `foo`，目录 `foo` 里又有文件 `bar.txt`，那么这个文件的绝对路径就是：

```text
/foo/bar.txt
```

文件系统为系统里几乎所有持久对象提供了一套统一命名机制。命名在操作系统里非常重要，因为访问资源的第一步，永远是先能准确地找到并引用它

#### 文件系统接口

从用户程序视角看，文件系统接口主要围绕几类操作展开：

- 创建文件
- 打开并读写文件
- 改变当前文件偏移
- 强制刷盘
- 重命名
- 获取元数据
- 创建、读取和删除目录
- 创建链接
- 挂载文件系统

#### 创建文件

创建文件最常见的方式是调用 `open()` 并带上 `O_CREAT` 标志

```c
int fd = open("foo", O_CREAT | O_WRONLY | O_TRUNC);
```

这里几个标志的含义分别是：

- `O_CREAT`：如果文件不存在就创建它
- `O_WRONLY`：只写打开
- `O_TRUNC`：如果文件已存在，先截断为 0 字节

`open()` 最重要的返回值不是布尔值，而是一个 **文件描述符 `file descriptor`**。它是一个整数，由进程私有，用来表示“这个进程当前已经打开的某个文件对象”。后续的 `read()`、`write()`、`close()` 等操作，基本都围绕文件描述符展开

可以把文件描述符理解为：

- 一个不透明句柄
- 一种 capability
- 或者一个指向“打开文件对象”的引用

旧 UNIX 里还存在一个 `creat()` 调用：

```c
int fd = creat("foo");
```

它本质上相当于 `open(..., O_CREAT | O_WRONLY | O_TRUNC)`，现在大多只是历史遗留知识

#### 读写文件

一旦文件被打开，最基本的操作就是 `read()` 和 `write()`

例如，`cat foo` 在内部大致会做这些事：

1. `open("foo", O_RDONLY)`
2. `read()` 读取文件内容到用户缓冲区
3. `write(1, ...)` 把内容写到标准输出
4. `close()`

如果用 `strace` 观察，会看到类似这样的调用顺序：

```c
open("foo", O_RDONLY) = 3
read(3, "hello\n", 4096) = 6
write(1, "hello\n", 6) = 6
close(3) = 0
```

这里有几个需要注意的点

第一，进程默认已经打开了三个标准文件描述符：

- `0`：标准输入
- `1`：标准输出
- `2`：标准错误

所以第一次 `open()` 成功后，通常返回的是 `3`。

第二，`read()` 的三个关键参数分别是：

- 读哪个文件描述符
- 把数据放到哪里
- 最多读多少字节

第三，`write()` 并不一定是程序直接显式调用的。有些程序调用的是 `printf()` 之类的库函数，但库函数最后通常还是会落到 `write()` 系统调用上

#### 读取和写入，但不按顺序

到目前为止，读写都是顺序进行的。但很多程序并不会从文件头一路线性处理到文件尾，而是需要跳到某个偏移位置随机访问。这时候就要用 `lseek()`：

```c
off_t lseek(int fildes, off_t offset, int whence);
```

修改这个打开文件的**当前偏移量**。其中 `whence` 决定偏移基准：

- `SEEK_SET`：从文件开头算
- `SEEK_CUR`：从当前偏移位置算
- `SEEK_END`：从文件末尾算

操作系统会为每个“打开的文件对象”维护一个当前文件偏移。每次 `read()` 或 `write()` 成功后，这个偏移会自动向前推进；而 `lseek()` 则允许程序显式修改这个偏移

`lseek()` 不会触发磁盘物理寻道。它只是修改内核里记录的“下次从文件哪个偏移读写”的变量。真正的磁盘寻道只会在之后真的发起 I/O 且目标块不在当前磁道时发生

#### 用 fsync() 立即写入

默认情况下，`write()` 往往并不会立刻把数据写到磁盘。为了性能，文件系统通常会先把数据放进内核缓冲区，等稍后再异步刷盘，这意味着：

- `write()` 很快返回
- 但数据不一定已经真正落盘
- 如果系统在刷盘前崩溃，数据可能丢失

对很多应用来说，这种语义足够了；但数据库、编辑器、日志系统等经常需要更强保证。这时会用到：

```c
fsync(int fd)
```

调用 `fsync()` 后，文件系统会尽量把这个文件相关的脏数据真正写到持久存储，等写入完成后才返回。典型模式如下：

```c
int fd = open("foo", O_CREAT | O_WRONLY | O_TRUNC);
write(fd, buffer, size);
fsync(fd);
```

如果你新建了一个文件，有时光 `fsync()` 这个文件还不够，还需要 `fsync()` 它所在的目录。因为目录项本身也是元数据，如果目录更新没刷到磁盘，崩溃后文件可能依然“消失”

#### 文件重命名

给文件改名使用的是 `rename()`：

```c
rename(old, new)
```

它提供原子化的重命名语义，这也是很多编辑器和应用实现“原子更新文件”的关键技巧。典型流程是：

```c
int fd = open("foo.txt.tmp", O_WRONLY | O_CREAT | O_TRUNC);
write(fd, buffer, size);
fsync(fd);
close(fd);
rename("foo.txt.tmp", "foo.txt");
```

只有在新文件完整写好后，才一次性把它“切换”成正式文件名，从而避免把半写完的文件暴露给用户

#### 获取文件信息

除了文件内容本身，文件系统还维护大量元数据。获取这些元数据，可以用 `stat()` 或 `fstat()`。它们返回的信息包括：

- inode 号
- 文件大小
- 权限模式
- 硬链接数量
- 所有者和组
- 最后访问、修改、状态变更时间

这类信息通常保存在文件系统内部的 inode 结构中。可以把 inode 看成一个持久元数据对象，它描述了“这个文件是什么、归谁、占多少空间、数据块在哪”等信息

命令行里常用的 `stat file`，本质上就是在做这件事

#### 删除文件

删除文件表面看上去像“把文件删掉”，但 UNIX 里的真正系统调用却叫：

```c
unlink()
```

删除文件在 UNIX 里本质上不是“立即销毁数据”，而是取消一个名字到 inode 的链接。因为 UNIX 文件系统里，真正持有文件内容和元数据的是 inode，而目录只是在保存“名字 -> inode”的映射关系。所以，删除一个文件名，本质是把这条映射删掉，而不是直接把文件实体暴力抹掉

#### 创建目录

目录用 `mkdir()` 创建。和普通文件不同，目录内容不能随便直接写，因为目录的内部格式属于文件系统元数据，必须由文件系统自己维护

新建目录时，它看起来是“空的”，但实际上最少会包含两个特殊项：

- `.` 指向目录自身
- `..` 指向父目录

这两个特殊目录项解释了为什么很多目录遍历和路径解析逻辑能够自然地“回到上一级”

#### 读取目录

目录不能像普通文件那样随便按字节解析，通常要通过专门接口读取：

- `opendir()`
- `readdir()`
- `closedir()`

例如：

```c
DIR *dp = opendir(".");
struct dirent *d;
while ((d = readdir(dp)) != NULL) {
  printf("%d %s\n", (int)d->d_ino, d->d_name);
}
closedir(dp);
```

目录项 `dirent` 里最重要的信息通常有：

- `d_name` 文件名
- `d_ino` inode 号

目录读取本质上再次印证目录保存的核心就是名字到 inode 的映射。至于文件大小、时间戳、权限等更丰富信息，则需要进一步再调用 `stat()` 获取

#### 删除目录

删除目录使用 `rmdir()`。它和删普通文件最大的不同在于：目录必须是空的，才能删除。这里的“空”通常只允许剩下：

- `.`
- `..`

如果目录里还有别的文件或子目录，`rmdir()` 会失败。这也是为什么递归删除整棵目录树并不是一个简单系统调用，而通常需要上层程序例如 `rm -r` 自己遍历和处理

#### 硬链接

理解 `unlink()` 的最好方式，就是先理解硬链接 `hard link`。硬链接通过 `link()` 或命令行 `ln` 创建。它的本质不是复制文件，而是给**同一个 inode**再起一个新名字。

例如：

```text
ln file file2
```

做完之后 `file` 和 `file2` 是两个不同的目录项名称，但它们都指向同一个 inode，因此看到的是同一份文件内容

如果用 `ls -i` 查看，会发现它们的 inode 号相同

这就引出了链接计数 `link count` 的概念。inode 会记录当前有多少个目录项名字指向它。每创建一个硬链接，计数加一；每次 `unlink()` 删除一个名字，计数减一。只有当计数降到零时，文件系统才真正回收 inode 和数据块

#### 符号链接

硬链接有局限：

- 不能轻易给目录做硬链接
- 不能跨文件系统分区链接

于是 UNIX 又提供了符号链接 `symbolic link`，也叫软链接 `soft link`

```text
ln -s file file2
```

符号链接本身是一个**独立文件类型**，它里面保存的不是目标文件的数据内容，而是目标文件的路径名。因此：

- 它有自己的 inode
- 它的大小通常就是目标路径名字符串的长度
- 它依赖路径解析去找到真正目标

这也带来了一个后果：符号链接可能悬空。如果原文件被删掉，符号链接还在，但它指向的路径已经不存在了

这与硬链接不同。硬链接只要还有至少一个名字活着，inode 和数据就还活着

#### 创建并挂载文件系统

到目前为止讨论的是“文件系统内部如何组织文件和目录”。最后还有一个更大的问题：系统如何把多个不同的文件系统统一接到同一棵目录树上？

第一步是创建文件系统，通常使用 `mkfs` 工具。它会在某个设备或分区上写入一个空文件系统结构，例如：

- 超级块
- 根目录
- 其他基础元数据

第二步是挂载 `mount`。挂载的作用，就是把某个独立文件系统“粘贴”到现有目录树的某个挂载点上

例如，把 `/dev/sda1` 上的 `ext3` 文件系统挂到 `/home/users`：

```text
mount -t ext3 /dev/sda1 /home/users
```

挂载完成后，访问 `/home/users` 实际上就是在访问这个新文件系统的根目录。于是，不同来源的文件系统都能被统一组织进同一棵目录树里

这也是 UNIX 文件系统模型非常优雅的一点：不需要让用户在很多彼此分裂的命名空间里切换，所有内容都被收进一棵统一树中

从这个角度回看整章，会发现 UNIX 文件系统接口虽然看起来零散，实际上都在服务同一个统一模型：

- 文件是字节数组
- 目录是名称到 inode 的映射
- 链接决定名字和对象之间的关系
- 挂载把多个文件系统拼接成一棵全局命名树

理解了这个模型，后面再看 inode、目录实现、日志、崩溃一致性等更底层话题，就会清楚很多

### 文件系统实现

这一章开始正式讨论文件系统如何在磁盘上实现。书里选择了一个教学用的极简文件系统 `VSFS`，也就是 `Very Simple File System`。它并不追求现实系统的全部复杂性，而是用最少的结构把文件系统最核心的设计思路展示出来：磁盘上到底放了什么数据结构，系统调用又是如何一步步落到这些结构上的

#### 思考方式

理解文件系统，最好同时抓住两个方面

第一个方面是**数据结构**。也就是：文件系统在磁盘上放了哪些结构，它们长什么样，负责存什么信息

第二个方面是**访问方法**。也就是：上层发出的系统调用怎样映射到这些结构上，哪些结构会被读，哪些结构会被改，整个过程为什么快或为什么慢

这两个方面加起来，才构成对文件系统的完整心智模型。只背 API 或只记磁盘布局都不够，真正需要理解的是：

- 文件数据在哪里
- 元数据在哪里
- 空闲空间如何跟踪
- 路径名如何解析
- 一次简单操作为什么会触发这么多 I/O

这一章的 VSFS，就是用来建立这套心智模型的

#### 整体组织

VSFS 的第一步是假设磁盘被划分为固定大小的块。这里用的是典型的 `4KB` 块。因此，从文件系统角度看，一个磁盘分区就是：一串从 `0` 到 `N-1` 编号的大小为 `4KB` 的块。在这些块上，VSFS 需要放下几类不同的信息

第一类当然是**用户数据**，也就是文件内容本身。文件系统把存放文件数据块的区域称为**数据区域 `data region`**

第二类是**inode 表**。文件系统必须为每个文件记录元数据，例如文件大小、所属用户和权限、数据块位置、时间戳

这些信息保存在 inode 结构里，而 inode 表就是磁盘上的一个 inode 数组

第三类是**空闲空间管理结构**。文件系统必须知道哪些 inode 已被分配、哪些数据块已被分配

VSFS 用两个位图来做这件事：

- inode 位图
- 数据位图

最后还需要一个**超级块 `superblock`**，用来保存整个文件系统的全局信息，例如：

- inode 数量
- 数据块数量
- inode 表起始位置
- 文件系统类型标识

因此，VSFS 的磁盘布局大致就是：

```text
[ Superblock | inode bitmap | data bitmap | inode table | data region ]
```

挂载文件系统时，操作系统首先读取超级块，了解这块磁盘上的文件系统是什么样，然后才能正确解释后续所有结构

#### 文件组织：inode

inode 是文件系统最关键的结构之一。每个文件对应一个 inode，而每个 inode 都由一个 inode 号 `inumber` 隐式引用

inode 这个名字来自 `index node`。原因很简单：文件系统通常把所有 inode 放在一个数组里，而 inode 号就是这个数组的索引

给定一个 inode 号，VSFS 可以直接计算对应 inode 在磁盘上的位置。假设：

- 每个 inode 大小为 `256B`
- 块大小是 `4KB`

那么一个块里能放 `16` 个 inode。如果 inode 区一共有 `5` 个块，那就一共能放 `80` 个 inode。这个数字也意味着：这个文件系统最多只能同时拥有 `80` 个文件或目录对象

计算某个 inode 所在块的思路是：

```text
块号 = (inumber * sizeof(inode)) / blockSize
扇区号 = ((块号 * blockSize) + inodeStartAddr) / sectorSize
```

inode 里保存的内容大致包括：

- 文件类型
- 文件大小
- 权限信息
- 链接计数
- 时间信息
- 指向数据块的位置

其中最关键的一个设计问题是：**inode 如何记录文件数据块的位置**

最简单的做法是放一些**直接指针 `direct pointers`**，每个指针直接指向一个数据块。但直接指针数量有限，所以这种做法只能支持有限大小的文件

为了解决大文件问题，就会引入：

- 一级间接指针 `indirect pointer`
- 二级间接指针 `double indirect pointer`
- 三级间接指针 `triple indirect pointer`

一级间接指针不直接指向数据，而是指向一个“指针块”；这个块里又保存大量指向数据块的指针。二级和三级间接则继续多套一层

这种方法叫**多级索引 `multi-level index`**。它形成了一棵明显不平衡的树：

- 小文件直接由少量直接指针覆盖
- 大文件再逐步用间接块扩展

之所以这样设计，是因为文件系统工作负载有一个长期稳定的经验事实：**大多数文件都很小**。所以，把常见的小文件路径优化得更简单、更紧凑，是很合理的

书里还提到了另一类方案：用范围 `extent` 代替逐块指针。范围本质上是：

- 一个起始块地址
- 一个连续长度

这种方式元数据更紧凑，但要求文件块尽量连续分配。相比之下，基于指针的方法更灵活，但元数据更多

#### 目录组织

在 VSFS 里，目录本质上就是一种特殊文件。它的数据块里保存的不是普通用户数据，而是一组目录项：

```text
(名称, inode号)
```

一个简化的目录项布局可能包含：

- `inum`
- `reclen`
- `strlen`
- `name`

例如目录里可能有这些内容：

```text
5   4   2   .
2   4   3   ..
12  4   4   foo
13  4   4   bar
24  8   7   foobar
```

这里再次看到特殊项：

- `.`
- `..`

目录本身也有 inode，也会占用数据块；因此目录在本质上仍然服从“inode + 数据块”的统一模型。区别只是它的数据块格式不是任意字节流，而是文件名到 inode 号的映射表

这也解释了为什么路径解析本质上就是一层层查目录：

- 先读当前目录的 inode
- 再读该目录的数据块
- 在目录项里找下一级名字对应的 inode 号
- 重复直到找到目标文件

VSFS 用线性目录项列表实现目录，简单但效率一般。更复杂的文件系统会用树结构来提高大目录查找和插入效率

#### 空闲空间管理

文件系统必须始终知道哪些资源还没被用掉，否则就无法创建新文件或给文件分配新块

VSFS 用 inode 位图、数据位图管理空闲空间：

- `0` 表示空闲
- `1` 表示已占用

例如创建新文件时，文件系统会：

- 扫描 inode 位图
- 找一个空闲 inode
- 把对应位设成已使用

写入新数据块时，则同样要扫描并更新数据位图

位图并不是唯一方法。还可以用空闲链表、树结构等方式管理空闲空间。但位图有个很大的优势：直观、简单，而且很适合教学系统如 VSFS

书里还提到一个常见优化：**预分配 `pre-allocation`**。也就是说，当文件系统要给一个新文件分配块时，尽量一次找到一段连续空闲块，而不是一块一块零散找。这样可以提高后续顺序访问性能

#### 访问路径：读取和写入

到这里为止，我们已经知道磁盘上有什么结构。接下来要理解：一次系统调用到底会触发什么 I/O，这就是文件系统的访问路径问题

先看读文件。假设我们要打开并读取 `/foo/bar`，为了完成 `open("/foo/bar", O_RDONLY)`，文件系统必须一步步解析路径：

1. 从根目录开始，找到根目录的 inode，读根目录的数据块
2. 在里面找到 `foo` 对应的 inode 号并读取，读 `foo` 目录的数据块
3. 找到 `bar` 的 inode 号，并把 `bar` 的 inode 读入内存

只有做到这一步，文件系统才真正知道：

- 这是哪个文件
- 大小是多少
- 权限是否允许访问
- 数据块指针在哪里

这说明，单单一次 `open()`，就可能已经触发多次磁盘读取，而且路径越长，I/O 越多

文件真正开始 `read()` 之后，文件系统再根据 inode 找到对应数据块，把数据读出来，并更新访问时间等元数据

关闭文件则简单得多，通常主要是释放内存里的打开文件表项，不需要再做额外磁盘 I/O

写入更复杂。因为写一个新块时，不仅要写数据本身，还可能要先分配新块。因此一次写入常常意味着：

1. 读数据位图，更新数据位图并写回
2. 读 inode，更新 inode 并写回
3. 写真正的数据块

也就是说，一个逻辑 `write()` 可能引出多次物理 I/O

而创建文件就更贵。创建一个新文件至少可能涉及：

- 分配一个 inode，更新 inode 位图
- 初始化新 inode
- 在父目录里加入新的目录项
- 更新父目录 inode

如果目录本身还要扩容，那么又会引入更多 I/O

一次 `open()`、一次 `write()`、一次创建文件，背后都可能要碰很多分散在磁盘不同位置上的结构。文件系统设计的难点之一，就是如何把这些必需操作做得足够高效

#### 缓存和缓冲

如果每次 `open()`、`read()`、`write()` 都老老实实直接打到磁盘上，文件系统性能会非常差。因此，现代文件系统高度依赖内存中的缓存

最直接的用途就是缓存经常访问的：

- inode
- 目录块
- 数据块

例如，第一次打开一个深层路径文件时，可能真的要把根目录 inode、目录数据、子目录 inode 等一层层读出来；但后续再次打开同一路径上的文件，很多内容就可能已经在缓存里，磁盘 I/O 会显著减少

早期系统常用固定大小的缓存；现代系统更多采用统一页缓存 `unified page cache`，让文件系统页面和虚拟内存页面共享一套更灵活的内存管理机制

写入方面，缓存同样很重要，不过这里通常更准确地说是**写缓冲 `write buffering`**

- 可以把多个更新合并成批量写入
- 可以重排写入顺序，提高磁盘效率
- 某些短命写入甚至可以完全避免真正落盘

例如，一个文件被创建后马上删除，如果写入被适度延迟，系统甚至可能根本不必真的把这些中间状态写进磁盘

但写缓冲也意味着风险：如果系统在缓冲数据真正刷盘前崩溃，最近的修改可能丢失。对大多数应用，默认缓冲策略可以接受；但数据库等程序通常需要更强保证，于是它们会调用 `fsync()`、使用直接 I/O，甚至绕开普通文件系统接口，以确保关键数据按预期持久化

### 局部性和快速文件系统

这一章讨论为什么早期 UNIX 文件系统性能很差，以及 FFS，也就是快速文件系统 `Fast File System`，是如何通过“磁盘意识”设计把性能拉起来的。核心思想是：磁盘不是内存，访问代价高度依赖布局，因此文件系统必须认真考虑局部性

#### 问题：性能不佳

最早的 UNIX 文件系统结构很简单，大致就是：

- 一个超级块
- 一整片 inode 区
- 一整片数据区

这种布局功能上没有问题，能够支持文件和目录层次结构；但性能很差，而且随着时间推移会越来越差。书中引用的测量显示，老 UNIX 文件系统最后可能只能发挥磁盘总带宽的 `2%` 左右

第一，**缺乏局部性**。文件系统把磁盘当成随机访问内存使用，没有认真考虑磁盘寻道的高代价。于是：

- 一个文件的 inode 可能离数据块很远
- 读一个文件时先读 inode，再跳到数据块，容易产生长距离寻道

第二，**严重碎片化**。老文件系统使用简单空闲列表，空闲块随着文件删除和新建逐渐变得分散。这样新文件分配到的块往往不连续，逻辑上连续的文件被切得七零八落，顺序读写性能迅速恶化

例如，原本一片连续空间中如果删除几个中间文件，就会留下零散空洞。之后再分配一个较大的新文件，它只能被拆开填进这些洞里。结果就是：

- 逻辑上连续
- 物理上离散
- 顺序访问被迫夹杂额外寻道

第三，**块太小**。早期块大小是 `512B`。小块确实能减少内部碎片，但每块可能都要付一次定位代价，因此传输效率很差

这些问题加起来，导致老文件系统虽然接口正确，却完全没有围绕磁盘介质本身优化

#### FFS：磁盘意识是解决方案

伯克利的设计者提出 FFS 的核心思路就是：文件系统必须有“磁盘意识”。这意味着文件系统的内部布局和分配策略都要围绕磁盘特性设计，而不是把磁盘当作一块缓慢的随机访问内存

FFS 非常重要的一点是，它没有改变文件系统对外接口。变化的是内部实现。也就是说，FFS 保持了兼容性，却显著改变了磁盘上的组织方式和分配策略。这种做法对后来的文件系统影响极大：**接口稳定，内部持续演进**，几乎成了现代文件系统发展的标准路线

#### 组织结构：柱面组

FFS 的第一项关键改进，是把磁盘划分成若干分组，称为**柱面组 `cylinder group`**。现代文件系统里常见的块组 `block group`就是类似思想

柱面组的核心目的，是把“相关的东西”尽量放在一起，这样访问相关数据时就不需要跨越整块磁盘长距离寻道。一个柱面组内部通常包含：

- 超级块的副本
- inode 位图
- 数据位图
- 一组 inode
- 一组数据块

这种组织方式和 VSFS 最大的不同在于：VSFS 把 inode 区和数据区作为全局大块连续区域放置，而 FFS 则把这些结构分散复制到多个局部组里，这样做有几个好处

第一，局部性更强。一个目录、它的 inode、它的文件和这些文件的数据块，往往可以被安排在同一个柱面组中

第二，空闲空间管理更局部化。每个组自己有位图，文件系统更容易在局部范围内寻找可用 inode 和数据块

第三，可靠性更好。超级块不只保存一份，而是在多个柱面组里保留副本，这样即使局部损坏，文件系统仍有机会恢复挂载

#### 策略：如何分配文件和目录

有了柱面组，下一步的问题就是：文件系统怎么决定一个新目录或新文件该放进哪个组？

FFS 的总体原则是 **相关的东西放一起，不相关的东西分开**，实际就是局部性原则

对于目录，FFS 倾向于把新目录放到：

- 已分配目录较少的组
- 同时还有较多空闲 inode 的组

这样做是为了两件事：

- 把目录在全盘范围内分散开，避免热点过于集中
- 确保目录所在组后续还有足够空间容纳该目录下创建的文件

对于普通文件，FFS 有两个关键策略

第一，把文件的数据块尽量放在和它的 inode 同一个组里，从而减少 inode 到数据块之间的长距离寻道

第二，把同一目录下的文件尽量放在同一组里。这样，如果某个目录里的文件经常被一起访问，例如：

- 编译同一目录下的一组源文件
- 读取同一目录下的一组配置文件

那么这些访问就会从局部布局中受益

这些规则并不是通过复杂统计模型得出的，而更多是良好的经验判断。但这正是 FFS 的成功之处：它抓住了工作负载中最重要的局部性

#### 测量文件的局部性

书里专门分析了命名空间局部性，想看看 FFS 的假设是否真的合理

这里使用的“距离”概念是：两个连续打开的文件，在目录树里离得有多远。具体来说：

- 如果两次访问的是同一个文件，距离为 `0`
- 如果是同一目录下两个不同文件，距离为 `1`
- 如果要往目录树上走到共同祖先再分叉，距离就更大

测量结果显示：

- 相当一部分访问是同一个文件的重复访问
- 还有很大一部分访问发生在同一目录中的不同文件之间

这就证明**命名空间里的邻近性，往往和访问局部性相关**。也就是说，把同一目录下的文件放在磁盘上彼此靠近的位置，通常确实有意义

书里还发现，距离为 `2` 的访问也不少。例如：

- `proj/src/foo.c`
- `proj/obj/foo.o`

这两个文件不在同一目录，但共享较近的共同祖先目录。FFS 并没有显式针对这种模式优化，因此这里仍然会有一些额外寻道

这个结果也提醒我们：FFS 的策略是有效的，但并不是对所有局部性模式都完全捕获

#### 大文件例外

如果始终坚持“文件和 inode 同组、同目录文件同组”，那么大文件会带来新问题：它们可能把一个柱面组的大量空间吃光

- 后续真正相关的小文件没地方再放进这个组
- 原本为了局部性保留的空间被单个大文件破坏

因此，FFS 对大文件采用了例外策略。它不会把整个大文件全塞进一个组，而是：

- 前面一小段块和 inode 放在同一组
- 后面的较大部分按块段分布到其他组

保持前部访问的局部性的同时避免一个超大文件占满某个组。这当然会损失顺序访问性能，因为文件块跨组分散后，顺序读会遇到更多寻道。但如果每次跳转前能传输的数据足够多，这个寻道成本就可以被摊销

书里用一个简单估算说明了这一点。假设：

- 平均定位时间是 `10ms`
- 磁盘传输速度是 `40MB/s`

如果希望一半时间用于寻道、一半时间用于传输，那么一次寻道之间至少要传输大约 `409.6KB` 数据。传输的数据越多，寻道开销被摊薄得越明显

FFS 实际上采用了一种很简单的近似方法：

- 前若干直接块和 inode 同组
- 每个后续间接块所覆盖的数据段再放到别的组中

#### 关于 FFS 的其他几件事

除了柱面组和分配策略，FFS 还有几个重要改进

第一个是为小文件引入**子块 `sub-block`**。因为块大小变成 `4KB` 后，虽然顺序 I/O 更高效，但对很多只有 `2KB` 左右的小文件来说，内部碎片会变严重

FFS 的做法是：

- 大块仍然是 `4KB`
- 但允许以 `512B` 子块为单位分配给小文件

这样小文件就不会浪费整块空间。随着文件变大，文件系统再把这些子块整理进完整块中

第二个改进是对磁盘布局做了参数化优化。早期磁盘较“傻”，顺序读取连续逻辑块时，如果文件系统发下一个请求的速度稍慢一点，就可能错过紧接着转过来的下一个扇区，导致整圈旋转延迟

FFS 的解决办法是：在布局上故意跳过若干块，让下一块到来时机刚好匹配主机发请求的速度。这种做法叫参数化布局 `parameterization`

后来磁盘内部变聪明了，能自己读整条磁道到缓存里，于是文件系统不再需要操心这类极低层细节。但这个例子很典型：**当设备接口不够强时，系统软件就不得不自己补设备知识**

第三类改进属于可用性增强，而不只是性能优化，例如：

- 长文件名
- 符号链接
- 原子 `rename()`

这些特性不一定像柱面组那样“技术味很重”，但它们极大提升了文件系统的实用性和可部署性。FFS 的成功，不只是因为它更快，也因为它更好用
