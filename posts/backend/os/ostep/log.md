### 崩溃一致性与日志

前面几章里，文件系统已经有了 inode、目录、位图、数据块这些核心结构。问题在于，这些结构不是内存里的临时数据，而是要持久放在磁盘上的。一旦系统在更新过程中断电或崩溃，磁盘上就可能只留下“更新到一半”的状态，这就是崩溃一致性 `crash consistency`问题

和普通内存数据结构不同，磁盘更新不能假设“一组修改会同时完成”。文件系统往往必须把几个块分开写出，而系统可能恰好在任意两次写入之间崩溃。那么文件系统该如何把磁盘状态从一个一致状态安全地推进到下一个一致状态？

#### 一个追加写的例子

假设现在有一个很简单的文件系统，里面有：

- inode 位图
- 数据位图
- inode 表
- 数据块区域

某个文件当前只占用一个数据块，inode 大致如下：

```text
I[v1]
owner: remzi
permissions: read-write
size: 1
pointer[0]: 4
pointer[1]: null
pointer[2]: null
pointer[3]: null
```

现在用户做了一次典型的追加写：把一个新的 4KB 数据块追加到文件尾部。文件系统至少要更新 3 处磁盘状态：

- 新数据块 `Db`
- 数据位图 `B[v2]`，把新块标记为已分配
- inode `I[v2]`，把文件大小改为 2，并让第二个指针指向新块 5

更新后的 inode 变成：

```text
I[v2]
owner: remzi
permissions: read-write
size: 2
pointer[0]: 4
pointer[1]: 5
pointer[2]: null
pointer[3]: null
```

理想情况当然是这 3 个块一起“原子切换”到新状态。但真实磁盘不会替你完成这种高层原子性；它只会接收一个个独立的写请求

#### 为什么会出错

如果 3 次写入里只完成了其中一部分，问题就出现了：

- 只写入 `Db`：磁盘上多了一块没人引用的数据，从元数据看这次写入像没发生过
- 只写入 `I[v2]`：inode 指向了还没真正写好的块，读文件时可能读到垃圾；同时 inode 和位图也不一致
- 只写入 `B[v2]`：位图说块 5 已占用，但没有任何 inode 指向它，造成**空间泄漏**
- 写入 `I[v2]` 和 `B[v2]`，但没写 `Db`：元数据彼此一致，但文件内容是垃圾
- 写入 `I[v2]` 和 `Db`，但没写 `B[v2]`：文件内容在，位图却没记录，仍然不一致
- 写入 `B[v2]` 和 `Db`，但没写 `I[v2]`：块被占用，但没人知道它属于哪个文件

### 方案 1：`fsck`

早期文件系统的思路很直接：先允许不一致发生，等系统重启时再统一修

`fsck` 就是这种思路的代表。它在文件系统挂载前扫描整个磁盘，尽量把元数据修回一个自洽状态。常见工作包括：

- 检查超级块是否合理
- 扫描 inode、间接块等信息，重建正确的空闲块位图
- 检查 inode 的类型和字段是否损坏
- 重新计算每个 inode 的链接计数
- 处理重复块引用
- 清理越界或明显错误的块指针
- 检查目录项格式、`.` 和 `..`、层次结构是否合理
- 把没有目录引用的 inode 挪到 `lost+found`

`fsck` 能解决的是**元数据内部一致性**，但它并不能保证用户数据一定正确。例如前面那种“inode 和位图都对，但数据块里是垃圾”的情况，`fsck` 往往无能为力

它最大的问题是慢。明明可能只是在 3 个块的更新过程中崩溃了，恢复时却要扫描整个磁盘。磁盘越大，这种做法越难接受

### 方案 2：日志 `journaling`

比 `fsck` 更积极的办法，是在真正覆写文件系统之前，先把“我要做什么”写到一个专门区域里。这个想法来自数据库，叫**预写日志 `write-ahead logging`**；在文件系统里通常直接叫**日志 `journaling`**

核心思路很简单：

1. 先把即将发生的更新写入日志
2. 确认日志落盘
3. 再把这些更新写到它们的最终位置

这样，如果系统在中途崩溃，恢复程序只需要查看日志并重放已提交事务，而不用扫描整个磁盘

#### 数据日志 `data journaling`

最直接的版本是把**元数据和用户数据都写进日志**。对前面的追加写例子，一次事务大致包含：

- `TxB`：事务开始块，说明这是哪个事务、将更新哪些最终位置
- 日志中的块内容：`I[v2]`、`B[v2]`、`Db`
- `TxE`：事务提交块，表示事务完整落盘

这种把完整块内容直接写进日志的方式，可以理解为**物理日志 `physical logging`**

可以把协议理解为 4 步：

1. **日志写入**：把 `TxB` 和所有待更新内容写入日志
2. **日志提交**：最后写 `TxE`，事务才算真正提交
3. **加检查点 `checkpoint`**：把这些块拷贝到文件系统中的最终位置
4. **释放日志空间**：等检查点完成后，标记这段日志可以复用

恢复时的规则也很直接：

- 如果崩溃发生在 `TxE` 写入前，说明事务没提交，直接丢弃
- 如果 `TxE` 已写入，但检查点没做完，就从日志重放这笔事务

这是一种典型的**重做日志 `redo logging`**

#### 为什么提交块必须最后写

这里的问题是磁盘和 I/O 子系统会**重排序写入**。即便操作系统“一次发了 5 个块”，磁盘内部也可能先把 `TxE` 写上去，再慢慢写别的块。如果 `TxE` 先落盘，而事务内容里某个数据块还没真正写进日志，恢复程序会误以为“这是一个完整事务”，然后把不完整的数据重放到正式位置，结果反而把垃圾写进文件系统。所以日志协议必须强制一个顺序：

- 事务内容必须先稳定写到日志
- 之后才能写提交块 `TxE`

现代系统通常要借助刷盘、屏障 `barrier`、缓存同步等机制来实现这个顺序保证。提交块本身通常也会做成一个足够小、能够原子落盘的写入，这样恢复时只需要判断它是否真正存在即可

#### 批处理和循环日志

如果每次系统调用都单独生成一笔日志事务，写放大会很严重。实际文件系统通常会把一段时间内的多次修改缓冲在内存里，合并成一个较大的全局事务再提交，这样可以减少重复写

日志空间本身也是有限的，因此它通常被实现成**循环日志 `circular log`**。文件系统会在日志超级块中记录：

- 最旧的未检查点事务
- 最新写入的位置

一旦某个事务已经成功加检查点，就可以把那段日志标记为空闲，下次继续复用

#### 元数据日志 `metadata journaling`

完整数据日志的缺点也很明显：**数据被写了两遍**

- 第一次写进日志
- 第二次写到正式位置

而磁盘的大头流量往往正是用户数据。于是更常见的折中方案出现了：**只记录元数据，不记录普通文件数据**。Linux ext3 的 ordered 模式就是典型例子。这时协议变成：

1. 先把数据块 `Db` 写到它的最终位置
2. 再把元数据 `I[v2]`、`B[v2]` 写入日志
3. 写入提交块 `TxE`
4. 把元数据加检查点到正式位置
5. 释放日志空间

**先写被指向的对象，再写指针本身**，也就是说，必须先让数据块安全落盘，再让 inode 指向它。这样即使崩溃，inode 也不会指向垃圾数据

这就是为什么**有序元数据日志 `ordered journaling`**在现实里很常见：它保住了大部分性能，又避免了“元数据正确但指向垃圾”的严重问题。一些文件系统还提供 unordered 模式，依然保证元数据一致，但数据语义会更弱

#### 块复用为什么麻烦

日志还有一个容易踩坑的边角问题：**块复用**

比如某个目录块 `1000` 之前被记录进日志；后来这个目录被删除，块 `1000` 被释放；再后来，一个新文件正好复用了块 `1000` 作为自己的数据块。此时如果系统崩溃，恢复程序天真地重放老日志，就可能把“旧目录内容”重新写回块 `1000`，从而覆盖新文件的数据

ext3 为此引入了 **revoke record**。它的作用可以理解为一句话：**这个块过去虽然出现在旧事务里，但现在已经无效，恢复时不要再重放它**

### 其他方法

除了 `fsck` 和 journaling，文件系统还尝试过其他崩溃一致性方案

#### 软更新 `soft updates`

软更新不依赖单独的日志区域，而是通过极其仔细的写入排序规则，让磁盘上的结构始终不落入明显不一致的状态。它的优势是不用额外写整份日志；代价是实现复杂度很高，因为系统必须理解并维护各种元数据之间的依赖关系

#### 写时复制 `Copy-On-Write`

COW 的思路是：**永远不在原地覆写旧结构**。有更新时，直接把新版本写到磁盘的空闲位置，等整套新结构都准备好后，再原子地切换根指针。ZFS 等文件系统大量使用这一思路。它天然适合和快照等特性结合

#### 其他研究方向

书里还提到了一些更偏研究的方案：

- **基于反向指针的一致性 `BBC`**：给块增加反向指针，用于判断正向引用是否真的安全落盘
- **乐观崩溃一致性 `OCC`**：尽量少等待磁盘，通过校验和等手段在恢复时发现不一致并修正

它们的共同目标都一样：尽量少牺牲正常写入性能，同时在崩溃后还能快速、安全地恢复

### 日志结构文件系统 `LFS`

上一部分讨论的是：在原地更新文件系统时，如何靠 `fsck` 或 journaling 保住一致性。LFS 走的是另一条路：**既然随机写很贵，那就尽量不要原地覆写，而是把所有更新都整理成顺序写**。这套思路由 Berkeley 的 Rosenblum 和 Ousterhout 在 90 年代初系统化提出，名字就叫**日志结构文件系统 `Log-structured File System`**

#### 为什么会有 LFS

LFS 的出发点来自几个很实际的观察：

- 内存越来越大，更多读请求会被缓存命中，磁盘 I/O 越来越偏向写入
- 磁盘的顺序带宽增长很快，但寻道和旋转延迟改善很慢，随机 I/O 和顺序 I/O 的差距越来越大
- 传统文件系统在小文件创建、目录更新这类常见负载上会触发一串分散写入，吞吐并不理想
- 在 RAID-4/5 上，小写入还有额外放大问题，传统布局经常踩中最差路径

所以 LFS 想解决的核心问题是能不能把文件系统里的几乎所有写入，都变成大块的顺序写？

#### 核心思路：永远往空闲位置追加

LFS 的核心非常直接：

- 把数据块、inode、目录块、imap 等更新先缓冲在内存里
- 缓冲到足够多时，组成一个大块连续写入
- 始终写到磁盘的空闲区域
- 从不原地覆写旧版本

也就是说，LFS 不是“找到旧块然后改掉”，而是“把新版本整个追加到磁盘后面”。因此它天然带有很强的 **append-only** 和 **copy-on-write** 色彩

#### 只顺序还不够，还要足够大

LFS 很强调“段 `segment`”这个概念。**只按逻辑顺序写，并不自动等于高性能**

如果你在时刻 `T` 写一个块到地址 `A`，过一小会儿再写地址 `A+1`，磁盘也可能已经转过去了；第二次写依然要等一整圈旋转，性能还是差。所以真正高效的办法不是“零散地顺序写”，而是：

- 一次发出一大批连续写入
- 让定位成本被足够多的数据摊薄

LFS 用的就是经典的**写缓冲 `write buffering`**。它先在内存里积累修改，等够大了再一次性写出。这个“一次性写出的单位”就是段

#### 段要多大才合适

书里给了一个很实用的估算：如果磁盘定位时间是 `T_position`，峰值带宽是 `R_peak`，希望最终有效带宽达到峰值的 `F`，那么大概要缓冲：

```text
D = F / (1 - F) * R_peak * T_position
```

其中 `D` 是每次最好写出的数据量

举个例子：

- `T_position = 10ms`
- `R_peak = 100MB/s`
- 希望达到 `90%` 峰值带宽

那么大概需要：

```text
D = 0.9 / 0.1 * 100MB/s * 0.01s = 9MB
```

这说明 LFS 想跑得好，段通常不能太小。写得越大，就越接近磁盘的顺序带宽上限

#### 新问题：inode 到处移动，怎么找

传统 UNIX 文件系统里，inode 通常放在固定区域里，给定 inode 号后，很容易算出它在磁盘上的位置

但 LFS 恰恰相反：

- inode 会随着每次更新被写到新位置
- 旧版本不会被覆盖
- 最新 inode 可能散落在磁盘任意地方

这就引出了 LFS 最关键的数据结构之一：**inode map `imap`**

#### `imap`：给 inode 再加一层间接

`imap` 本质上就是一个映射表：

- 输入：inode 号
- 输出：这个 inode 最新版本所在的磁盘地址

于是，inode 可以自由迁移，目录里保存的 inode 号却不用跟着改。每次 inode 被写到新位置，只需要同步更新 `imap` 即可。这是一个非常典型的“加中间层解决问题”的例子。它的代价是多了一层查找；它的好处是让文件系统可以自由移动 inode，而不用沿着整个目录树级联修改

#### 检查点区域 `CR`

但 `imap` 本身也在不断变化，也会被写到新位置。那系统启动时怎么知道“最新的 imap 在哪里”？

LFS 的做法是再保留一个固定位置的数据结构：**检查点区域 `checkpoint region, CR`**。CR 存在磁盘上的固定位置，里面记录：

- 最新 `imap` 片段的位置
- 日志头尾等必要恢复信息

于是查找链条变成先读固定位置的 `CR`->找到最新 `imap`->找到目标 inode->找到数据块。这也是 LFS 启动和挂载时的起点

#### 读取文件时实际发生什么

如果内存里什么都没有，从磁盘读取一个文件大致会经历这几步：

1. 读取 `CR`，根据 `CR` 找到并加载 `imap`
2. 用 inode 号在 `imap` 中找到 inode 地址
3. 读取 inode，再根据 inode 的直接或间接指针读取数据块

也就是说，LFS 在读路径上并没有魔法。它只是比传统文件系统多了 `CR -> imap` 这一层定位。但如果 `imap` 常驻内存，这个额外成本在正常情况下并不大

#### 目录怎么处理

LFS 并没有发明一套全新的目录格式。目录仍然是：

- 文件名
- inode 号

的映射集合。

比如新建文件 `foo` 时，LFS 会顺序写出：

- 新文件的数据块
- 新文件的 inode
- 父目录更新后的数据块
- 父目录的新 inode
- 对应更新过的 `imap` 片段

这时 `imap` 的价值就更明显了。因为目录里存的是 inode 号，而不是 inode 的物理地址，所以 inode 移动并不会逼着父目录、祖先目录一路改上去。LFS 用 `imap` 避开了经典的**递归更新问题 `recursive update problem`**

#### 代价：旧版本会变成垃圾

LFS 通过“永不原地覆盖”换来了顺序写性能，但也引入了新的问题：**垃圾回收**

因为每次修改文件，新的数据块和 inode 都会被写到新位置，旧版本会留在磁盘上。它们可能是：

- 仍然有效的旧块
- 已经失效、再也不会被访问的垃圾块

如果一直不清理，磁盘迟早会被这些旧版本填满

#### 清理器 `cleaner`

LFS 的后台会运行一个清理器：

- 读入若干旧段
- 判断其中哪些块还活着
- 把活块重新整理到更少的新段里
- 释放原来的整段空间

这里按**段**清理非常关键。因为如果只零散回收单个块，磁盘上会形成很多碎洞，后续就很难再找到足够大的连续空闲空间，LFS 赖以生存的顺序写性能也会迅速塌掉

所以 cleaner 的本质不是简单“删垃圾”，而是：

- **压实活数据**
- **回收整段连续空间**

#### 怎么判断一个块还活着

给定某个旧段里的数据块，LFS 需要知道它现在是不是文件系统里的最新版本。为此，LFS 会在每个段前面保存**段摘要块 `segment summary block`**，记录每个块对应的：

- inode 号
- 文件内偏移

判断流程可以概括成：

1. 从段摘要里读出这个块属于哪个 inode、对应哪个逻辑偏移
2. 通过 `imap` 找到该 inode 的最新地址
3. 读取 inode，查看它在这个偏移上当前指向哪个磁盘地址
4. 如果还指向这个块，说明它是活的；否则它已经被新版本替代，是垃圾

伪代码就是：

```c
(N, T) = SegmentSummary[A];
inode = Read(imap[N]);
if (inode[T] == A)
    // live
else
    // garbage
```

LFS 还会配合版本号等技巧，尽量减少为判断死活而产生的额外 I/O

#### 策略问题：什么时候清，清哪些

机制只是第一步，真正难的是策略：

- 什么时候启动 cleaner
- 优先清理哪些段

最直观的时机包括：

- 周期性触发
- 系统空闲时触发
- 磁盘接近写满时触发

而“清哪些段”则更依赖经验。经典 LFS 论文里的一条思路是区分**热段**和**冷段**：

- 热段里的内容经常被覆盖，晚点清理更划算，因为过一阵可能会死掉更多块
- 冷段里的内容稳定，若其中混入少量垃圾，早点清理更容易回收出整段空间

这里没有绝对完美的策略，但冷热分离提供了一个相当实用的方向

#### 崩溃恢复

LFS 同样要处理崩溃一致性问题，只是方式和 journaling 不同，关键在于 `CR` 必须可靠更新。为此，LFS 通常维护两个 `CR`，放在磁盘固定位置并交替写入。更新时采用比较谨慎的协议：

- 先写头部，带时间戳
- 再写主体
- 最后写尾部，也带时间戳

如果系统在更新 `CR` 中途崩溃，重启后只要比较头尾时间戳是否一致，就能判断哪个 `CR` 是最后一个完整版本

但 `CR` 并不会每次写都同步更新，它可能每隔几十秒才落盘一次。这意味着只靠 `CR` 恢复，可能会丢掉最近几十秒的更新

因此 LFS 还会做一件事，叫**前滚 `roll forward`**：

- 从最后一个一致的 `CR` 出发
- 沿着日志尾部继续扫描后续段
- 如果发现其中包含有效的新更新，就把这些更新重新并入当前文件系统状态

可以把它理解为：`CR` 提供一个可靠但稍旧的恢复基点，roll-forward 尽量把基点之后已经落盘但还没进检查点的更新也捞回来

### 数据完整性与保护

现在我们来关注如何确保系统写进去的数据，和以后读出来的数据，真的是同一份内容？

#### 现代磁盘的故障模型已经变了

早期 RAID 设计里，大家经常假设磁盘符合 **fail-stop** 模型：

- 要么磁盘正常工作
- 要么整个磁盘彻底挂掉

这个模型很干净，也很适合做冗余恢复。但现代磁盘更麻烦，它们很多时候表现为 **fail-partial**：

- 磁盘大体上还活着
- 但某些块会变得不可读
- 或者更糟，磁盘会返回“看起来正常、其实是错的”数据

书里重点讨论了两类部分故障：

- **潜在扇区错误 `Latent-Sector Error, LSE`**：某些块已经坏了，读取时会明确报错
- **块讹误 `block corruption`**：块内容错了，但设备自己可能没检测出来，属于**无声故障 `silent fault`**

这两类问题都不算高频，但在大规模系统里已经足够常见。研究数据显示，在约 3 年、150 万块磁盘的观察中：

- 廉价盘出现过 LSE 的比例大约是 `9.4%`
- 高端盘出现过 LSE 的比例大约是 `1.4%`
- 廉价盘出现过块讹误的比例大约是 `0.5%`
- 高端盘出现过块讹误的比例大约是 `0.05%`

即便买更贵的盘，也只是把问题变少，而不是让问题消失

#### 先处理容易的：LSE

LSE 相对容易处理，因为它是**可检测的**。读取某个块时，磁盘会直接返回错误。这时存储系统只要利用已有的冗余副本恢复即可：

- 在镜像里读另一份副本
- 在 RAID-4/5 里利用其他数据块和奇偶校验块重建

所以 LSE 的关键不在“怎么发现”，而在“有没有足够的冗余帮你补回来”

这也是为什么后来的 RAID 设计会更在意重建期间再次出错的问题。比如 RAID-5 某块盘整盘失效后，系统需要读同一条带上的其他块来重建；如果这时其他盘上再碰到一个 LSE，重建就可能失败。于是一些系统会采用双校验之类的设计来提高容错上限

#### 更麻烦的是无声讹误

比 LSE 更危险的是块讹误，因为系统读到的数据“形式上正常”，却不一定是真的。这种问题可能来自：

- 磁盘介质或固件异常
- 控制器把块写到了错误位置
- 总线传输出错
- 设备报告写入完成，但数据其实没真正落盘

只靠“设备有没有报错”已经不够，系统必须自己想办法验证数据

#### 核心武器：校验和 `checksum`

现代存储系统最常见的做法是给每个块计算一个**校验和**。思路很简单：

- 写入块 `D` 时，先算出它的校验和 `C(D)`
- 把 `C(D)` 和块一起存起来
- 以后读取 `D` 时，再重新计算一遍当前数据的校验和
- 把“存储的校验和”和“现算的校验和”做比较

如果两者一致，数据大概率没坏；如果不一致，就说明块在某个环节被改坏了

注意这里并不存在“完美校验和”。因为你总是在用很短的摘要去概括很大的数据块，所以不同数据最终得到相同摘要的**碰撞 `collision`**始终可能存在。设计目标不是彻底杜绝碰撞，而是在合理成本下把碰撞概率压得足够低

#### 常见校验和函数

不同校验和的主要权衡在于两点：

- **强度**：多大程度上能发现错误
- **速度**：计算它要花多少 CPU

常见方案大致有这几类：

- **XOR 校验和**：实现简单、速度快，但对某些成对位翻转不敏感
- **加法校验和**：也很快，能发现很多变化，但对某些重排或位移不够强
- **Fletcher checksum**：比前两者更强，能检测单比特、双比特和大部分突发错误
- **CRC**：工程里很常见，本质是把整块数据当作一个大二进制数去做模运算，检测能力很强，也有成熟高效实现

这里没有免费的午餐。保护越强，通常计算成本越高

#### 校验和放在哪里

有了校验和之后，下一个问题是布局：**校验和怎么和数据一起存？**

最理想的方式是“每个块都带着自己的校验和”。如果硬件支持额外元数据区域，例如每个扇区除了数据还有几个字节可以存校验和

但如果磁盘只提供普通扇区，文件系统就得自己安排布局。一种常见办法是：

- 先放一组校验和块
- 再放对应的一组数据块

这种布局能工作，但更新代价更高。比如只改一个数据块时，系统还得顺带读取并更新它所在的校验和块，于是会多出额外 I/O

#### 读取时怎么使用校验和

读取块 `D` 时，可以把两份值区分成：

- **存储的校验和** `Cs(D)`
- **计算得到的校验和** `Cc(D)`

流程就是：

1. 读出块 `D`
2. 读出与之对应的 `Cs(D)`
3. 对当前读出的 `D` 重新计算 `Cc(D)`
4. 比较 `Cs(D)` 和 `Cc(D)`

如果：

- `Cs(D) == Cc(D)`：数据大概率可信
- `Cs(D) != Cc(D)`：数据出现讹误

一旦检测到讹误，恢复方式和 LSE 类似：

- 有冗余副本就尝试修复
- 没有冗余就只能报错

所以校验和解决的是**检测**问题，不会自动凭空创造出正确数据

#### 新问题 1：错误位置写入 `misdirected write`

基本校验和方案可以发现“块内容被改坏”，但它还挡不住一种特殊错误：**数据被完整地写到了错误的位置。**

例如，本来应该把块 `D_x` 写到地址 `x`，结果设备写到了地址 `y`。这时如果你只检查块内容本身：

- 数据内容看起来没坏
- 校验和也可能完全匹配

但它就是出现在不该出现的位置

解决办法是：**让校验和覆盖的不只是数据内容，还包括物理身份。** 比如把这些信息一起写下来：

- 校验和
- 磁盘号
- 块号或扇区偏移

这样，系统在读某个位置时，不只验证“数据内容对不对”，还验证“这份数据是不是本来就属于这里”。如果物理 ID 对不上，就能检测出 misdirected write

#### 新问题 2：丢失写入 `lost write`

还有一种更刁钻的故障叫 **lost write**：

- 上层收到了“写入完成”的通知
- 但数据实际上根本没真正持久化
- 磁盘里留下的仍然是旧块内容

这时，前面那些方案为什么不够？因为：

- 旧数据有旧校验和
- 旧数据所在的物理位置也是对的

也就是说，**“内容 + 位置”同时验证都可能通过**，但块其实没有更新成功。一种办法是 **write verify / read-after-write** 每次写完立刻再读回来验证。有效，但代价非常高，等于显著增加写入 I/O

更聪明的办法是在系统的其他层也保存校验和。书里举的例子是 ZFS：它会把子块的校验和存到上层元数据里，比如 inode 或间接块中。这样即使数据块本身还是旧内容，只要上层元数据已经更新，校验和就会对不上，于是可以发现 lost write

#### 磁盘擦净 `scrubbing`

如果校验和只在“用户正好读取这个块”时才检查，那很多冷数据可能几年都不会被验证一次。这显然不够安全。所以可靠存储系统通常会定期做 **scrub**：

- 顺序扫描整个磁盘或整个阵列
- 逐块读取
- 重新计算校验和
- 一旦发现某个副本损坏，就趁其他副本还好时修复它

scrub 的价值在于：**主动发现那些平时不会被访问的数据问题，避免等到所有副本都坏了才第一次暴露**

这也是为什么很多系统会把 scrub 安排成每天、每周，或者在空闲时间定期跑一次

#### 校验和的开销

校验和当然不是零成本，主要有两类开销

第一类是**空间开销**：

- 磁盘上要额外存校验和
- 某些场景下内存里也要临时或长期保留校验和

如果是每 `4KB` 数据配 `8B` 校验和，磁盘空间开销大约只有 `0.19%`，通常不算大

第二类是**时间开销**：

- 写入时要计算校验和
- 读取时要重新计算并比对
- 如果校验和和数据分开存，还会带来额外 I/O
- scrub 本身也会消耗后台带宽

因此，实际系统通常会做很多工程优化，比如把“数据拷贝”和“校验和计算”合并在一条流水线上执行，尽量摊薄 CPU 成本
