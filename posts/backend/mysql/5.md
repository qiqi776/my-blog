### 什么是锁

锁是数据库系统区别于文件系统的一个关键特性，锁机制用于管理对共享资源的并发访问。在 innodb 引擎中会在行级别上对表数据上锁，也会在数据库内部其他多个地方使用锁，和 Oracle 的锁实现非常类似，提供一致性的非锁定读、行级锁支持。行级锁没有相关额外开销，并可以同时得到并发性和一致性。各个引擎的锁实现不同，如 MyISAM 引擎是表锁设计，并发情况下读锁没有问题，写锁性能差一些。

### lock 与 latch

**latch**（闩锁）是轻量级的锁，要求锁定的时间必须非常短，否则性能差，在 innodb 中可分为**mutex**和**rwlock**，用来保证并发中临界资源的正确性，通常没有死锁检测的机制。

**lock**的对象是事务，用来锁定数据库中的对象，如表、页、行。一般对象仅在事务 commit 或 rollback 后释放。有死锁机制

#### 一致性非锁定读

Innodb 通过行多版本控制的方式来读取当前执行时间数据库中行的数据。在执行 select 时不加锁，如果读取的行正在被 delete 或者 update，innodb 不会等待行被释放，而是去读取该行的一个快照数据

**实现机制：MVCC+Undo Log**

undo 在事务中回滚数据，因此快照数据本身是没有额外开销的。另外读快照数据不需要上锁，大大提高了数据库的并发性。这是 Innodb 引擎的默认读取方式

但是在不同事务隔离级别下，读取的方式不同

快照数据其实就是当前行数据之前的历史记录，每行记录有多个快照数据，因此称之为多版本并发控制

**READ COMMITTED（读已提交） 和 REPEATABLE READ（可重复读，默认）：使用非锁定一致性读，但是对于快照数据定义，前者总是读取被锁定行的最新一份快照数据，后者总是读取事务开始时的行数据版本**

#### 一致性锁定读

某些情况用户需要显式地对读取操作进行加锁保证数据一致性

支持两种一致性锁定读操作：

1. SELECT...FOR UPDATE
2. SELECT...LOCK IN SHARE MODE

1 对读取的行记录加一个 X 锁，其他事务不能对已锁定的行加上任何锁

2 对读取的行记录加一个 S 锁，其他事务可以向被锁定的行加 S 锁，加 X 锁会被阻塞

#### 自增长与锁

你一定用过`AUTO_INCREMENT`。在单机单线程下它很简单，但在高并发下，如果有 1000 个线程同时插入数据，InnoDB 如何保证 ID 不重复且连续？

**为什么 ID 会不连续（出现空洞）？事务回滚**

- InnoDB 的自增计数器是在内存中的。
- 事务 A 申请了 ID=5，然后回滚了。
- 自增计数器**不会回退**（为了性能，也为了避免锁竞争）。
- 下一个事务 B 申请到的就是 ID=6。ID=5 就永远消失了。

这就涉及到了一个特殊的锁机制：**AUTO-INC Locking**。

另外 MyISAM 时表锁设计，自增长不需要考虑并发插入

在 Innodb 中自增长值的列必须是索引，同时必须是索引的第一个列，否则会抛出异常

InnoDB 强制规定：**子表的外键列，必须有索引。** 如果你没建，它会自动帮你建一个。

- **原因**： 如果子表的外键列没有索引，当你要在父表中删除一行数据（比如删除一个用户）时，为了检查“有没有订单关联这个用户”，InnoDB 就不得不对子表进行 **全表扫描 (Full Table Scan)**。
- 这将导致父表的删除操作极其缓慢，并且会锁住子表的大量数据。

#### 外键与锁

外键主要用于引用完整性的约束检查

InnoDB 强制规定：**子表的外键列，必须有索引。** 如果你没建，它会自动帮你建一个。

- **原因**： 如果子表的外键列没有索引，当你要在父表中删除一行数据（比如删除一个用户）时，为了检查“有没有订单关联这个用户”，InnoDB 就不得不对子表进行 **全表扫描 (Full Table Scan)**。
- 这将导致父表的删除操作极其缓慢，并且会锁住子表的大量数据。

假设你有两张表：

**父表**:`users (id, name)`

**子表**:`orders (id, user_id, amount)`，其中 `user_id` 是外键。

执行以下 SQL ：

```sql
INSERT INTO orders (id, user_id, amount) VALUES (100, 1, 50);
```

InnoDB 不仅要在 `orders` 表里写数据，它必须去 `users` 表里检查 `id=1` 是否存在。 **关键点来了**： 这种检查不仅仅是“读一下”，而是必须加锁！它会在父表 (`users`) 的 `id=1` 这行上加一个 **S 锁 (共享锁 / 读锁)**。

- **原因**： 必须保证在我插入订单的瞬间，这个用户不能被删掉。

这种隐形的 S 锁，非常容易导致死锁。

1. **事务 A (插入子表)**:`INSERT INTO orders ... VALUES (..., user_id=1)`。
   - _结果：_ 事务 A 持有 `users` 表 id=1 的 **S 锁**。
2. **事务 B (更新父表)**:`UPDATE users SET name='NewName' WHERE id=1`。
   - _结果：_ 事务 B 想要 `users` 表 id=1 的 **X 锁** (排他锁)。
   - _冲突：_ X 锁被 A 的 S 锁阻塞，B 进入等待。
3. **事务 A (继续操作)**: 如果事务 A 接着想 `UPDATE users WHERE id=1`...
   - _结果：_ A 想要升级自己的 S 锁为 X 锁。但发现 B 正在排队等 X 锁（或者已经有其他意向锁）。
   - **BOOM! 死锁发生。**

### 锁的算法

#### 行锁的 3 种算法

- Record Lock：单个行的锁，总是会去锁住索引记录，如果没有创建索引，会使用隐式的主键进行锁定
- Gap Lock：间隙锁，锁定一个范围（开区间），但不包括记录本身（解决了幻读）
- Next-Key Lock：Gap Lock+Record Lock，锁定一个范围，并且锁定记录本身（左开右闭，同样有 previous-key locking 技术左闭右开）

#### 解决 Phantom Problem（幻读）

**幻读**：同一事务连续执行两次相同的 SQL 结果却不同，第二次 SQL 可能会返回不存在的行。

**举例**：

| **时间轴** | **事务 A**                                                                            | **事务 B**                                                           | **结果**                         |
| :--------- | :------------------------------------------------------------------------------------ | :------------------------------------------------------------------- | :------------------------------- |
| **T1**     | `BEGIN;`                                                                              |                                                                      |                                  |
| **T2**     | `SELECT * FROM users WHERE age > 20;`<br>_(假设查到了 2 人：Alice(25), Bob(30))_      |                                                                      | A 以为只有 2 人                  |
| **T3**     |                                                                                       | `INSERT INTO users (name, age) VALUES ('Charlie', 22);`<br>`COMMIT;` | **B 成功插入了一个 age=22 的人** |
| **T4**     | `SELECT * FROM users WHERE age > 20;`<br>_(这次查到了 3 人：Alice, Bob, **Charlie**)_ |                                                                      | **Charlie 是哪来的？**           |

InnoDB 默认事务隔离级别是 RR（可重复读），在 SQL 标准下会发生幻读，但是 InnoDB 通过 **Next-key Lock** 在范围内加锁从而避免幻读（想要出现上述情况，得设置成 READ COMMITTED）。

同时该机制在应用层实现唯一性的检查。

两个事务（A 和 B）并发插入一个数据 `4`，为了防止重复，它们决定先查后插。

- A 查 `b=4`（假设不存在）。拿到了一把 **S 锁 (共享锁)**，这是一个 **Gap Lock (间隙锁)**。
- B 也查 `b=4`。**S 锁和 S 锁是兼容的！** 间隙锁也是兼容的！B 也拿到了这块地的 S 锁。
- A 想要写入数据。这需要升级为 **X 锁**。但发现 B 手里拿着 S 锁。A 被阻塞，只能等待 B 释放 S 锁。
- B 也想要写入数据，也需要升级为 X 锁。但发现 A 手里拿着 S 锁。B 被阻塞，只能等待 A 释放 S 锁。

**怎么解决？**
不要用 `LOCK IN SHARE MODE` (S 锁) 做检查。直接用 **`SELECT ... FOR UPDATE`** **(X 锁)** 或者利用数据库的 **唯一索引约束** 让数据库自己去报错，而不是在业务层手动 check。

### 锁问题

#### 脏读

- **脏页**：在缓冲池中已经被修改，但是没有刷新到磁盘中的页，但是日志都已经被写入重做日志文件。
- **脏数据**：事务对缓冲池中行记录的修改，并且没有被提交。
- 对于脏页的读取，是最终一致性，不影响数据库的可用性。
- 对于脏数据的读取，即为一个事务读取到另一个事务未提交的数据，违反了事务的隔离性。

- **脏读**：当前事务读取到另外事务未提交的数据。

上述例子中，事务隔离级别为 READ UNCOMMITTED（读未提交），所以会产生脏读（生产环境下不常出现，因为事务隔离级别基本是 RR）。

#### 不可重复读

- **定义**：一个事务内多次读取同一数据集合，因为另一事务的修改而导致的结果不同。
- **区别**：不可重复读和脏读的区别是：前者读到的是已提交的数据，后者读到的是未提交的数据。

和上一个例子的区别就是这里发生了提交。

不可重复读的问题是可接受的，因为读到的是已提交的数据。因此很多数据库事务默认隔离级别是 READ COMMITTED，允许不可重复读。

InnoDB 中通过 Next-key Lock 避免不可重复读。

#### 丢失更新

一个事务的更新操作会被另一个事务的更新操作所覆盖。

例如：T1 更新行记录 r 为 v1，T2 更新行记录为 v2，T1 提交，T2 提交。

但是数据库在任何隔离级别下，都不会导致理论意义上的丢失更新问题（因为锁）。

要避免丢失更新的发生，需要让事务变成串行化，而不是并行操作：

1. **数据库层面**：InnoDB 自动加了锁。多个事务都想修改同一行时，数据库会让后面的排队。**根本不可能**发生“两人同时写进去”的情况。
2. **业务层面**：先读出来余额 100，在内存里算 100-10，写回去 90。都读到了 100，算出了 90，最后余额变成 90。所以读的时候就告诉数据库要修改它 —— **`SELECT ... FOR UPDATE`**。

#### 阻塞

不同事务之间的锁需要等待彼此的释放。

- `innodb_lock_wait_timeout`（动态，可以在运行时调整）：负责控制等待的时间，默认 50 秒。
- `innodb_rollback_on_timeout`（静态，不能在启动时调整）：负责设定是否在等待超时时对进行中的事务进行回滚操作，默认关闭。

发生超时时，MySQL 会抛出 1205 错误。

默认 InnoDB 不会回滚超时引发的错误异常，大部分情况都不会对异常进行回滚（用户必须判断是否需要 commit 还是 rollback）。

### 死锁

#### 死锁的概念

死锁是指两个或以上的事务在执行过程中，因争夺锁资源而造成的一种相互等待的现象。

解决死锁最简单的方式是不要有等待，将任何等待都转化为回滚，并且事务重新开始，但是并发性能会下降。

最简单的一种方法是超时回滚，但是倘若超时的事务占比权重较大就不合适，所花时间就比较多。

除了超时机制，数据库普遍采用 **wait-for-graph（等待图）** 进行死锁检测，该方式保存两种信息：**锁的信息链表，事务等待链表**，构造出一张图，如果存在回路就代表有死锁，通常来说 InnoDB 会选择回滚 undo 量最小的事务。

该方法通常采用深度优先算法实现，用非递归方式实现。

#### 死锁概率

从纯概率论的角度，死锁概率极低。

假设数据库有 个事务同时在跑，每个事务操作 行数据，数据总量是 。且事务操作的数据占总数据的一小部分（）。

- 一个事务获得一把锁需要等待的概率是非常小的（因为数据总量 很大）。
- 死锁是“循环等待”（A 等 B，B 等 A），这意味着需要 **连续发生两次特定的等待**。
- 概率本身就很小的事件，还要连续发生两次，其概率就是“小概率的平方”，所以非常非常小。

**死锁概率公式 (仅作参考)**

- : 系统中事务的数量（并发度）
- : 每个事务操作的数据行数（事务长度）
- : 数据库总的数据行数（数据规模）

**影响死锁概率的三大因素**

1. 系统中事务的数量 (\*\*\*\*) 越多，死锁概率越大。
2. 每个事务操作的数量 (\*\*\*\*) 越多，死锁概率越大。事务要尽量短小。
3. 操作数据的集合 (\*\*\*\*) 越小，死锁概率越大。

### 锁升级

锁升级是指将当前锁的粒度降低，即将多个行锁升级为页锁，或者将页锁升级为表锁。锁是一种稀缺资源，锁升级可以避免开销

SQL Server 在 2005 之后支持了行锁，但是设计和 Innodb 完全不同，以下情况会发生锁升级

1. 由一个单独的 SQL 语句在一个对象上持有的锁的数量超过了阈值，默认这个阈值为 5000。如果是不同对象，不会发生锁升级
2. 所资源占用的内存超过了激活内存的 40%时就会发生锁升级

但是 InnoDB 中不存在锁升级问题，它是根据每个事务访问的每个页对锁进行管理的，采用内部维护一个位图的方式。因此不管一个事务锁住页中的多少记录，开销都是一致的
