# Monkey: 最优可导航键值存储

Niv Dayan Manos Athanassoulis Stratos Idreos 哈佛大学 {dayan, manos, stratos}@seas.harvard.edu

## 摘要

在本文中，我们表明基于LSM-tree的键值存储表现出查找成本、更新成本和主内存占用之间的内在权衡，然而所有现有设计在这些指标之间都呈现出次优且难以调优的权衡。我们将问题归结为这样一个事实：所有现代键值存储都次优地共同调优了合并策略、缓冲区大小以及每一层布隆过滤器的误报率。

我们提出了Monkey，一个基于LSM的键值存储，它在任何给定的主内存预算下，都能在更新成本和查找成本之间达成最优平衡。其关键在于，最坏情况下的查找成本与LSM树所有层级布隆过滤器误报率之和成正比。与为所有布隆过滤器分配固定每元素比特数的现有键值存储相反，Monkey在不同层级之间分配过滤器内存，以最小化这个总和。我们从理论上证明，Monkey降低了最坏情况查找I/O成本的渐近复杂度，并通过在LevelDB之上的实现进行了实证验证——随着数据量的增长，Monkey将查找延迟降低了\(50\% - 80\%\)（在我们实验的数据规模下）。此外，我们将LSM树设计空间映射到一个封闭形式的模型上，该模型能够共同调优合并策略、缓冲区大小和过滤器的误报率，以根据工作负载（查找和更新的比例）、数据集（条目数量和大小）以及底层硬件（可用主内存、磁盘与闪存），在查找成本、更新成本和/或主内存之间进行权衡。我们展示了如何使用该模型来回答"假设"类设计问题，即环境参数的变化如何影响性能，以及如何相应地调整各种LSM树设计元素。

## 1. 引言

**基于LSM的键值存储。** 现代持久化存储应用数据的键值存储通常使用日志结构合并树（LSM-tree）[27]作为其存储层。与涉及对持久存储进行原地更新的传统存储范式相比，LSM树执行非原地更新，从而实现了（1）高吞吐量的更新[29]和（2）良好的空间效率，因为数据被紧凑存储[14]（它们不需要在每个节点保留空闲空间以允许原地更新）。它们通过将所有更新缓存在主内存中，当缓冲区填满时将缓冲区刷新到磁盘作为一个排序运行，并将磁盘驻留运行组织成若干大小逐层递增的层级来实现这一点。为了限制查找为找到目标键而需要探测的运行数量，相似大小的运行（即同一层级）会被排序合并，并在当前层级填满时推送到下一个更深的层级。为了加速在实践中很常见的点查找[6]，每个运行在主内存中都有一个关联的布隆过滤器，它可以概率性地允许查找在目标键不在该运行时跳过该运行。此外，每个运行在主内存中有一组栅栏指针，将值映射到运行的磁盘页面（有效地为运行的每个页面维护最小-最大信息），从而允许查找以单次I/O搜索运行中的目标键。这种设计被广泛应用于现代键值存储中，包括Google的LevelDB [19]和BigTable [12]、Facebook的RocksDB [15]、Apache的Cassandra [21]、HBase [5]和Accumulo [3]、LinkedIn的Voldemort [25]、Amazon的Dynamo [13]、MongoDB的WiredTiger [34]，以及Yahoo的bLSM [29]和cLSM [18]。今天许多关系型存储也支持这种设计。例如，MySQL可以使用MyRocks [14]在RocksDB上运行，它通过为键添加前缀来指示其所属的表，并将SQL命令映射到RocksDB命令。此外，SQLite最近将其存储引擎从SQLite3中的B-tree更改为SQLite4中的LSM-tree，这意味着现在每个表都是一个LSM-tree [31]。

**问题：次优的设计调优。** 在本文中，我们深入研究了LSM树的设计空间，并表明基于LSM的键值存储在查找成本、更新成本和主内存占用之间表现出内在的权衡（正如[8, 7]中对各种数据结构的讨论）。现有系统在这些指标之间达成了次优的权衡。图1使用成本模型（稍后描述）和在其最新源代码和文档中找到的几个现有系统的默认配置设置来图形化地展示这一点。现有系统并没有沿着最优Pareto曲线进行调优——在给定的主内存预算下，超越该曲线就不可能在不损害更新成本的情况下改善查找成本，反之亦然。因此，它们无法在给定的主内存预算和应用工作负载下最大化吞吐量。

我们将问题归结为这样一个事实：所有基于LSM的键值存储都次优地共同调优了LSM树中的核心设计选择：合并策略、层级间的大小比、缓冲区大小以及布隆过滤器的误报率。

第一个问题是，现有设计为每个布隆过滤器分配相同的误报率（即每元素比特数），而不管其对应运行的大小。我们的见解是，整个LSM树上最坏情况点查找成本与所有过滤器误报率之和成正比。然而，为所有过滤器分配相等的误报率并不能最小化这个总和。原因在于，在所有运行中保持相同的误报率意味着较大的运行拥有按比例较大的布隆过滤器，而探测任何运行的I/O成本是相同的，无论其大小如何（因为每个运行都有主内存中的栅栏指针，允许直接访问相关的磁盘页面）。结果，最大层级的运行占据了分配给布隆过滤器的总体内存预算的大部分，却没有带来查找成本的显著降低。

第二个问题是，不同设计参数与性能之间的关系是非线性的，因此很难共同调优LSM树设计空间中的各种设计选项以优化性能。例如，可用的主内存预算不仅可以用于提高布隆过滤器精度，还可以用于增加LSM树缓冲区的大小（这意味着更好的查找性能，因为需要探测的层级更少，以及更好的更新性能，因为需要合并条目通过的层级更少）。然而，如何在这些结构之间分配固定的主内存预算以达到最佳平衡并不清楚。此外，可以通过改变层级间的大小比和切换合并策略（在leveling和tiering之间切换，分别支持每层一个运行与每层多个运行）来在查找成本和更新成本之间进行权衡。然而，鉴于设计空间的复杂性，预测给定变化将如何影响性能仍然很困难。

**解决方案：Monkey。** 在本文中，我们映射了LSM树的设计空间。这使我们能够（1）整体地调优关键设计参数，从而沿Pareto曲线实现性能（如图1所示），以及（2）准确地导航Pareto曲线，为给定应用找到最佳权衡。

我们引入了Monkey：最优可导航键值存储。Monkey通过一种新颖的解析解达到Pareto曲线，该解通过在主内存中分配布隆过滤器以最小化其误报率之和来最小化查找成本。其核心思想是将每个布隆过滤器的误报率设置为与其对应运行中的条目数成正比（这意味着较浅层级的误报率呈指数级递减）。直觉是，分配给较大运行布隆过滤器的任何给定数量的主内存，在降低其误报率（以节省I/O）方面只能带来相对较小的收益。相反，相同数量的内存在降低较小运行误报率方面可以产生更大的影响。我们从理论上证明，这种方式从最坏情况查找成本中削减了一个\(O(L)\)因子，其中\(L\)是LSM树的层级数。直觉是，各层级的误报率形成一个几何级数，其和收敛到一个与\(L\)无关的常数。层级数为\(O\log (\frac{NL}{M*{buffer}})\)，其中\(N\)是条目数，\(E\)是条目大小，\(M*{buffer}\)是缓冲区大小。这有两个重要好处：（1）查找成本随着条目数量和大小的增加而更好地扩展，以及（2）查找成本与缓冲区大小无关，从而消除了在过滤器和缓冲区之间分配主内存的争用。因此，Monkey扩展性更好且更易于调优。

Monkey的第二个关键点是导航Pareto曲线，以在给定的主内存预算和应用工作负载（查找与更新之比）下找到查找成本和更新成本之间的最优平衡。为此，我们映射了影响这种平衡的设计空间和环境参数，并将查找和更新的最坏情况成本表示为简洁的封闭形式表达式。虽然所有现有的主要键值存储实现都暴露了许多调优参数，但Monkey的新颖之处在于它允许以可预测的结果精确导航设计空间，使得设置或调整键值存储安装变得容易。

**贡献。** 总结来说，我们的贡献如下。

在第3节中，我们表明由LSM-tree支持的键值存储在查找成本、更新成本和主内存占用之间表现出可导航的权衡；然而，现有键值存储并未沿最优权衡曲线进行调优，因为它们没有在布隆过滤器和LSM树的缓冲区之间最优地分配主内存。在第4节中，我们介绍了Monkey，一种基于LSM树的键值存储，它通过在布隆过滤器之间分配主内存以最小化其误报率之和来优化查找成本。我们从理论上证明，Monkey的布隆过滤器调优（1）降低了查找成本的渐近复杂度，从而更好地扩展到大型数据集，并且（2）消除了查找成本对LSM树缓冲区大小的依赖，从而简化了系统调优。我们确定了决定最坏情况性能的调优和环境参数，并将最坏情况下的查找和更新成本建模为封闭形式表达式。我们展示了如何使用这些模型来找到整体调优方案，该方案（1）在具有任意查找/更新比的均匀随机工作负载下最大化吞吐量，以及（2）在任何其他工作负载下最大化吞吐量的下界。我们还展示了如何使用该模型来回答"假设"类设计和环境问题。例如，如果我们改变（i）主内存预算，（ii）工作负载中读和写的比例，（iii）数据条目的数量和/或大小，或（iv）底层存储介质（例如，闪存与磁盘），我们应该如何调整LSM树设计，以及对性能的影响是什么？在第5节中，我们通过在LevelDB之上实现Monkey，应用了广泛的应用程序查找模式（即，针对存在与不存在的键以及不同的时间局部性）进行评估。在这些实验中，Monkey将查找延迟提高了\(50\% - 80\%\)。

## 2. 背景

本节提供LSM树的必要背景知识。LSM树存储键值对。键标识应用程序的对象并允许检索其值。为了本文的讨论，键和值都存储在LSM树内部，尽管也可以将大值存储在LSM树外部，并使用附加到键上的定宽指针指向它们[26]。为便于呈现，本文中的所有图只显示键，但可以将其视为键值对。

**缓冲更新。** 图2展示了一个LSM树和本文中使用的术语列表。一个LSM树概念上由\(L\)层组成。第0层指内存中的缓冲区，其余层指二级存储中的数据。LSM树通过立即将更新存储在缓冲区（第0层）而无需访问二级存储来优化插入、更新和删除（此后统称为更新）（每个条目附加一个标志以指示是否为删除）。如果更新引用的键已经存在于缓冲区中，则原始条目被原地替换，只有最新的条目存活。

当缓冲区容量达到时，其条目按键排序为数组并刷新到二级存储的第1层。我们将此类数组称为运行。我们将分配给缓冲区的主内存位数记为\(M*{buffer}\)，并将其定义为\(M*{buffer} = P\cdot B\cdot E\)，其中\(B\)是一个磁盘页中能容纳的条目数，\(P\)是以磁盘页数计的分配给缓冲区的主内存量，\(E\)是数据条目的平均大小。例如，在LevelDB中，默认缓冲区大小为2 MB。

第1层及更高层的运行是不可变的。每一层\(i\)有一个容量阈值\(B\cdot P\cdot T^i\)个条目，其中\(T\)是一个调优参数，表示相邻层级容量之间的比例。因此，层级具有以因子\(T\)指数增长的容量。总层级数由公式1给出。

\[L = \left[\log_{T}\left(\frac{N\cdot E}{M_{buffer}}\cdot \frac{T - 1}{T}\right)\right] \quad (1)\]

大小比\(T\)有一个极限值\(T*{lim}\)，其中\(T*{lim} = \frac{N\cdot E}{M*{buffer}}\)。\(T\)的值可以设置在2到\(T*{lim}\)之间的任何位置。当\(T\)接近\(T\_{lim}\)时，层级数\(L\)接近1。

**合并操作。** 为了限制查找必须探测的运行数量，LSM树根据运行的大小将其组织在不同层级，并合并相似大小（即同一层级）的运行。有两种可能的合并策略：leveling和tiering [20]。前者更优化查找，后者更优化更新。使用leveling时，每一层\(i\)最多有一个运行，从第\(i - 1\)层移动到第\(i\)层的任何运行都会立即与第\(i\)层的运行（如果存在）进行排序合并。使用tiering时，第\(i\)层最多可以积累\(T\)个运行，此时这些运行被排序合并。本质区别在于，leveled LSM树更贪婪地合并运行，因此对查找必须探测的总运行数给出了更严格的界限，但这是以更高的摊销更新成本为代价的。图3比较了当大小比\(T\)设置为3时，tiering和leveling的合并操作行为。

如果多个正在排序合并的运行包含相同键的条目，则只保留最近创建（最年轻）运行中的条目，因为它是最新的。因此，结果运行可能小于原始运行的累计大小。当合并操作完成时，如果第\(i\)层已满，结果运行将移动到第\(i + 1\)层。

**查找。** 点查找从缓冲区开始，从最低层到最高层遍历层级（在tiering情况下，层内运行从最新到最旧）。当找到第一个匹配条目时终止。无需进一步查找，因为较旧运行中相同键的条目已被取代。零结果查找（即目标键不存在）可能产生较高的I/O成本，因为它探测所有层级中的所有运行。相比之下，范围查找需要对所有具有重叠键范围的运行进行排序合并，以识别并忽略被取代的条目。

**探测运行。** 在1996年的原始LSM树设计[27]中，每个运行都结构化为一个紧凑的B-tree。然而，在过去的二十年中，主内存变得便宜，因此现代设计只需在主内存中为每个运行的每个磁盘页面存储一个栅栏指针数组，包含最小/最大信息[15, 19]。维护平面数组结构要简单得多，并在内存中产生良好的搜索性能（二分查找，因为每个运行都已排序）。鉴于LSM树在磁盘上，这些内存中的二分查找不在性能的关键路径上（I/O才是）。因此，查找首先搜索栅栏指针。如果是点查找，则随后以一次I/O读取适当的磁盘页面，如果是范围查找，则从该页面开始扫描。

栅栏指针的大小是适中的。例如，对于16 KB磁盘页面和4字节指针，栅栏指针比原始数据大小小约4个数量级。正式地说，我们将栅栏指针占用的主内存量记为\(M*{pointers}\)，并在本文中假设\(M*{pointers}\)为\(O(\frac{N}{B})\)，从而保证点查找探测一个运行需要\(O(1)\)次磁盘I/O。

**布隆过滤器。** 为了加速点查询，每个运行在主内存中都有一个对应的布隆过滤器[10]。点查找在访问二级存储中的运行之前探测该运行的过滤器。如果过滤器返回阴性，则目标键不在该运行中，因此查找跳过访问该运行并节省一次I/O。如果过滤器返回阳性，则目标键可能存在于该运行中，因此查找以一次I/O的成本探测该运行。如果运行确实包含该键，则查找终止。否则，我们有一个"假阳性"，查找继续探测下一个运行。假阳性增加了查找的I/O成本。误报率（FPR）取决于（1）运行中的条目数，以及（2）分配给该运行过滤器的主内存位数。这种关系由以下方程捕捉[32]²。

\[FPR = e^{-\frac{bits}{entries}\ln (2)^2} \quad (2)\]

据我们所知，所有基于LSM树的键值存储在所有布隆过滤器中使用相同数量的每元素比特数。这意味着一个查找平均探测\(O(e^{-\frac{M*{filters}}{N}})\)个运行，其中\(M*{filters}\)是分配给过滤器的总主内存量。当\(M*{filters}\)趋近0或无穷时，项\(O(e^{-\frac{M*{filters}}{N}})\)分别趋近1或0。我们所知的所有实现默认对其布隆过滤器使用10 bits per entry [3, 4, 5, 15, 19, 29]。相应的误报率约为\(1\%\)。在这种调优下，平均条目大小为128字节（实践中典型[2]），布隆过滤器比原始数据大小小约2个数量级。

**成本分析。** 我们现在分析tiered和leveled LSM树更新和查找的最坏情况I/O成本复杂度。首先，我们解释如何衡量这些成本。对于更新，我们衡量摊销的最坏情况I/O成本，它考虑了一个条目被更新后参与合并操作的次数。对于查找，我们衡量平均最坏情况零结果I/O成本，即查找一个不在LSM树中的键所执行的预期I/O次数。我们关注零结果查找，因为（1）它们在实践中非常常见[11, 29]（例如，insert-if-not-exist查询[29]），以及（2）它们产生最大的纯I/O开销（即，未找到与查找相关的条目的读I/O）。在本文的其余部分，除非另有说明，我们使用"最坏情况查找和更新"这一术语时遵循这些定义。稍后我们还将建模非零结果查找和范围查找的最坏情况成本以作完整。

对于tiered LSM树，最坏情况查找成本为\(O(L \cdot T \cdot e^{-\frac{M*{filters}}{N}})\)次I/O，因为有\(O(L)\)层，每层\(O(T)\)个运行，由于栅栏指针，探测每个运行的成本为一次I/O，且平均只探测\(O(e^{-\frac{M*{filters}}{N}})\)个运行。最坏情况更新成本为\(O(\frac{L}{B})\)次I/O，因为每个条目参与\(O(L)\)次合并操作，即每层一次，而在合并操作期间复制一个条目的I/O成本为\(O(\frac{1}{B})\)，因为每次写I/O将\(O(B)\)个条目复制到新运行中。

对于leveled LSM树，最坏情况查找成本为\(O(L \cdot e^{-\frac{M*{filters}}{N}})\)次I/O，因为有\(O(L)\)层，每层有一个运行，由于栅栏指针，探测每个运行的成本为一次I/O，且平均探测\(O(e^{-\frac{M*{filters}}{N}})\)个运行。最坏情况更新成本为\(O(\frac{L}{B})\)，因为每个更新每层被复制\(O(T)\)次，总共通过\(O(L)\)层。

## 3. LSM树设计空间

问题是我们如何准确地导航这个设计空间，以及每个设计决策的确切影响是什么？为了接近这些问题的答案，我们继续更详细地讨论图4以及各种设计决策之间的争用。

**调优合并策略和大小比。** 关于设计空间的第一个见解是，当大小比\(T\)设置为2时，tiering和leveling的查找和更新成本复杂度变得相同。当我们分别增加tiering/leveling的\(T\)时，更新成本降低/增加，而查找成本增加/降低。为了生成图4，我们将合并策略和大小比的所有组合代入表中第2行和第3行的复杂度方程，并针对合并策略和大小比的相应值绘制点查找成本与更新成本的关系。我们没有按比例绘制曲线，实际上标记点更接近图的原点。然而，曲线的形状及其极限是准确的。虚线和实线分别对应使用tiering和leveling可访问的设计空间分区。当大小比\(T\)设置为2时，这些线相交，并随着\(T\)的增加在相反方向上分开更远。这表明tiering和leveling是导航同一权衡连续体的互补方法。

当大小比\(T\)接近其极限值\(T\_{lim}\)时，层级数\(L\)接近1。当\(L\)为1时，tiered LSM树退化为日志（图4左上），而leveled LSM树退化为排序数组（图4右下）。日志是更新友好的数据结构，而排序数组是读友好的数据结构。通过这种方式，LSM树可以在性能特性方面调优到这两个极端之间的任何位置。这是我们在本文中提出并大量利用的设计空间的一个特征。

**调优主内存分配。** 图4中曲线的极限由内存在过滤器\(M*{filters}\)和缓冲区\(M*{buffer}\)之间的分配决定。正确的内存分配至关重要。今天的主内存由DRAM芯片组成，其每比特价格比磁盘贵约2个数量级，并且这个比率作为行业趋势正在增加[24]。此外，DRAM在运行期间每比特功耗约是磁盘的4倍[33]。因此，布隆过滤器和缓冲区占用的主内存占系统（基础设施和运行）成本的很大一部分，应该被谨慎利用。

**设计空间争用。** 总体而言，我们识别出LSM树设计空间中的三个关键性能争用。

**争用1** 出现在如何将给定数量的主内存\(M*{filters}\)分配给不同布隆过滤器之间。通过将主内存从一个过滤器重新分配到另一个，我们分别降低和提高了前者和后者的误报率。我们如何最优地在不同布隆过滤器之间分配\(M*{filters}\)以最小化查找成本？

**争用2** 出现在如何将可用主内存在缓冲区和过滤器之间分配。如图4中的复杂度表所示，向缓冲区分配更多主内存一方面降低了查找成本和更新成本，但另一方面降低了布隆过滤器的精度从而增加了查找成本。我们如何达到最佳平衡？

**争用3** 出现在如何调优大小比和合并策略。这很复杂，因为工作负载由不同比例的（1）更新、（2）零结果查找、（3）非零结果查找和（4）不同选择性的范围查找组成。在tiering下减小大小比和在leveling下增大大小比会改善查找成本并降低更新成本，但对不同操作类型成本的影响和变化率是不同的。我们如何为特定应用工作负载找到最佳大小比和合并策略？

**现有技术。** 我们所知的所有基于LSM树的键值存储都应用了关于上述争用的静态且次优的决策。所有布隆过滤器调优相同，缓冲区大小相对于布隆过滤器大小是静态的，大小比和合并策略也是静态的[3, 4, 5, 15, 19, 29]。我们将这些存储统称为现有技术。尽管它们在各个方面有所不同（例如集中式与分布式架构、不同的一致性保证、不同的数据模型等），但这些设计方面与本文工作正交。在下一节中，我们将介绍Monkey，它通过解决这些争用并能够快速、准确且最优地导航LSM树设计空间，改进了现有技术。

## 4. MONKEY

在本节中，我们详细介绍Monkey。Monkey是一种基于LSM树的键值存储，其新颖之处在于能够达到并导航Pareto曲线，以在任何给定的主内存预算、工作负载和存储介质下找到查找成本和更新成本之间最佳可能的平衡。它针对均匀随机工作负载最大化吞吐量，并针对所有其他工作负载最大化吞吐量的下界。Monkey通过（1）解决LSM树设计空间中的争用，以及（2）使用模型在查找成本、更新成本和主内存占用之间进行最优权衡来实现这一点。下面我们在深入描述每个主要设计元素之前，先给出Monkey的主要设计元素和性能影响的高级总结。

**设计参数。** Monkey将影响最坏情况行为的设计元素转化为调优参数，并可以通过调整它们来改变其行为。这些参数包括：（1）层级间大小比\(T\)，（2）合并策略（leveling与tiering），（3）分配给不同层级布隆过滤器的误报率\(p*{1} \ldots p*{L}\)，以及（4）主内存\(M\)在缓冲区\(M*{buffer}\)和过滤器\(M*{filters}\)之间的分配。Monkey可以共同调优这些参数以优化吞吐量，或者根据应用需要（例如，对平均查找或更新延迟的约束）偏向于某一性能指标。图5显示了Monkey实现的性能效果。

**最小化查找成本。** Monkey的第一个核心设计元素是在布隆过滤器之间最优分配主内存以最小化查找成本。关键见解是查找成本与所有布隆过滤器误报率（FPR）之和成正比。在第4.1节中，我们展示了如何在不同层级之间不同地调优过滤器以最小化这个总和。图5（a）直观地显示了这一变化带来的影响。对于任何主内存预算，它都比现有技术实现了更快的读取，因此将整个权衡曲线垂直向下移动到Pareto曲线。

**性能预测。** Monkey的第二个设计元素是能够预测改变设计决策或环境参数将如何影响最坏情况性能。我们在第4.2节中通过推导查找和更新最坏情况I/O成本的封闭形式模型（用LSM树设计空间参数表示）来实现这一点。例如，这些模型预测改变主内存总量或其分配将如何重新定位Pareto曲线，如图5（b）所示。我们推导了一个类似的现有技术模型作为基线，并表明Monkey优于它。

**自动调优。** Monkey的第三个设计元素是能够进行整体自我调优以最大化最坏情况吞吐量。我们分两步实现这一点。首先，在第4.3节中，我们使用渐近分析来映射设计空间，从而制定一个如何在缓冲区和过滤器之间分配主内存的规则。其次，在第4.4节中，我们针对（1）查找成本和更新成本的模型，（2）工作负载中查找和更新的比例，以及（3）持久存储读写成本，对最坏情况吞吐量进行建模。我们引入了一种算法，该算法快速搜索Pareto曲线，找到最大化最坏情况吞吐量的查找成本和更新成本之间的平衡点。这一特性在图5（c）中直观地展示。

**使用Monkey。** 我们将Monkey作为一个键值存储来呈现。然而，我们的工作适用于任何会使用LSM树的应用程序（关于此的讨论见附录A）。

### 4.1 最小化查找成本

我们现在继续讨论Monkey如何最小化最坏情况查找成本。我们关注零结果查找，因为它们产生最高的纯I/O开销（即不执行有用工作的I/O），因此最小化其最坏情况成本可以实现稳健的性能，我们稍后在实验中表明，它还能显著改善其他情况下的性能（例如，非零结果查找和工作负载倾斜）。

图6给出了用于描述Monkey的术语列表。我们将\(R\)表示为零结果点查找的最坏情况预期I/O成本。我们首先证明\(R\)等于所有布隆过滤器误报率（FPR）之和。然后我们展示如何在不同层级之间调优布隆过滤器的FPR，以在总体主内存\(M\_{filters}\)的约束下最小化这个总和。我们在本节中假设条目大小\(E\)是固定的；在附录C中，我们给出了一个迭代优化算法，即使条目大小可变或随时间变化，也能快速找到最优的FPR分配。

**平均最坏情况查找成本建模。** 零结果查找探测的平均运行数（即期望值）是所有布隆过滤器FPR之和。公式3用分配给不同层级过滤器的FPR \(p_1, \ldots , p_L\)来表示这个总和。使用leveling时，每层最多有一个运行，因此\(R\)简单地等于所有层级FPR之和。使用tiering时，每层最多有\(T - 1\)个运行（当第\(T\)个运行从上一层到达时，触发合并操作并推送到下一层）。tiering中同一层级所有运行的FPR相同，因为它们大小相同。

\[R = \left\{ \begin{array}{ll}\sum*{i = 1}^{L}p_i, & \mathrm{使用~leveling}\\ (T - 1)\cdot \sum*{i = 1}^{L}p_i, & \mathrm{使用~tiering} \end{array} \right. \quad (3)\]

**主内存占用建模。** 我们现在用不同层级的FPR \(p_1, p_2, \ldots , p_L\)来建模布隆过滤器的总主内存占用。为此，我们首先将公式2重新排列为过滤器位数：bits = - entries \(\frac{\ln(FPR)}{\ln(2)^2}\)。这个方程适用于具有相同FPR的任意数量布隆过滤器的累计大小，因此我们可以将其直接应用于leveling（每层一个布隆过滤器）和tiering（每层\(T-1\)个布隆过滤器）。我们通过识别并代入每一层的条目数和FPR来实现。如图2所示，LSM树的最后一层最多有\(N \cdot \frac{T - 1}{T}\)个条目，一般来说，第\(i\)层最多有\(\frac{N}{T - i} \cdot \frac{T - 1}{T}\)个条目，因为较小的层级按因子\(T\)指数级地具有较小的容量。因此，第\(i\)层过滤器占用的主内存最多为\(\frac{N}{T - i} \cdot \frac{T - 1}{T} \cdot \frac{\ln(p_i)}{\ln(2)^2}\)比特。所有布隆过滤器累计分配的总主内存量是这个表达式在所有层级上的总和，如公式4所示。

\[M*{filters} = -\frac{N}{\ln(2)^2} \cdot \frac{T - 1}{T} \cdot \sum*{i = 1}^{L} \frac{\ln(p_i)}{T - i} \quad (4)\]

**使用Monkey最小化查找成本。** 使用公式3和4，我们可以计算任何FPR分配方案下的平均最坏情况查找成本\(R\)和主内存占用\(M*{filters}\)。为了相对于\(M*{filters}\)最小化\(R\)，我们首先为了便于呈现而处理对偶但等价的问题：找到在用户指定的\(R\)值下最小化\(M\_{filters}\)的最优FPR分配\(p_1, \ldots , p_L\)。这是一个多变量约束优化问题。在附录B中，我们通过应用拉格朗日乘数法于公式3和4来解决它。结果出现在leveled和tiered设计的公式5和6中³。

| Leveling                                                                                                                                                                                                         | Tiering                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| \(p*i = \begin{cases} 1, & \text{如果 } i > L*{filtered} \\ \frac{R-L*{filtered}}{T-1}, & \text{否则} \end{cases}\) 对于 \(0 < R \le L\) 且 \(1 \le i \le L\) 且 \(L*{filtered} = L-\max(0, \lceil R-1 \rceil)\) | \(p*i = \begin{cases} 1, & \text{如果 } i > L*{filtered} \\ \frac{R-L*{filtered}}{T-1}, & \text{否则} \end{cases}\) 对于 \(0 < R \le L\cdot(T-1)\) 且 \(1 \le i \le L\) 且 \(L*{filtered} = L-\max(0, \lceil R-1 \rceil)\) |

图6说明了Monkey如何使用公式5和6在不同层级之间最优地分配FPR。一般来说，第\(i\)层的最优FPR是第\(i-1\)层最优FPR的\(T\)倍。换句话说，第\(i\)层的最优FPR与第\(i\)层的元素数成正比。直觉是，探测任何运行的I/O成本是相同的，无论其大小如何（由于栅栏指针，我们只获取符合条件的磁盘页面），而在更深层级实现低FPR所需的主内存量显著更高，因为它们有指数级更多的条目。因此，最好为较小层级的过滤器设置相对更多的每元素比特数（即更低的FPR）。相比之下，现有的基于LSM的键值存储为所有不同层级的布隆过滤器分配相同的FPR。

我们将查找成本\(R\)设置得越高，布隆过滤器所需的主内存就越少。如图6所示，在Monkey中这通过以下机制实现：对于更高的\(R\)值，更多最深层的布隆过滤器因其最优FPR收敛到1而消失。我们将有过滤器和无过滤器的层级数分别记为\(L*{filtered}\)和\(L*{unfiltered}\)（注意\(L = L*{filtered} + L*{unfiltered}\)）。公式5和6经过调整，可以找到\(L*{filtered}\)和\(L*{unfiltered}\)之间的最优划分，并基于具有\(L*{filtered}\)层的较小版本问题，为最浅的\(L*{filtered}\)层规定FPR。

总之，对于给定的查找成本\(R\)，Monkey通过以下方式最小化布隆过滤器的内存占用：（1）找到应分配布隆过滤器的最优层级数\(L\_{filtered}\)，以及（2）将每一层的FPR设置为其容量的比例。通过这些步骤，它实现了图5（a）中所示的性能效果。

### 4.2 预测查找和更新成本

我们现在继续以能够准确预测各种设计决策影响的方式映射LSM树的设计空间。为此，我们使用Monkey设计空间中所有调优参数的封闭形式表达式来建模查找和更新成本。我们还从理论上证明Monkey优于现有设计。

**零结果查找成本（R）建模。** 为了推导Monkey中零结果查找成本\(R\)的封闭形式表达式，我们将最优误报率（公式5和6）代入公式4，简化并重新排列。完整推导见附录B.1，结果如公式7所示。该方程假设条目大小固定（我们在附录C中放宽此限制）。

\[\begin{array}{rl} & R = R*{filtered} + R*{unfiltered}\\ & \quad \left\{ \begin{array}{ll}T\frac{T}{T - 1}\cdot e^{-\frac{M*{filter}}{N}\ln (2)^2\cdot T^{L*{unfiltered}}} & \mathrm{使用~leveling}\\ T\frac{T}{T - 1}\cdot e^{-\frac{M*{filter}}{N}\ln (2)^2\cdot T^{L*{unfiltered}}} & \mathrm{使用~tiering} \end{array} \right.\\ & R*{unfiltered} = \left\{ \begin{array}{ll}L*{unfiltered}, & \mathrm{使用~leveling}\\ L\_{unfiltered}\cdot (T - 1), & \mathrm{使用~tiering} \end{array} \right. \end{array} \quad (7)\]

为了解析公式7，注意加性项\(R*{filtered}\)和\(R*{unfiltered}\)分别对应于有过滤器和无过滤器层级中探测的平均运行数。还要注意，当大小比\(T\)设置为2时，tiering和leveling行为相同，因此方程的两个版本产生相同的结果。

\[L*{unfiltered} = \left\{ \begin{array}{ll}0, & M*{threshold}\leq M*{filters}\\ \left[\log*{T}\left(\frac{M*{threshold}}{M*{filters}}\right)\right], & \frac{M*{threshold}}{T}\leq M*{filters}\leq M*{threshold}\\ L, & 0\leq M*{filters}\leq \frac{M*{threshold}}{T}\\ M*{threshold} = \frac{N}{\ln(2)^2}\cdot \frac{\ln(T)}{(T - 1)} \end{array} \right. \quad (8)\]

接下来，我们推导公式8，它给出没有过滤器的更深层级的数量。为此，我们首先推导最后一层（即第\(L\)层）过滤器FPR收敛到1时的内存阈值\(M*{threshold}\)（见公式8底部）。最优的\(L*{unfiltered}\)值由公式8给出，可以代入公式7计算\(R\)。

**最坏情况非零结果查找成本（V）建模。** 使用平均最坏情况零结果查找成本\(R\)（公式7），我们现在也可以建模非零结果查找的平均最坏情况成本\(V\)，它找到最旧运行中的目标键。为了建模此成本，我们减去\(p_L\)（最旧运行过滤器的FPR），并加上1以考虑读取该运行的一个页面。

\[V = R - p_L + 1 \quad (9)\]

**最坏情况更新成本（W）建模。** 为了建模最坏情况更新成本，我们假设最坏情况更新模式：一个条目在\(N\)次应用写入的周期内最多被更新一次。因此，在条目被合并到最大层级之前，没有条目被消除。使用算术级数，我们建模每个条目每层参与的摊销最坏情况合并操作次数约为\(\frac{T - 1}{T}\)（tiering）和\(\frac{T - 1}{T}\)（leveling）。我们将其乘以\(L\)，因为每个条目通过\(L\)层，并除以\(B\)，因为每次写I/O将\(B\)个条目从原始运行移动到结果运行。最后，我们考虑读取原始运行以进行合并，以及对于某些存储设备（例如闪存），写入二级存储的写I/O比读取更昂贵，因此乘以\((1 + \phi)\)，其中\(\phi\)是写入和读取之间的成本比。总I/O成本由公式10捕捉。当\(T\)设置为2时，tiering和leveling行为相同，因此方程的两部分产生相同的结果。

\[W = \left\{ \begin{array}{ll}\frac{L}{B}\cdot \frac{(T - 1)}{2}\cdot (1 + \phi), & \mathrm{使用~leveling}\\ \frac{L}{B}\cdot \frac{(T - 1)}{2}\cdot (1 + \phi), & \mathrm{使用~tiering} \end{array} \right. \quad (10)\]

**最坏情况范围查找成本（Q）建模。** 范围查找涉及\(L\)次（leveling）或\(L\cdot (T - 1)\)次（tiering）磁盘寻道（每个运行一次）。每次寻道后跟一个顺序扫描。所有运行上扫描的累计页面数为\(s\cdot \frac{N}{B}\)，其中\(s\)是范围查找平均包含的所有条目的比例。因此，总范围查找成本\(Q\)（以页面读取计）如下。

\[Q = \left\{ \begin{array}{ll}s\cdot \frac{N}{B} +L, & \mathrm{使用~leveling}\\ s\cdot \frac{N}{B} +L\cdot (T - 1), & \mathrm{使用~tiering} \end{array} \right. \quad (11)\]

**现有技术建模。** 我们现在为现有的现有技术设计推导一个类似的模型。\(V\)、\(W\)和\(Q\)的模型与Monkey相同，即公式9、10和11，因为Monkey的核心设计不改变这些操作。为了建模最坏情况预期点查找I/O成本，我们将公式3中的所有误报率\(p_1,p_2\dots p_L\)设置为彼此相等。完整推导和最终的封闭形式公式26见附录E。

**Monkey优于现有设计。** 我们现在有了Monkey（公式7和8）和现有技术（公式26）的查找成本模型。在图7中，我们通过使用这些方程改变\(M*{filters}\)来比较Monkey与现有技术的零结果查找成本。尽管我们保持图中的项为一般形式，但曲线是针对具有512 TB数据的LSM树绘制的；条目数\(N\)为\(2^{35}\)，条目大小\(E\)为16字节，大小比\(T\)为4，缓冲区大小\(B\cdot P\cdot E\)为2 MB，并且我们将\(M*{filters}\)从0变化到35 GB。

Monkey在分配给过滤器的任何总主内存量下，在查找成本方面都优于现有技术。原因是它最优地将此内存分配给布隆过滤器，以最小化每次查找的平均读取I/O数。

如图7所示，当\(M\_{filters}\)趋近0时，Monkey和现有技术都退化为没有布隆过滤器的LSM树，因此它们的曲线汇合。图中的术语\(X\)用于调整leveling和tiering的项。两条曲线看起来相同，只是tiering的曲线在垂直方向上拉伸了\(T - 1\)倍，因为每层有\(T - 1\)个更多的运行。

### 4.3 可扩展性和可调优性

我们现在继续使用渐近分析来探索和映射Monkey的设计空间。我们表明，Monkey中的查找成本在数据量方面的扩展性优于现有技术。我们还表明，Monkey消除了查找成本对缓冲区大小的依赖，从而简化了调优。

**复杂度分析。** 在表1中，我们使用大O符号表示最坏情况查找成本和更新成本的模型。我们通过对Monkey中\(R\)的公式7和8、现有技术中查找成本的公式26以及两者中更新成本的公式10应用标准简化规则来实现。

Monkey中最坏情况查找成本的复杂度根据\(M*{filters}\)是大于还是小于\(M*{threshold}\)而有所不同。要理解原因，回想公式7中的\(R\)表示为两个加性项\(R*{filtered}\)和\(R*{unfiltered}\)之和。只要\(M*{filters} > M*{threshold}\)，所有层级都有过滤器，因此\(R*{unfiltered}\)为零，\(R*{filtered}\)是主导项。此外，通过将\(M*{threshold}\)代入公式7中的\(M*{filters}\)，我们观察到\(R*{filtered}\)的值最多为leveling的\(O(1)\)和tiering的\(O(T)\)。然而，随着条目数\(N\)相对于\(M*{filters}\)增加，最终\(M*{filters}\)降到\(M*{threshold}\)以下。此时\(R*{unfiltered}\)变为非零并开始主导\(R*{filtered}\)，因为当\(M*{filters} = M*{threshold}\)时其值至少为leveling的\(O(1)\)和tiering的\(O(T)\)，并且随着\(N\)的增加增加到leveling的\(O(L)\)和tiering的\(O(L \cdot T)\)。因此，当\(M*{filters} > M*{threshold}\)时，最坏情况查找成本\(R\)的复杂度为\(O(R*{filtered})\)，否则为\(O(R*{unfiltered})\)。

条件\(M*{filters} > M*{threshold}\)等价于每元素比特数\(\frac{M*{filters}}{N} > \frac{\ln(T)}{\ln(2)^2} \cdot \frac{\ln(T)}{T - 1}\)。\(\frac{1}{\ln(2)^2} \cdot \frac{\ln(T)}{T - 1}\)的值在\(T\)等于2时最多为1.44。因此，我们可以更具体地说，当每元素比特数高于1.44时，最坏情况查找成本\(R\)的复杂度为\(O(R*{filtered})\)，否则为\(O(R*{unfiltered})\)。在现代键值存储中，每元素比特数通常为10，远高于1.44，因此在大多数实际情况下，Monkey的复杂度为\(O(R*{filtered})\)。

为了进行同类比较，我们还分别针对\(M*{filters}\)低于和高于\(M*{threshold}\)的情况，用大O符号表示现有技术查找成本的复杂度（表1中的列\(b\)和\(c\)）。我们观察到，当\(M*{filters}\)低于\(M*{threshold}\)时，查找成本的复杂度收敛到没有过滤器的LSM树的复杂度。

**Monkey与现有技术的比较。** 我们首先在\(M*{filters} \geq M*{threshold}\)时比较Monkey与现有技术（表1中的列\(c\)和\(e\)）。对于tiering和leveling，Monkey从查找成本的复杂度中削减了一个\(O(L)\)因子（表1中的第2行和第3行）。注意，我们按照公式1将表1中的\(O(L)\)表示为\(O(\log*{T}(\frac{N \cdot E}{M*{threshold}}))\)。换句话说，Monkey中的查找成本\(R\)在渐近意义上与LSM树的层级数\(L\)无关。直觉是，较小层级的FPR呈指数级递减，因此探测各层级过滤器的预期成本收敛到一个乘法常数。从查找成本中削减一个\(O(L)\)因子有三个重要好处。

1. 只要我们随着数据条目数的增加而扩展布隆过滤器的占用（即保持比率\(\frac{M\_{filters}}{N}\)固定），Monkey中的查找成本保持不变，而现有技术中以对数速率增加。通过这种方式，随着条目数的增加，Monkey以越来越大的优势优于现有技术。

2. 查找成本与条目大小无关，因此对于具有较大条目大小的数据集不会增加。

3. 查找成本与缓冲区大小无关。这相对于现有技术简化了调优，因为我们不需要仔细平衡缓冲区和过滤器之间的主内存分配来优化查找性能。

接下来，我们在\(M*{filters} \leq M*{threshold}\)时比较Monkey与现有技术。在现有技术中（表1第2行和第3行列\(b\)），查找成本随着\(M*{buffer}\)的增加以对数速率降低，因为它吸收了更多较小层级。在Monkey中（表1第2行和第3行列\(d\)），查找成本随着\(M*{filters}\)的增加以对数速率降低，因为更多更深层级有布隆过滤器。Monkey通过从查找成本中削减一个加性因子\(O(\log\_{T}(E))\)（其中\(E\)是条目大小）来改进现有技术。原因是布隆过滤器只对条目数敏感，而不是它们的大小。这意味着Monkey中的查找成本对于具有较大条目的数据集不会增加。

Monkey在所有数据集和调优下都优于现有技术，因为它最优地在布隆过滤器之间分配主内存，从而最小化查找成本。

**探索极限行为。** 我们现在关注查找成本相对于大小比的极限行为。这显示在表1的第1行和第4行。我们也绘制了图8来帮助讨论。图8是第2节中图4的扩展，我们在其中映射了LSM树设计空间对查找和更新成本的影响。图4除现有技术外还包括Monkey。随着\(T\)接近其对leveling和tiering的极限值\(T*{lim}\)，层级数\(L\)接近1。当\(T = T*{lim}\)时，Monkey和现有技术在tiering和leveling下分别退化为日志和排序数组，因此它们的性能特征收敛。对于所有其他介于中间的\(T\)值，Monkey通过降低查找成本优于现有技术，从而达到Pareto曲线。

**分析主内存分配。** 我们现在分析在过滤器和缓冲区之间分配主内存对查找和更新成本的影响。在图9中，我们绘制了Monkey和现有技术中随着缓冲区和过滤器相对大小变化的查找成本和更新成本。我们将除了栅栏指针外要在栅栏指针和缓冲区之间分配的主内存量定义为\(\hat{M}\)比特，因此\(\hat{M} = M*{buffer} + M*{filters}\)。在x轴（对数刻度）上，我们将\(M*{buffer}\)从1个磁盘页面\((B \cdot E\)比特)增加到\(\hat{M}\)比特，以牺牲\(M*{filters}\)为代价，此时布隆过滤器消失（即\(M\_{filters} = 0\)）。虽然图中的项是通用的，但曲线是使用第4.2小节中的模型为小节末尾概述的配置绘制的。术语\(X\)用于调整leveling和tiering的y轴。

图9的顶部显示，在现有技术中，布隆过滤器在空间的重要部分实际上损害了查找性能，因为它们占用的主内存更适合分配给缓冲区。Monkey消除了这种性能争用，从而通过使查找成本与缓冲区大小无关（只要\(M*{filters} > \frac{M*{threshold}}{T}\)，如公式8所示）来简化系统调优。然而，随着缓冲区继续增长，布隆过滤器缩小并最终消失，此时Monkey和现有技术的曲线汇合。图9的底部显示，增加缓冲区大小会降低更新成本，但随着更新成本以对数速率降低，收益递减。总体见解是，最好将缓冲区大小设置为尽可能大以降低更新成本，同时仍保持在其开始显著损害查找成本的点以下。我们在图9中将其标记为"最佳点"。在下一小节中，我们给出一个使用此见解在过滤器和缓冲区之间分配主内存的策略。

### 4.4 基于工作负载、硬件和SLA的调优

我们现在展示如何导航LSM树设计空间。Monkey通过能够精确地在查找成本、更新成本和主内存占用之间进行权衡来实现这一点，它控制四个调优参数：合并策略（tiering与leveling）、大小比、分配给过滤器的主内存量以及分配给缓冲区的主内存量。我们展示如何根据数据集（条目数量和大小）、工作负载（查找和更新的比例）和存储介质（读写成本比和磁盘块大小）来调优这些参数。我们对最坏情况吞吐量在这些参数下进行建模，并设计了一种找到最大化吞吐量的调优的算法。在表2中我们列出了新的术语。

**吞吐量建模。** 首先，我们通过对零结果点查找成本\(R\)、非零结果点查找成本\(V\)、范围查找成本\(Q\)和更新成本\(W\)（分别来自公式7、9、10和11）按工作负载中的比例（由项\(r\)、\(v\)、\(q\)和\(w\)表示，注意\(r + v + q + w = 1\)）进行加权，来建模平均操作成本\(\theta\)。结果为公式12。

\[\theta = r\cdot R + v\cdot V + q\cdot Q + w\cdot W \quad (12)\]

为了获得最坏情况吞吐量\(\tau\)，我们取平均操作成本\(\theta\)乘以\(\Omega\)（执行一次二级存储读取的时间）的倒数。结果为公式13。

\[\tau = 1 / (\theta \cdot \Omega) \quad (13)\]

**调优大小比和合并策略。** 合并策略和大小比是导航同一权衡连续体的互补手段。我们设计了一种分治算法，将该连续体线性化为单一维度，并找到最大化吞吐量的调优。图10展示了算法前三次迭代的示例，以找到标记为"目标"的最优调优。完整的算法见附录D。

该算法首先将\(T\)设置为2，并计算此调优的\(\theta\)。然后它迭代地将空间分为两部分，并计算每个部分中心的\(\theta*{1}\)和\(\theta*{2}\)。如果\(\theta*{1}\)或\(\theta*{2}\)小于\(\theta\)，我们在下一次迭代中缩小到该空间分区。否则，我们停留在同一点，但探测距离当前点两倍近的点。该算法运行时间为\(O(\log*2(T*{lim}))\)，因为可能有\(O(T\_{lim})\)种调优，并且我们每次迭代都缩小问题规模。在实践中，它在毫秒级内运行。

使用此算法，我们还可以对查找成本或更新成本施加上界，以支持不同的服务级别协议（SLA）。为此，算法丢弃查找或更新成本超过施加的上界的配置。这类似于在图10中通过设置查找成本的水平限制或更新成本的垂直限制来限制搜索空间。

**调优主内存分配。** 我们引入了一个三步策略来在缓冲区和过滤器之间分配可用主内存\(\hat{M}\)。公式8显示，当\(M*{filters}< \frac{M*{threshold}}{T*{L}}\)时，过滤器太小而无法产生任何收益，因此第一步是始终将\(\hat{M}\)的前\(\min (\hat{M},\frac{M*{threshold}}{T\_{L}})\)比特分配给缓冲区。在第二步中，我们将剩余主内存的\(5\%\)分配给缓冲区，\(95\%\)分配给过滤器。此方法近似图9中的最佳点。我们继续遵循第二步，直到由于假阳性产生的I/O开销变得可忽略（例如，与探测布隆过滤器的CPU和RAM开销相比，我们估计其约为微秒级）。在基于磁盘的系统中，寻道延迟约为10毫秒。这意味着当公式7中假阳性之和\(R\)达到\(10^{-4}\)量级时，I/O对查找延迟的平均贡献约为\(1\mu \mathrm{s}\)，与其他系统开销相比微不足道。闪存系统的类似阈值\(R\)为\(10^{-2}\)，因为对闪存设备的读I/O在数十到数百微秒量级。如果我们的预算中有更多主内存超出第二步，我们将其分配给缓冲区以进一步降低更新成本。

## 5. 实验分析

我们现在继续实验性地评估Monkey与现有技术设计。我们首先展示Monkey调优布隆过滤器的方法如何显著降低整个设计空间和各种工作负载下的查找成本。然后我们展示Monkey导航设计空间以为给定应用工作负载找到最大化吞吐量的设计的能力。

**实验设置。** 为了实验，我们使用一台配备500GB 7200RPM磁盘、32GB DDR4主内存和4个2.7GHz核心（8MB L3缓存）的机器。该机器运行64位Ubuntu 16.04 LTS，我们在关闭日志记录的ext4分区上运行实验。

**实现。** 我们在LevelDB之上实现了Monkey，LevelDB是一个众所周知且广泛使用的基于LSM树的键值存储，代表现有技术。LevelDB的当前实现是设计空间中的一个固定点。它只支持leveling作为合并策略，具有固定、硬编码的大小比，并为所有层级的过滤器分配相同的FPR。我们通过添加对tiering、不同大小比以及不同层级过滤器的最优FPR的支持（通过嵌入附录C中的算法）来实现Monkey。为了实现同类比较，在所有实验中，Monkey与LevelDB的唯一区别在于如何分配布隆过滤器，我们对所有其他参数使用相同的默认值。默认配置为：大小比为2（leveling和tiering行为相同的大小比）；缓冲区大小为1 MB；分配给所有布隆过滤器的总主内存量为\(\frac{M\_{filters}}{N} = 5\) bits per element（尽管Monkey在不同层级之间不同地分配这些比特）。我们一次改变其中一个参数，以在广泛的设计空间范围内进行比较。与最新版本的RocksDB类似，我们实现了直接I/O以便能够完全控制内存预算。此外，论文主体部分报告的所有实验都是在LevelDB和Monkey的块缓存被禁用的条件下进行的。这代表了一个最坏情况场景，即没有足够内存用于缓存，并允许我们测量Monkey对纯LSM树结构的影响。在附录F中，我们表明当有足够内存用于块缓存时，Monkey保持其优势。

**默认设置。** 除非另有说明，默认实验设置如下。数据库初始为空。我们插入1GB的键值条目，每个条目大小为1KB。条目在键空间中均匀随机分布，并以随机顺序插入。初始化阶段后，我们发出16K个均匀随机分布在键空间中的零结果点查找。（我们使用不同的数据大小和查询工作负载重复此设置的几种变体。）

**指标。** 我们重复每个实验试验（数据加载和查询）三次。对于每次试验，我们测量平均查找延迟和每次查找的I/O数。图中的误差条表示查找延迟跨试验的一个标准差。

**Monkey随数据量扩展性更好。** 在第一个实验中，我们展示Monkey随着数据量的增长以越来越大的幅度改善查找延迟。我们通过多次重复默认实验设置来设置此实验，每次使用更多的数据条目。

结果如图11（A）所示。LevelDB的查找延迟随着数据条目数的增加以对数速率增加，正如第4.3节中我们的成本模型所预测的那样。原因在于，随着数据条目数增加，LSM树的层级数以对数速率增加，而LevelDB的查找延迟与层级数成正比。相比之下，Monkey随着条目数的增加保持稳定的查找延迟，也如我们的成本模型所预测的那样。原因是Monkey为较低层级的过滤器分配指数级递减的FPR，因此每次查找的平均I/O数收敛到一个与层级数无关的常数。总体而言，Monkey优于LevelDB高达\(80\%\)，并且其改进幅度随着条目数的增长而增加。图11（A）中的水平虚线显示了查找延迟如何对应磁盘I/O。每次查找的平均I/O数低于1，因为查找通常只探测几个运行。

**Monkey在点查找中减少I/O。** 在下一个实验中，我们更深入地研究Monkey如何影响点查找的I/O行为和延迟。我们通过重复默认实验设置来设置此实验，但这次使用16KB的条目大小。

结果如图11（B）所示。我们绘制了每次查找的I/O数与查找延迟的关系。每个数据点代表不同的配置，其中我们改变大小比\(T\)和合并策略。对于每个配置，我们测量平均I/O数和平均查找延迟。一个关键的观察是，Monkey在所有配置下都优于LevelDB，将查找延迟降低了\(50\%\)到\(80\%\)。另一个观察是，Monkey能够减少I/O数和延迟之间的权衡。对于给定的I/O数，Monkey实现更低的延迟，反之亦然。这是因为Monkey在布隆过滤器之间最优地分配内存，减少了假阳性的数量，从而减少了查找的I/O数。

**Monkey在倾斜工作负载下表现更好。** 在下一个实验中，我们展示Monkey在存在时间局部性的倾斜工作负载下也优于LevelDB。我们通过重复默认实验设置来设置此实验，但这次查询不是均匀随机的，而是表现出时间局部性。我们使用参数\(c\)来控制局部性程度，其中\(c\)表示最近更新的条目中接收\((1-c)\)查询的比例。因此，较高的\(c\)值表示较强的时间局部性。

结果如图11（C）所示。对于所有工作负载，Monkey都优于LevelDB，并且其改进幅度随着局部性程度的增加而增加。在强局部性（\(c=0.9\)）下，Monkey将查找延迟降低了高达\(70\%\)。原因是具有时间局部性的工作负载倾向于查询较新的条目，这些条目位于较浅层级。Monkey为较浅层级分配更低的FPR，因此对于这些条目具有更少的假阳性。相比之下，LevelDB为所有层级分配相同的FPR，因此对于较浅层级的条目具有相对较高的假阳性率。

**Monkey在不同内存预算下表现更好。** 在下一个实验中，我们展示Monkey在不同主内存预算下优于LevelDB。我们通过重复默认实验设置来设置此实验，但这次我们改变分配给布隆过滤器的总主内存量\(\frac{M\_{filters}}{N}\)从1到10 bits per element。

结果如图11（D）所示。对于所有内存预算，Monkey都优于LevelDB。对于低内存预算（1 bit per element），Monkey将查找延迟降低了约\(50\%\)。对于高内存预算（10 bits per element），Monkey将查找延迟降低了约\(80\%\)。原因是Monkey在所有内存预算下都最优地分配内存，而LevelDB在内存预算低时次优地分配内存。

**Monkey在不同条目大小下表现更好。** 在下一个实验中，我们展示Monkey在不同条目大小下优于LevelDB。我们通过重复默认实验设置来设置此实验，但这次我们改变条目大小从256字节到4KB。

结果如图11（E）所示。对于所有条目大小，Monkey都优于LevelDB，并且其改进幅度随着条目大小的增加而增加。对于4KB条目，Monkey将查找延迟降低了高达\(60\%\)。原因是布隆过滤器只对条目数敏感，而不是它们的大小。因此，随着条目大小的增加，每元素比特数减少，布隆过滤器的假阳性率增加。Monkey通过最优地分配内存来缓解这种情况，而LevelDB在所有层级上均匀分配内存。

**Monkey在不同查找与更新比例下表现更好。** 在下一个实验中，我们展示Monkey在不同查找与更新比例下优于LevelDB。我们通过重复默认实验设置来设置此实验，但这次我们在查询处理阶段改变零结果查找与更新的比例从\(10\%\)到\(90\%\)。

我们比较Monkey的两个实例与LevelDB。第一个名为Fixed Monkey，是我们迄今为止实验过的Monkey默认配置。第二个名为Navigable Monkey，是完整版本，它导航设计空间以找到合并策略和大小比，从而在查找成本和更新成本之间取得平衡（以及相应的最优布隆过滤器分配），以最大化吞吐量。LevelDB和Fixed Monkey具有固定的大小比2（即leveling和tiering行为相同的空间点）。

结果如图11（F）所示。对于Navigable Monkey的每个数据点，我们显示其采用的配置（T代表tiering，L代表leveling，数字是大小比）。一个关键的观察是Navigable Monkey的曲线呈钟形。原因是工作负载越倾向于一种操作类型，就越有可能实现更高的吞吐量，因为单一配置能很好地处理大多数操作。总体而言，Fixed Monkey显著优于LevelDB，而Navigable Monkey显著优于Fixed Monkey。Navigable Monkey通过能够达到Pareto曲线并导航设计空间，使吞吐量相对于LevelDB提高了一倍以上。

## 6. 相关工作

**基于LSM的键值存储。** 作为现有技术的基于LSM树的键值存储[4, 12, 15, 18, 19, 21, 29, 34]，Monkey使用主内存中的布隆过滤器来概率性地使查找能够跳过LSM树中不包含目标键的运行。现有技术的基于LSM树的键值存储为每个布隆过滤器分配相同的误报率，而不管其对应的运行大小[4, 12, 15, 18, 19, 21, 29, 34]。在这项工作中，我们观察到最坏情况查找成本与所有过滤器误报率之和成正比。然而，为所有过滤器分配相等的误报率并不能最小化这个总和。

相反，Monkey通过将每个布隆过滤器的误报率设置为与其对应运行中的条目数成正比（意味着较浅层级的运行具有指数级更低的误报率）来最小化误报率之和。这降低了最坏情况查找成本的渐近复杂度，在实践中，它至少将查找延迟降低了\(50\% - 80\%\)，而没有损失任何东西。

**整体调优。** 现有的基于LSM树的键值存储不允许在查找成本、更新成本和主内存占用之间轻松地进行权衡。例如，LevelDB [19]将层级间大小比硬编码为10（使用leveled compaction），RocksDB [15]和LSM-trie [35]分别只启用leveled或tiered compaction，并且它们对所有布隆过滤器使用固定的每元素比特数。WiredTiger [34]支持动态的大小比值，起始值为15，然而，它也对所有布隆过滤器使用固定的每元素比特数（默认设置为16 bits per element）。此外，查找成本、更新成本和主内存占用之间的平衡取决于必须精确共同调优的相互依赖的调优和环境参数的组合。通过这种方式，现有键值存储中的调优实际上变成了一个试错过程，依赖于高素质工程师的直觉和经验。

Monkey代表了使这个过程更加自动化和简单的一步。它暴露了影响最坏情况查找成本、更新成本和主内存占用的关键调优参数。此外，它使用新颖的最坏情况封闭形式模型，能够优化吞吐量并回答关于环境参数变化如何影响性能的"假设"问题。

最近的互补工作[23]使用数值方法来估计在更新模式存在倾斜时leveled LSM树中的更新成本。我们在这里更进一步；我们在leveled和tiered LSM树下对查找成本和更新成本都进行建模，从而能够在整个设计空间上进行整体调优。

**去摊销合并操作。** 为了保持稳定的性能，所有基于LSM树的键值存储都将合并操作的工作分散到时间上。一些存储直接根据应用更新来调节合并操作[9, 22, 29]。另一些将运行分区为多个文件（通常称为SSTable），并一次将一个文件与下一层中具有重叠范围的文件集进行合并[4, 12, 15, 18, 19, 21, 29, 34]。其他最近的工作[1]提出在专用服务器上合并运行。由于我们的工作关注合并操作完成的总工作量而不是如何调度这些工作，上述任何技术都可以与Monkey结合使用。

**减少合并开销。** 为了减少合并操作期间复制的数据量，WiscKey [26]将值与键解耦，并将值存储在单独的日志中。这种技术与Monkey的核心设计兼容，但需要调整成本模型以考虑（1）只合并键，以及（2）查找期间必须访问日志。

VT-tree [30]提出在合并操作期间避免包含不重叠的运行部分。这种技术被用于主要的键值存储中，如果一个SSTable在下一层中没有具有重叠键范围的SSTable，它被简单地移动到下一层[4, 12, 15, 19, 21, 29]。我们在LevelDB上的实现利用了这种技术。

**内存存储。** 诸如Redis [28]和Memcached [17]之类的键值存储将应用数据存储在主内存中，而不是持久存储在二级存储中。我们在本文中专注于映射持久键值存储的设计空间，因此这项工作与内存工作正交。然而，鉴于在纯内存环境中为了最小化缓存未命中而存在类似的权衡，我们期望类似的研究来映射内存键值存储的设计空间也将是有益的。

## 7. 结论

我们表明，基于LSM树的键值存储在查找成本、更新成本和主内存占用之间表现出内在的权衡。然而，所有现有设计在这些指标之间达成了次优且难以调优的平衡。我们提出了Monkey，一种基于LSM的键值存储，它通过分配布隆过滤器以最小化最坏情况查找成本来达到Pareto性能曲线。Monkey使用封闭形式模型来导航设计空间，以在给定的主内存预算、应用工作负载和存储介质下找到最大化吞吐量的整体调优。

**LSM树的调优。** 本文中提供的封闭形式公式可用于针对给定场景（读/写比）静态调优键值存储。只要调优参数是暴露的，任何键值存储都可以使用这些公式沿Pareto曲线进行调优。

**任何LSM树应用。** LSM树被用于许多应用中。如果点查找的LSM树性能在关键路径上，任何场景都可以从我们的分析中受益以提高吞吐量。

## B. 最优误报率

在本附录中，我们通过优化查找成本\(R\)（公式3）相对于主内存占用\(M*{filters}\)（公式4）来推导最优误报率（FPR）\(p*{1}\ldots p\_{L}\)。为此，我们使用拉格朗日乘数法来找到在公式3作为约束的条件下最小化公式4的FPR。我们展示leveling的详细推导，然后给出tiering的结果，因为它是用公式3的tiering形式重复相同过程。我们首先将leveling的公式3和公式4表示为标准形式：

\[g(p*{L}\ldots p*{1},R) = p*{L} + p*{L - 1} + \ldots +p\_{1} - R\]

\[y(p*{L}\ldots p*{1},N,T) = -\frac{N}{\ln(2)^2}\cdot \frac{T - 1}{T}\cdot \sum*{i = 1}^{L}\frac{\ln(p*{i})}{T^{L - i}}\]

我们现在可以用这些函数表示拉格朗日函数：

\[\mathcal{L}(p*{L}\ldots p*{1},N,T,R,\lambda) = y(p*{L}\ldots p*{1},N,T) + \lambda \cdot g(p*{L}\ldots p*{1},R)\]

接下来，我们对拉格朗日函数关于每个FPR \(p*{1}\ldots p*{L}\)求偏导，并将每个偏导数设为0。因此，我们得到以下方程组。

\[\frac{N}{\ln(2)^2\cdot\lambda}\cdot \frac{T - 1}{T} = P\_{L - i}\cdot T^i\]

我们令这些方程相等以消去常数。

\[P*{L}\cdot T^{0} = P*{L - 1}\cdot T^{1} = \ldots = P\_{1}\cdot T^{L - 1}\]

我们现在用第\(L\)层的最优FPR \(P\_{L}\)来表示所有最优FPR。

\[P\_{L - i} = \frac{P_L}{T_i}\]

接下来，我们将这些FPR代入公式3，用仅含\(T\)和\(P_L\)的项来表示\(R\)。我们观察到\(R\)现在用一个几何级数表示。我们使用几何级数求和公式将其简化到\(L\)项。

\[\begin{array}{l}{R = \frac{p_L}{T^0} +\frac{p_L}{T^1} +\dots +\frac{p_L}{T^{L - 1}}}\\ {= p_L\cdot \frac{(\frac{1}{T})^L - 1}{\frac{1}{T} - 1}} \end{array} \quad (14)\]

我们现在重新排列，并用第\(i\)层的FPR进行通用表示。结果分别出现在leveled和tiered LSM树的公式15和16中。这些方程以\(R\)、\(T\)和\(L\)为参数，并返回任何第\(i\)层的FPR规定，使得用最少的主内存\(M\_{filters}\)来实现用户指定的\(R\)值。

| Leveling                                                               | Tiering                                                                |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| \(p\_{i}=\frac{R}{T^{L- i}}\cdot\frac{T^{L- 1}}{T^{L- 1}}\cdot(T- 1)\) | \(p\_{i}=\frac{R}{T^{L- i}}\cdot\frac{T^{L- 1}}{T^{L- 1}}\cdot(T- 1)\) |
| \(0< R< \frac{T^{L- 1}}{T^{L- 1}}\cdot\frac{1}{T- 1}\)                 | \(0< R< \frac{T^{L- 1}}{T^{L- 1}}\)                                    |
| 且 \(1\leq i\leq L\)                                                   | 且 \(1\leq i\leq L\)                                                   |

公式15和16之间的关键区别在于，tiering下分配给任何第\(i\)层的最优误报率比leveling下低\((T - 1)\)倍。原因是在tiering中每层包含\((T - 1)\)个运行，因此为了保持\(R\)固定，误报率必须降低\((T - 1)\)倍。

**支持\(R\)的整个范围。** \(R\)的最高可能值是LSM树中的运行数：leveling为\(L\)，tiering为\(L\cdot (T - 1)\)。然而，当\(R\)设置高于leveling下的\(\frac{T^{L - 1}}{T^{L - 1}}\cdot \frac{1}{T - 1}\)和tiering下的\(\frac{T^{L - 1}}{T^{L - 1}}\)时，公式15和16是未定义的。原因是当\(R\)增长超过这些界限时，FPR规定开始超过1。这违反了误报率最多为1的约束。

我们现在展示如何调整公式15和16以处理更大的\(R\)值。第一个关键见解是，第\(i\)层的FPR严格大于第\(i - 1\)层的FPR。这意味着随着\(R\)的增长，\(p*i\)在\(p*{i - 1}\)之前收敛到1。因此，随着\(R\)的增加，FPR从最深到最浅的顺序收敛到1。因此，我们将\(L*{\text{unfiltered}}\)表示为从第\(L\)层向下FPR收敛到1的层级数，而\(L*{\text{filtered}}\)是从第1层向上FPR低于1的层级数。这种层级划分如图6所示。注意\(L = L*{\text{filtered}} + L*{\text{unfiltered}}\)。

第二个关键见解是，过滤层级\(L*{\text{filtered}}\)的FPR之和在leveling下永远不能大于2，在tiering下不能大于\(2\cdot (T-1)\)，因为这些层级中最大层级的FPR最多为1，其余FPR呈指数递减。这意味着如果\(R\)大于这些界限，则\(L*{\text{unfiltered}}\)必须非零。事实上，它意味着\(L\_{\text{unfiltered}}\)在leveling下等于\(\max (0,\lfloor R - 1\rfloor)\)，在tiering下等于\(\max (0,\lfloor \frac{R - 1}{T - 1}\rfloor)\)。

第三个关键见解是，我们现在可以将公式15和16应用于具有\(L*{\text{unfiltered}}\)层布隆过滤器的较小版本问题，其中这些层级的假阳性之和在leveling下为\(R - L*{\text{unfiltered}}\)，在tiering下为\(R - L\_{\text{unfiltered}}\cdot (T - 1)\)。

我们的调整分别出现在公式17和18中。为简洁起见，我们在这些方程中使用\(L*{u}\)表示\(L*{\text{unfiltered}}\)。

| Leveling                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| \(p*{i}=\left\{\begin{array}{l l}{{1,}}&{{\text{如果 } i>L- L*{u}}}\\ {{\frac{R- L_{u}}{T- L*{u}- i}}\cdot\frac{T^{L- L*{u}- 1}\cdot(T- 1)}{T- L*{u}- 1},}&{{\text{否则}}}\\ {{\text{对于 } 0< R\leq L}}\\ {{\text{且 } 1\leq i\leq L}}\\ {{\text{且 } L*{u}=\max (0,\lfloor R- 1\rfloor)}}\end{array}\right.\) |
| (17)                                                                                                                                                                                                                                                                                                            |

| Tiering                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| \(p*{i}=\left\{\begin{array}{l l}{{1,}}&{{\text{如果 } i>L- L*{u}}}\\ {{\frac{R- L_{u}\cdot(T-1)}{T- L_{u}- i}}\cdot\frac{T^{L- L*{u}- 1}}{T- L*{u}- 1},}&{{\text{否则}}}\\ {{\text{对于 } 0< R\leq L\cdot(T-1)}}\\ {{\text{且 } 1\leq i\leq L}}\\ {{\text{且 } L_{u}=\max (0,\lfloor \frac{R-1}{T-1}\rfloor)}}\end{array}\right.\) |
| (18)                                                                                                                                                                                                                                                                                                                                |

**简化。** 随着层级数\(L\)的增长，公式15和16分别收敛到leveling下的\(P*{i} = \frac{R}{T^{L - i}}\cdot (T - 1)\)和tiering下的\(P*{i} = \frac{R}{T^{L - i}}\)。当\(L\)约为5或以上时，这些简化方程已经能准确近似最优误报率。我们可以利用这一见解将公式17和18简化为第4.1节中出现的公式5和6。对于实际分析和实现，我们建议使用公式17和18。

### B.1 内存占用和查找成本建模

我们现在展示如何推导Monkey中过滤器主内存利用\(M*{filters}\)和查找成本\(R\)的封闭形式模型。我们首先假设所有层级都有过滤器，但稍后我们将模型扩展以支持并非所有层级都有过滤器的情况（即\(L*{\text{unfiltered}} = 0\)）。我们的逐步示例针对leveling，但tiering的情况是相同的，只是我们需要使用公式6而不是公式5。我们首先将最优误报率（leveling的公式5）代入公式4，得到布隆过滤器相对于误报率的主内存利用。

\[M*{\text{filtered}} = -\frac{N}{\ln(2)^2}\cdot \frac{T - 1}{T}\cdot \left(\sum*{i = 0}^{L}\frac{1}{T^i}\ln \left(R\frac{T - 1}{T^{i + i}}\right)\right)\]

然后我们应用对数运算得到以下结果：

\[M\_{\text{filtered}} = -\frac{N}{\ln(2)^2}\cdot \frac{T - 1}{T}\cdot \ln \left(\frac{R^{1 + \frac{1}{T} + \frac{1}{T^2} + \dots}(T - 1)^{1 + \frac{1}{T} + \frac{1}{T^2} +\dots}}{T^{\frac{1}{T^0} + \frac{2}{T^1} + \frac{2}{T^2} + \dots}}\right)\]

为了简化上述方程，我们对分子的指数应用几何级数求和公式，对分母的指数应用算术-几何级数求和公式。经过进一步简化得到：

\[M\_{\text{filtered}} = \left\{ \begin{array}{ll}\frac{N}{\ln(2)^2}\cdot \ln \left(\frac{T^{\frac{T}{T - 1}}}{R\cdot(T - 1)}\right) & \mathrm{使用~leveling}\\ \frac{N}{\ln(2)^2}\cdot \ln \left(\frac{T^{\frac{T}{T - 1}}}{R}\right) & \mathrm{使用~tiering} \end{array} \right. \quad (19)\]

我们现在将此方程扩展到\(L*{\text{unfiltered}} > 0\)的情况。在这种情况下，FPR收敛到1的层级的布隆过滤器不占用空间，因此我们只需要找到较浅\(L*{\text{filtered}}\)层级中过滤器占用的空间。为此，我们通过将公式19应用于具有\(N / T^{L*{\text{unfiltered}}}\)个条目（即较浅\(L*{\text{filtered}}\)层级中的条目数）的较小版本问题来调整它，并从\(R\)中减去无过滤器层级中的运行数。

\[M*{filters} =
\begin{cases}
\frac{N}{\ln(2)^2 \cdot T^{L*{unfiltered}}} \cdot \ln\left(\frac{T^{\frac{T}{T-1}}}{(R - L*{unfiltered}) \cdot (T - 1)}\right) & \text{对于 leveling} \\
\frac{N}{\ln(2)^2 \cdot T^{L*{unfiltered}}} \cdot \ln\left(\frac{T^{\frac{T}{T-1}}}{R - L\_{unfiltered} \cdot (T - 1)}\right) & \text{对于 tiering}
\end{cases}
\quad (20)\]

**查找成本。** 我们现在将公式19重新排列为查找成本\(R\)的形式。

\[R*{filtered} =
\begin{cases}
\frac{T^{\frac{T}{T-1}}}{T - 1} \cdot e^{-\frac{M*{filters}}{N} \cdot \ln(2)^2} & \text{使用 leveling} \\
T^{\frac{T}{T-1}} \cdot e^{-\frac{M\_{filters}}{N} \cdot \ln(2)^2} & \text{使用 tiering}
\end{cases}
\quad (21)\]

上述方程尚未适应\(M*{filters}\)低到某些更深层级的过滤器消失的情况。为了适应这种情况，我们首先找到阈值点\(M*{threshold}\)，在此点最高层级过滤器的FPR收敛到1。为此，我们将\(R\)的界限（leveling下为\(\frac{T}{T-1}\)，tiering下为\(T\)）代入公式19。结果对leveling和tiering都简化为以下形式。

\[M\_{threshold} = N \cdot \frac{1}{(T - 1)} \cdot \frac{\ln(T)}{\ln(2)^2}\]

随着\(M\)下降到\(M\_{threshold}\)以下，每次减少因子\(T\)，下一个更深层级的过滤器收敛到1。因此，我们可以如公式22所示计算无过滤器的层级数。

\[L*{unfiltered} =
\begin{cases}
0, & M*{threshold} \le M*{filters} \\
\left\lceil \log_T \left(\frac{M*{threshold}}{M*{filters}}\right) \right\rceil, & \frac{M*{threshold}}{T^L} \le M*{filters} \le M*{threshold} \\
L, & 0 \le M*{filters} \le \frac{M*{threshold}}{T^L}
\end{cases}
\quad (22)\]

现在，在最深的无过滤器层级中，我们需要探测每个运行，即leveling下为\(L*{unfiltered}\)，tiering下为\((T - 1) \cdot L*{unfiltered}\)。在有过滤器的层级中，我们必须探测的平均运行数等于其假阳性之和，因此我们可以将公式21应用于具有\(N / T^{L\_{unfiltered}}\)个层级的较小版本问题。这成为第4.2节中的公式7。

## C. 自动调优过滤器

在第4.1节中，我们表明最优FPR与每层中的条目数成正比。我们的分析假设条目大小是固定的，因此我们可以轻松推断每层的元素数，从而为其过滤器分配最优FPR。然而，在实践中，平均条目大小可能是可变的，或者可能随时间变化。如果是这种情况，我们不能再推断每层的元素数。为了处理这个问题，我们扩展了Monkey的实现，将每个运行的条目数记录为元数据。然后我们使用此元数据通过算法1（以及辅助算法2和3）找到最优误报率。算法1以（1）分配给布隆过滤器的总主内存量\(M\_{filters}\)，以及（2）一个运行向量为参数，其中每个运行有一对值，runs[i].entries是条目数，runs[i].bits是分配给第i个运行布隆过滤器的位数。该算法迭代地在不同布隆过滤器之间移动主内存，直到其假阳性之和最小化。该算法不需要频繁运行，在我们的实验平台上执行只需几分之一秒。

```
1 AutotuneFilters (M_filters, runs)
2     ∆ = M_filters;
3     runs[0] = M_filters;
4     R = runs.length - 1 + eval(runs[0].bits, runs[0].entries);
5     while ∆ >= 1 do
6         R_new = R;
7         for int i = 0; i < runs.length - 1; i++ do
8             for int j = i + 1; j < runs.length; j++ do
9                 R_new = TrySwitch(runs[i], runs[j], ∆, R_new);
10                R_new = TrySwitch(runs[j], runs[i], ∆, R_new);
11            end
12        end
13        if R_new == R then
14            ∆ = ∆ / 2;
15        end
16        R = R_new;
17    end
18    return R;
```

算法1: 分配M_filters以最小化FPR之和。

```
1 TrySwitch (run1, run2, ∆, R)
2     R_new = R - eval(run1.bits, run1.entries) - eval(run2.bits, run2.entries)
               + eval(run1.bits + ∆, run1.entries) + eval(run2.bits - ∆, run2.entries);
3     if R_new < R and run2.bits - ∆ > 0 then
4         R = R_new;
5         run1.bits += ∆;
6         run2.bits -= ∆;
7     end
8     return R;
```

算法2: 如果减少R，则将∆比特从run2移动到run1。

```
1 eval (bits, entries)
2     return e^{-(bits / entries) * ln(2)^2};
```

算法3: 返回布隆过滤器的误报率。

## D. 自动调优大小比和合并策略

在本附录中，我们给出完整的自动调优算法。该算法将调优空间线性化为一个维度，并在其上执行二分搜索。它由算法5组成，该算法计算归一化操作成本\(\theta\)。算法的主体在算法4中，我们在调优空间上执行二分搜索。

```
1 Autotune ()
2     i = 0;
3     θ = compute(i);
4     ∆ = (1/2) * (N * E / M_buffer);
5     while ∆ >= 1 do
6         θ1 = compute(i + ∆);
7         θ2 = compute(i - ∆);
8         if θ1 < θ and θ1 < θ2 then
9             θ = θ1;
10            i = i + ∆;
11        else if θ2 < θ then
12            θ = θ2;
13            i = i - ∆;
14        end
15        ∆ = ∆ / 2;
16    end
17    T_best = |i| + 2;
18    merge_best = if i > 0 then tiering else leveling;
```

算法4: 找到最佳大小比和合并策略。

```
1 compute (i)
2     T = |i| + 2;
3     merge = if i > 0 then tiering else leveling;
4     θ = θ(T, merge); // 公式12
5     return θ;
```

## E. 基线

在本附录中，我们对现有技术的预期零结果点查找I/O成本\(R\_{art}\)进行建模。首先，我们推导反映现有技术如何在leveling和tiering下分配误报率的方程。我们通过将公式3中的所有误报率\(p_1, p_2...p_L\)设置为彼此相等，简化并重新排列来实现。结果如公式23和24所示。

**Leveling**
\[p*i = \frac{R*{art}}{L} \quad \text{对于 } 0 < R\_{art} \le L \text{ 且 } 1 \le i \le L \quad (23)\]

**Tiering**
\[p*i = \frac{R*{art}}{L \cdot (T - 1)} \quad \text{对于 } 0 < R\_{art} \le L \cdot (T - 1) \text{ 且 } 1 \le i \le L \quad (24)\]

其次，我们将公式23和24中的误报率代入公式4，并通过应用对数运算和几何级数求和进行简化。结果如公式25所示。

\[R*{art} = \left\{ \begin{array}{ll}L\cdot e^{-\frac{M*{filters}}{N}}\ln (2)^2, & \text{使用 leveling}\\ L\cdot (T - 1)\cdot e^{-\frac{M*{filters}}{N}}\ln (2)^2, & \text{使用 tiering} \end{array} \right. \quad \text{对于 } 0 < M*{filters} \le N \cdot E \quad (25)\]

\(R*{art}\)的相应大O表示为leveling的\(O(L\cdot e^{-\frac{M*{filters}}{N}})\)和tiering的\(O(L\cdot T\cdot e^{-\frac{M\_{filters}}{N}})\)。

## F. 缓存

在论文主体部分的所有实验中，LevelDB和Monkey都不使用缓存。我们通过显式禁用LevelDB中的块缓存来实现这一点。我们使用此设置是为了隔离新的布隆过滤器分配策略的影响，以评估Monkey的潜力及其对纯LSM树结构的影响。在本实验中，我们启用块缓存，并表明Monkey（1）保持其优势，并且（2）在查询最近访问的键时能够利用缓存。

我们按如下方式设置此实验。我们激活LevelDB的块缓存功能，它缓存最近访问的数据块（在我们的设置中为16 KB）。我们使用三种不同的设置，其中块缓存大小分别为总数据量的\(0\%\)、\(20\%\)和\(40\%\)。我们从论文主体部分重复默认数据加载设置。数据加载后，我们使用具有不同时间局部性的非零结果查找来预热缓存。为了控制时间局部性，我们使用时间系数\(c\)（如第5节图11（D）的实验中那样），其中\(c\)百分比的最常更新的条目接收\((1-c)\)百分比的查找。当缓存预热（即满）时，我们继续发出相同的工作负载并测量平均查找时间。通过这种方式，我们测试了各种工作负载，即查询频率不同的键。通过改变此参数，我们能够测试缓存的效用不同的各种情况。

结果如图12所示。图12（A）作为参考，显示了不使用缓存时的性能。这与我们在先前实验中观察到的相同，Monkey在整个工作负载范围内都优于LevelDB。当启用缓存时，我们观察到图12（B）和（C）中相同的总体行为，Monkey优于LevelDB。这里的区别在于，当我们查询最近访问的键时，这些键可能存在于缓存中，因此不会通过LSM树处理。结果，当我们查询更多最近访问的项时，Monkey和LevelDB几乎收敛。Monkey可以像LevelDB一样利用缓存来缓存频繁访问的项。另一个属性是，即使查找主要针对累计大小远小于总缓存大小的一小组条目（例如，当图12（B）和（C）中\(c\)设置为0.9时），Monkey仍然保持较小的优势（对所有查询累计起来变得重要）。原因是缓存无法存储完整的一组频繁访问条目以消除访问它们的I/O；它是块缓存，因此为每个最近访问的1 KB键值条目存储一个16 KB的数据块。

总体而言，Monkey可以利用缓存，并且由于其在布隆过滤器之间更好的误报率分配，保持了性能优势。布隆过滤器和缓存分别缓解了很大程度上不同的延迟来源：假阳性和真阳性。在这项工作中，我们专注于调优布隆过滤器以减少和控制由于假阳性引起的I/O率。进一步的研究可能有助于同时调优缓存以减少和控制由于真阳性引起的I/O率。
